EXECUTIVE ARCHITECTURAL SUMMARY & VERSION 3.0 MANDATE
================================================================================

Version 3.0 of the Memory Engine introduces a foundational architectural upgrade:
the HYBRID MEMORY OWNERSHIP PRINCIPLE.

Version 2.0 treated the Memory Engine primarily as an advanced storage, retrieval, and
consolidation system — a database with structured epistemic records. It was passive:
other engines stored information, and Memory retrieved it on request.

Version 3.0 introduces a bidirectional development relationship:

  MEMORY CAN DEVELOP ITS OWN KNOWLEDGE STRUCTURES INDEPENDENTLY
  WHILE SPECIALIZED ENGINES RETAIN AUTHORITY OVER THEIR OWN INTERPRETATION DOMAINS.

This distinction matters because:

  - Memory can DISCOVER that three experiences share a recurring pattern.
  - Thought Engine can INVESTIGATE why that pattern exists.
  - Emotion Engine can EVALUATE the pattern's emotional significance.
  - Social Cognition can INTERPRET the interpersonal implications.
  - Learning Engine can IDENTIFY what process should be improved.
  - Memory can INTEGRATE validated contributions into its knowledge structures.

This is a feedback loop, not a one-way storage pipeline.


THE HYBRID OWNERSHIP PRINCIPLE — TWO DEVELOPMENT PATHS:
---------------------------------------------------------

PATH A — Independent Memory Development (Memory-Owned):
  Operations Memory performs without requesting another cognitive engine:
  - Experience organization and temporal ordering.
  - Entity association and alias resolution.
  - Pattern frequency detection (co-occurrence, recurrence).
  - Duplicate detection and record deduplication.
  - Knowledge generalization proposals (not automatic acceptance).
  - Memory consolidation (with seven-gate verification).
  - Contradiction detection between claims.
  - Retrieval gap and unresolved-question identification.

PATH B — Collaborative Cognitive Development (Cross-Engine):
  Operations requiring specialized engines:
  - Thought Engine: Investigate why a detected pattern exists.
  - Emotion Engine: Re-assess or develop emotional appraisals.
  - Social Cognition: Interpret interpersonal and relationship patterns.
  - Learning Engine: Identify procedural lessons and skill improvements.
  - Motivation Engine: Assess relevance to current goals and drives.


THE FOUR FINALIZED ARCHITECTURE DECISIONS:
------------------------------------------

Decision 1 — WHEN DOES MEMORY DEVELOPMENT HAPPEN?
  Selected: HYBRID PROCESSING
  Immediate lightweight operations on new data arrival; deeper background development
  when resources are available. No continuous polling; event-triggered + scheduled.

Decision 2 — HOW ARE GENERALIZATIONS ACCEPTED?
  Selected: RISK-BASED ACCEPTANCE
  Simple evidence-backed organizational representations can be accepted by Memory
  internally after deterministic validation. Uncertain, consequential, or contradicted
  interpretations require specialized cognitive review before acceptance.

Decision 3 — CAN RETRIEVAL TRIGGER DEVELOPMENT?
  Selected: GENERATE DEVELOPMENT PROPOSALS
  Retrieval may expose knowledge gaps, contradictions, or patterns and schedule
  development jobs. Retrieval never directly modifies or consolidates knowledge.

Decision 4 — COGNITIVE vs. AUTONOMOUS MEMORY?
  Selected: SHARED CORE WITH INDEPENDENT DOMAIN ADAPTERS
  One common Memory Engine implementation with separate cognitive and autonomous
  domain interfaces, isolated data partitions, and independent access policies.

PART 1 — DATA STRUCTURES & TYPE SYSTEM
================================================================================

This part defines every core data structure, enum, Pydantic model, and mathematical
type used throughout the Memory Engine. All structures are immutable (frozen=True) unless
explicitly noted as mutable runtime state.


1.1 REPRESENTATION TYPES & KNOWLEDGE DEVELOPMENT STATES
--------------------------------------------------------

REPRESENTATION TYPES — What kind of memory record is this?

  RAW_EXPERIENCE:   Unprocessed event record, as captured at intake time.
  EPISODIC:         A specific bounded experience with actors, time, and context.
  SEMANTIC:         A generalized fact, concept, or world-knowledge claim.
  AUTOBIOGRAPHICAL: Part of Diva's self-narrative, identity, or personal history.
  RELATIONSHIP:     Representation of an interpersonal dynamic or social bond.
  PROCEDURAL:       A learned skill, process, or strategy (how-to knowledge).
  GENERALIZED:      A pattern, abstraction, or generalization derived from episodes.
  CONSOLIDATED:     An integrated representation combining multiple related records.
  REFLECTIVE:       A metacognitive record about Diva's own knowledge or behavior.

A single experience can be associated with MULTIPLE representation types simultaneously.
Representations do not replace one another — they layer on top of the original record.

DEVELOPMENT STATUS STATES — Where is a knowledge structure in its lifecycle?

  RAW:          Stored; no processing performed beyond intake validation.
  ORGANIZED:    Sorted into temporal sequences, entity associations resolved.
  ASSOCIATED:   Connections established to related memories and concepts.
  PROPOSED:     A candidate representation generated but not yet validated.
  UNDER_REVIEW: Awaiting specialized cognitive engine assessment.
  ACCEPTED:     Validated and integrated into established knowledge structures.
  DISPUTED:     Contradicting evidence exists; active conflict not resolved.
  SUPERSEDED:   Replaced by a more accurate or comprehensive representation.
  ARCHIVED:     Moved to cold storage; source records preserved; not in active index.

LIFECYCLE DIMENSIONS — Kept Separate (Three Independent Dimensions):

  Dimension 1: Development Status  → (above enum)
  Dimension 2: Validity Status     → CURRENT | HISTORICAL | RETRACTED | REFUTED
  Dimension 3: Retention Status    → ACTIVE | CONSOLIDATED | ARCHIVED | DEPENDENCY_LOCKED

An archived memory may still contain a CURRENT validity claim.
A DISPUTED claim may still be ACTIVE in retention.
These dimensions MUST NOT be collapsed into a single enum.

DOMAIN PARTITION — Cognitive vs. Autonomous:

  COGNITIVE:   Owned by the deliberate cognitive processing domain (Engines 1-14).
  AUTONOMOUS:  Owned by Diva's independent background activity domain.
  SHARED:      Accessible to both domains under explicit access grants.

Data in the COGNITIVE partition is inaccessible to AUTONOMOUS processing by default.
Data in the AUTONOMOUS partition is inaccessible to COGNITIVE processing by default.
Shared data requires an explicit access_policy record and an audit event.


1.2 EPISTEMIC MODEL: CLAIMS, ASSESSMENTS, EVIDENCE
---------------------------------------------------

Claims are the atomic epistemic unit of Diva's knowledge system.
A claim is a proposition with independent epistemic dimensions.

EPISTEMIC TYPE — How was this claim produced?

  OBSERVATION:     Directly sensed by Diva's Input/Perception engine. Highest raw
                   fidelity, but Perception may still misinterpret signals.
  REPORTED:        A claim made by another agent (user, system, source document).
                   Memory preserves the report without asserting its truth.
  INFERENCE:       Derived by logical or statistical reasoning from observed evidence.
  INTERPRETATION:  A cognitive evaluation of meaning (Emotion, Social Cognition, Thought).
  OPINION:         An evaluative stance, preference, or aesthetic judgment.
  UNKNOWN:         Epistemic type cannot be established from available provenance.

EVIDENCE STATUS — How well is the claim supported?

  UNVERIFIED:    No corroborating evidence beyond initial source; not disputed.
  SUPPORTED:     At least one independent evidence record aligns.
  CORROBORATED:  Multiple independent evidence records consistently support the claim.
  DISPUTED:      At least one piece of conflicting evidence exists; not resolved.
  REFUTED:       The claim has been directly contradicted by reliable evidence.

CLAIM LIFECYCLE — Where is this claim in its operational lifecycle?

  ACTIVE:      Currently part of Diva's knowledge base; accessible to reasoning.
  HISTORICAL:  Was accurate for a past time window; superseded by later records.
  SUPERSEDED:  Replaced by a more precise or updated claim (linked by CORRECTS relationship).
  RETRACTED:   Withdrawn due to discovered source error or deliberate correction.

CLAIM DATA STRUCTURE (Primary Pydantic Contract):

  MemoryClaim (frozen=True):
    claim_id:           UUID         — UUIDv7, monotonically ordered
    subject_entity_id:  UUID | None  — FK to entities table (may be None for universal claims)
    predicate:          str          — Relationship verb / property name (lowercase slug)
    object_value:       str          — Literal string value or FK-reference identifier
    canonical_statement:str          — Human-readable full sentence form of the claim
    epistemic_type:     EpistemicType
    evidence_status:    EvidenceStatus
    lifecycle:          ClaimLifecycle
    domain_partition:   DomainPartition
    source_engine:      str          — Engine that submitted the claim
    source_session_id:  UUID         — Session during which the claim was submitted
    world_time_start:   datetime     — When this was true in the world (may be NULL = unknown)
    world_time_end:     datetime | None — When this stopped being true (NULL = still valid)
    diva_time_recorded: datetime     — When Diva first recorded this claim
    provenance_hash:    str          — SHA-256 of canonical_statement + source_engine + diva_time
    version:            int          — Monotonically incrementing; starts at 1

  ClaimAssessment (frozen=True):
    assessment_id:      UUID
    claim_id:           UUID         — FK to claims
    assessor_engine:    str          — Which engine produced this assessment
    assessor_session:   UUID         — Session context during assessment
    confidence:         float        — [0.0, 1.0]; assessor's confidence, NOT objective probability
    rationale:          str          — Explanation of the confidence value
    assessed_at:        datetime
    assessment_method:  str          — e.g. "DETERMINISTIC_RULE", "LLM_INFERENCE", "HEURISTIC"

  EvidenceReference (frozen=True):
    evidence_id:        UUID
    claim_id:           UUID         — FK to claims (this evidence supports or opposes this claim)
    source_memory_id:   UUID | None  — FK to experiences (original event evidence)
    source_claim_id:    UUID | None  — FK to claims (a claim as evidence for another claim)
    relationship:       EvidenceRole — SUPPORTS | OPPOSES | CONTEXTUALIZES
    weight:             float        — [0.0, 1.0]; relative evidence strength
    added_at:           datetime

NOTE ON CONFIDENCE:
  Confidence is a property of a specific ClaimAssessment by an identified assessor.
  It is NOT a property of the claim itself. The claim has an evidence_status derived
  from the totality of evidence records, not from one engine's confidence score.


1.3 TYPED CLAIM RELATIONSHIPS
------------------------------

Relationships between claims are stored as explicit, typed graph edges in the
claim_relationships table. They are NOT implicit from co-occurrence or proximity.

ClaimRelationshipType:
  SUPPORTS:        Claim A provides supporting evidence for Claim B.
  CONTRADICTS:     Claim A and Claim B make mutually exclusive assertions.
  DERIVED_FROM:    Claim A was derived by inference or generalization from Claim B.
  CORRECTS:        Claim A is a more accurate replacement for Claim B (B → SUPERSEDED).
  GENERALIZES:     Claim A is a general form of the more specific Claim B.
  SPECIALIZES:     Claim A is a specific instance of the more general Claim B.
  SUPERSEDES:      Claim A completely replaces Claim B, which is now HISTORICAL.
  ASSOCIATED_WITH: Claim A and Claim B are related but no stronger semantics applies.
  CO_OCCURS_WITH:  Claim A and Claim B appear together frequently; NO causal inference made.

IMPORTANT: CO_OCCURS_WITH does NOT imply causation. Memory can propose a co-occurrence
relationship. The Thought Engine is responsible for investigating causal explanations.
Contradiction graphs MAY contain cycles — this is acceptable and expected.

ClaimRelationship (frozen=True):
  relationship_id:    UUID
  claim_id_source:    UUID   — FK to claims (from)
  claim_id_target:    UUID   — FK to claims (to)
  relationship_type:  ClaimRelationshipType
  confidence:         float  — [0.0, 1.0]
  established_by:     str    — Engine or subsystem that established this relationship
  established_at:     datetime
  supporting_evidence:list[UUID]  — FKs to evidence_references

1.6 CONTINUITY CHECKPOINT DATA STRUCTURES
-------------------------------------------

Memory Continuity persists authorized snapshots of state OWNED BY OTHER ENGINES.
It does NOT own cognitive state directly.

ContinuityCheckpoint (frozen=True):
  checkpoint_id:              UUID
  session_id:                 UUID
  schema_version:             int     — Checkpoint schema version for forward-compat validation
  workspace_snapshot_ref:     UUID | None  — Reference to Shared Context Workspace snapshot
  attention_snapshot_ref:     UUID | None  — Reference to Attention Engine state snapshot
  activity_snapshot_refs:     tuple[UUID, ...]  — Activity Controller task snapshots
  active_goal_refs:           tuple[UUID, ...]  — Goal identifiers from Motivation Engine
  unresolved_commitment_refs: tuple[UUID, ...]  — Incomplete commitments from Decision Engine
  created_at:                 datetime
  valid:                      bool    — Passes integrity check
  restoration_attempted:      bool
  restoration_succeeded:      bool | None

RESTORATION PROTOCOL:
  1. Memory Continuity retrieves latest valid checkpoint with valid=True.
  2. Schema version is compared against current; mismatch triggers migration check.
  3. For each snapshot_ref, Memory Continuity notifies the OWNING ENGINE with the ref UUID.
  4. Each owning engine independently validates its own snapshot and restores its state.
  5. Memory Continuity does NOT interpret or parse the snapshot content itself.
  6. Autonomous processing checkpoints are stored in a SEPARATE table with restricted access.

1.8 LIFECYCLE DIMENSION SEPARATION
------------------------------------

The memory lifecycle has THREE INDEPENDENT DIMENSIONS that must NEVER be collapsed:

DEVELOPMENT DIMENSION:
  RAW → ORGANIZED → ASSOCIATED → PROPOSED → UNDER_REVIEW → ACCEPTED | DISPUTED
  ACCEPTED can transition to SUPERSEDED.
  DISPUTED may resolve to ACCEPTED or remain indefinitely.

VALIDITY DIMENSION:
  CURRENT:    This record accurately represents the current state of knowledge.
  HISTORICAL: This record was accurate for a past time window; not currently valid.
  RETRACTED:  Withdrawn by the originating engine due to source error or correction.
  REFUTED:    Directly contradicted by reliable, authoritative evidence.

  Validity state changes are ALWAYS represented as new events, never as updates to old records.

RETENTION DIMENSION:
  ACTIVE:            In primary storage; fully indexed; retrieved normally.
  CONSOLIDATED:      Original is in primary storage; a consolidated representation exists.
  DEPENDENCY_LOCKED: Cannot be archived because active records depend on this one.
  ARCHIVAL_ELIGIBLE: All retention conditions satisfied; may move to cold storage.
  ARCHIVED:          Moved to cold archive; retrievable but not in hot indexes.

ORTHOGONALITY RULE:
  Any combination of these three dimensions is valid:
  - An ARCHIVED (retention) memory can be CURRENT (validity) and ACCEPTED (development).
  - A DISPUTED (development) claim can be ACTIVE (retention) and HISTORICAL (validity).
  - A CONSOLIDATED (retention) record can be SUPERSEDED (development) and RETRACTED (validity).


1.9 IMPORTANCE, ACTIVATION & DEVELOPMENT PRIORITY MATHEMATICS
--------------------------------------------------------------

FOUR DISTINCT NUMERICAL DIMENSIONS (never collapsed into one score):

  Dimension A: PERMANENT IMPORTANCE   I_perm ∈ [0.0, 1.0]
    Long-term structural significance. Set at intake; updated via explicit reassessment events.
    Not subject to time decay. Changes only through deliberate cognitive events.

  Dimension B: TEMPORARY IMPORTANCE   I_temp(t) ∈ [0.0, 1.0]
    Current task or situation relevance. Decays when associated tasks complete.
    I_temp(t) = I_temp_initial × max(0, 1 - (t - t_assigned) / task_lifetime)

  COMPOSITE IMPORTANCE:
    I_total(M, t) = max(I_perm(M), I_temp(M, t))
    This ensures temporary relevance does not permanently elevate importance scores.

  Dimension C: RETRIEVAL ACTIVATION   A(M, t) ∈ [0.0, +∞)
    Based on ACT-R memory activation model:
    B(M, t) = ln( Σ_j t_j^(-d) )    [base-level activation: sum of recency-weighted accesses]
      where t_j = time since j-th access, d = decay parameter (default: 0.5)
    S(M, t) = Σ_k W_k × S_k(M)      [associative spread from currently active concepts W_k]
    A(M, t) = B(M, t) + S(M, t)

    Implementation note: B(M, t) is approximated during batch retrieval using the
    Anderson (2004) approximation:
      B(M, t) = ln(n / (1 - d)) - d × ln(L)
      where n = total access count, L = lifetime since creation

  Dimension D: DEVELOPMENT PRIORITY   P_dev ∈ [0.0, 1.0]
    Determines which memories are worth developing further:
    P_dev(M) = w1 × I_total(M, t) + w2 × R(M) + w3 × U(M) + w4 × D(M)

    Where:
      R = Recurrence strength (pattern frequency score)
      U = Uncertainty level (gap between CORROBORATED and UNVERIFIED evidence)
      D = Dependency significance (count of downstream memories depending on this record)
      w1, w2, w3, w4 = configurable weights (default: 0.4, 0.2, 0.2, 0.2)
      Weights are empirically tunable; not permanently fixed.

    P_dev determines SCHEDULING PRIORITY for development jobs, NOT truth probability.


================================================================================
PART 2 — DATABASE ARCHITECTURE & SCHEMA
================================================================================

SQLite 3.45+ in WAL mode is the SINGLE SOURCE OF TRUTH for all persistent memory state.
FTS5 and vector indexes are REBUILDABLE DERIVED INDEXES — they can be dropped and
reconstructed from the canonical relational tables without data loss.

SQLite is chosen over PostgreSQL or other databases because:
  - Zero-latency local access (no network hop, no connection overhead).
  - Single-file portability matches Diva's local embedded deployment.
  - WAL mode provides non-blocking concurrent readers with serialized writers.
  - FTS5 is a first-class extension requiring no additional process.
  - sqlite-vec provides native C KNN vector search without a separate vector server.
  - Full ACID compliance with foreign key enforcement and atomic transactions.


2.17 SQLITE CONFIGURATION & PRAGMA INVARIANTS
----------------------------------------------
(Listed first because all schema operations depend on this configuration.)

Mandatory PRAGMA settings applied at every connection open:

  PRAGMA journal_mode = WAL;              -- Write-Ahead Logging for concurrent reads
  PRAGMA synchronous = NORMAL;            -- Safe under WAL; faster than FULL
  PRAGMA foreign_keys = ON;              -- Enforce all FK constraints
  PRAGMA busy_timeout = 30000;            -- 30-second busy wait before SQLITE_BUSY error
  PRAGMA cache_size = -65536;             -- 64 MB page cache (negative = KB units)
  PRAGMA page_size = 4096;               -- Optimal for modern OS page sizes
  PRAGMA temp_store = MEMORY;             -- Temp tables in memory, not disk
  PRAGMA mmap_size = 268435456;           -- 256 MB memory-mapped I/O
  PRAGMA wal_autocheckpoint = 1000;       -- Checkpoint every 1000 WAL pages
  PRAGMA strict = ON;                     -- Strict type checking (SQLite 3.37+)
  PRAGMA auto_vacuum = INCREMENTAL;       -- Incremental page reclamation

SERIALIZED WRITER CONSTRAINT: All write operations route through a single AsyncIO
write-serialization lock (asyncio.Lock). Concurrent reads from WAL are unrestricted.
No connection pool for writes — a single persistent write connection is maintained.


2.1 DATABASE DOMAIN ORGANIZATION
---------------------------------

The schema is organized into 14 logical domains. Each domain is a grouping of related
tables. All tables live in the same SQLite database file unless explicitly noted.

DOMAIN                 | PURPOSE
-----------------------|--------------------------------------------------------
01. Experience         | Immutable raw event and experience records
02. Knowledge          | Claims, assessments, versioned updates
03. Provenance         | Evidence references, derivation links
04. Entity             | Entity identity, aliases, attributes
05. Association        | Memory-to-memory and claim-to-claim typed relationships
06. Representation     | Multi-type representation records and lineage tree
07. Appraisal          | Per-domain cognitive appraisals (Emotion, Social, etc.)
08. Development        | Development requests, proposals, reviews
09. Consolidation      | Consolidation jobs, source coverage, residual claims
10. Retrieval          | Access events, vector embeddings, FTS5 shadow tables
11. Retention          | Retention records, archive logs, dependency tracking
12. Continuity         | Continuity checkpoints
13. Governance         | Access policies, audit log, schema version tracking
14. Background Jobs    | Background job queue, worker leases, transactional outbox

2.16 BITEMPORAL RECORD DESIGN (World Time vs. Diva Time)
---------------------------------------------------------

Every knowledge record maintains two independent time dimensions:

  WORLD TIME (world_time_start, world_time_end):
    When something was true or occurred in reality.
    world_time_end = NULL means "this is still valid" or "unknown end time".
    May be NULL for claims where temporal validity is unknown.

  DIVA TIME (diva_time_recorded):
    When Diva first observed, recorded, or derived this claim.
    Always a concrete timestamp; never NULL.

This enables two distinct query types:

  Query A — "What was true in the world at time T?"
    WHERE world_time_start <= T AND (world_time_end IS NULL OR world_time_end > T)
    AND lifecycle = 'ACTIVE'  (excludes HISTORICAL, RETRACTED, REFUTED)

  Query B — "What did Diva believe at her-time T_diva (even if world-state has since changed)?"
    WITH state_at_diva_time AS (
      SELECT c.*, MAX(cv.version_number) as latest_version
      FROM claims c
      JOIN claim_versions cv ON cv.claim_id = c.claim_id
      WHERE cv.changed_at <= T_diva
      GROUP BY c.claim_id
    ) -- then join to get the state at that version

CORRECTION PRINCIPLE: Old records are NEVER modified to reflect corrections.
Instead, new claim_versions records with lifecycle changes (HISTORICAL, SUPERSEDED)
are appended, and the correcting claims reference the old ones via CORRECTS relationships.

3.1 MEMORY INTAKE PROCESSING PIPELINE
---------------------------------------

The intake pipeline runs for every incoming submission. It is synchronous for the
critical validation path and spawns async background jobs for deeper processing.

STAGE 1: INTAKE VALIDATION (synchronous, ~1-5ms)
  Input: Raw submission from source engine
  Steps:
    1. Validate JSON payload schema against engine-specific Pydantic model.
    2. Reject if content_hash does not match SHA-256(raw_content).
    3. Reject if source_engine not in permitted_submitters policy list.
    4. Reject if domain_partition is COGNITIVE and requestor is AUTONOMOUS (or vice versa).
    5. Check idempotency: compute submission_hash = SHA-256(source_engine + content + session_id).
       If hash exists in input_events.content_hash, return existing event_id (idempotent).
    6. Extract metadata: source, channel, session, timestamp.

STAGE 2: EPISTEMIC TAGGING (synchronous, ~1ms)
  Steps:
    1. Preserve original epistemic_type from source engine metadata.
    2. NEVER downgrade an INTERPRETATION to OBSERVATION silently.
    3. NEVER upgrade REPORTED to OBSERVATION (reported facts remain reported).
    4. If no epistemic_type provided by source, assign UNKNOWN.
    5. Write input_event record (immutable from this point).

STAGE 3: EXPERIENCE WORTHINESS FILTER (synchronous, ~1-5ms)
  Determines whether this input becomes a persistent experience.
  Uses a scored decision table:

    Score contributors (each in [0, 1], weighted sum):
      - Novelty:        1.0 if no near-duplicate found in last 24h; else 0.0
      - Source quality: 1.0 for PERCEPTION; 0.8 for THOUGHT; 0.6 for external tools
      - Semantic weight: 0.0–1.0 based on keyword salience score (TF-IDF against existing)
      - Flagged important: 1.0 if source engine set importance_flag=True
      - Session relevance: 0.5 baseline for active session inputs

    Weights: novelty(0.3) + source(0.2) + semantic(0.2) + flagged(0.2) + session(0.1)

    If total score >= threshold (default: 0.4): persist as experience.
    If score < 0.4: store reference in input_events.processed=1; no experience record.
    Threshold is configurable; initial value should be validated empirically.

STAGE 4: ENTITY EXTRACTION & RESOLUTION (synchronous fast path / async for deep NLP)
  Steps:
    1. Run deterministic entity extraction:
       - Regex patterns for known entity types (email, URL, file path, structured IDs).
       - Keyword matching against entity_aliases index (SQL LIKE on alias_text).
    2. For each candidate entity name:
       a. Query entity_aliases for exact match → linked to existing entity.
       b. Query entities.canonical_name for exact match.
       c. If no match: create provisional entity record (status=ACTIVE, low confidence).
    3. If embedding provider available: schedule async similarity check for entity linking.
    4. Record entity IDs in experience.participants JSON array.

STAGE 5: ATOMIC CLAIM EXTRACTION (synchronous for structured inputs, async for free-text)
  For structured submissions (source provides pre-formed claims): validate and persist directly.
  For free-text submissions: schedule CLAIM_EXTRACTION background job with priority=3.
  Claims must preserve epistemic_type from their originating source.

STAGE 6: DEVELOPMENT SCHEDULING (async)
  After experience is committed to SQLite:
    1. Compute development_priority score using formula from Section 1.9.
    2. If P_dev >= 0.6: schedule PATTERN_DETECTION background job (priority=5).
    3. If novelty_score = 1.0 (highly novel): schedule ENTITY_LINKING job (priority=4).
    4. Update FTS5 index via INDEXING background job (priority=8, lowest urgency).
    5. If embedding provider available: schedule EMBEDDING_GENERATION job (priority=7).
    6. Write outbox_events record for "memory.experience_received" event (committed atomically).

STAGE 7: OUTBOX DISPATCH (async, decoupled from intake)
  OutboxWorker polls outbox_events WHERE published=0 ORDER BY created_at ASC.
  Publishes events to subscribed engines via in-process AsyncIO event bus.
  Marks outbox_events.published=1 on successful dispatch.
  On failure: increments publish_attempts; retries with exponential backoff.


3.2 PATTERN DETECTION ALGORITHMS (DETERMINISTIC — PATH A)
-----------------------------------------------------------

Pattern detection uses deterministic algorithms only. No LLM required.

ALGORITHM: Temporal Co-Occurrence Pattern Detection
  Runs on a rolling window of recent experiences.

  Input: Set of experience_ids in window W (default: last 7 days or last 100 experiences)
  Steps:
    1. Build a co-occurrence matrix C where C[e_i][e_j] = number of times entity_set(e_i)
       and entity_set(e_j) share at least one entity, within a configurable time window.
    2. For each pair (e_i, e_j) where C[e_i][e_j] >= THRESHOLD (default: 3):
       a. Query existing memory_relationships for a CO_OCCURS_WITH relationship.
       b. If none exists: create a DevelopmentRequest with operation_type=PATTERN_DETECTION
          and processing_depth=0.
       c. If exists but confidence < 0.5: schedule update job.
    3. Build entity frequency map: freq[entity_id] = count of experiences containing entity.
    4. Flag entities with freq > RECURRENCE_THRESHOLD (default: 5) as recurring.
       Create development job for ENTITY_PATTERN investigation.

  Data Structure: Sparse Co-occurrence Matrix implemented as:
    dict[tuple[UUID, UUID], int]  (sorted UUID pairs as keys to avoid double-counting)

ALGORITHM: Contradiction Detection
  Triggered after every new claim is persisted.

  Steps:
    1. Query existing claims WHERE subject_entity_id = new_claim.subject_entity_id
       AND predicate = new_claim.predicate AND lifecycle = 'ACTIVE'.
    2. For each matching claim c_existing:
       a. If c_existing.object_value != new_claim.object_value:
          - Check world time ranges: if ranges overlap, potential contradiction.
          - If overlap exists: create claim_relationship(CONTRADICTS) between both.
          - Set evidence_status = 'DISPUTED' on both via claim_versions update.
          - Write outbox event "memory.claim_disputed".
    3. Query claim_relationships WHERE claim_id_source = new_claim.claim_id
       AND relationship_type = 'CONTRADICTS' (transitive contradiction check).

ALGORITHM: Duplicate Detection
  Runs as background job triggered by DEDUPLICATION operation type.

  Steps:
    1. EXACT DUPLICATE: Compare content_hash of new experience against existing.
       If match found: mark new experience as SUPERSEDED; link to original.
    2. NEAR-DUPLICATE (textual): Use FTS5 to find experiences with high BM25 overlap.
       If BM25 score > NEAR_DUP_THRESHOLD (default: 15.0): flag for review.
    3. SEMANTIC DUPLICATE (if embeddings available): cosine similarity >= 0.95.
       Flag for review; do NOT auto-merge without governance approval.

ALGORITHM: Temporal Sequence Organization
  Runs after a set of related experiences are detected.

  Steps:
    1. Collect all experiences WHERE entity_id IN common_entity_set.
    2. Sort by world_time_start ASC NULLS LAST.
    3. For consecutive pairs (e_i, e_i+1) in sorted order:
       a. If no EXPERIENCED_BEFORE relationship exists: create one.
       b. If exists but world_time values have changed: update with new version.
    4. Compute temporal gap statistics: min/max/avg gap in seconds.
    5. Flag unusually short or long gaps for investigation (PATTERN_DETECTION job).


3.3 ENTITY RESOLUTION & DEDUPLICATION ALGORITHMS
--------------------------------------------------

ALGORITHM: Entity Resolution Pipeline
  Goal: Determine whether a candidate name refers to an existing entity.

  Step 1 — EXACT ALIAS MATCH (SQL, O(log n) with index):
    SELECT e.entity_id FROM entity_aliases a
    JOIN entities e ON a.entity_id = e.entity_id
    WHERE LOWER(a.alias_text) = LOWER(:candidate_name)
      AND a.superseded = 0 AND e.status = 'ACTIVE';
    If result: return existing entity_id. DONE.

  Step 2 — FUZZY ALIAS MATCH (FTS5 on alias_text):
    SELECT entity_id, rank FROM entity_aliases
    WHERE alias_text MATCH :candidate_name ORDER BY rank LIMIT 5;
    For each candidate: compute normalized Levenshtein distance.
    If distance <= FUZZY_THRESHOLD (default: 2 chars): flag as probable match.
    Create provisional alias with confidence = 1.0 - (distance / max_length).

  Step 3 — SEMANTIC SIMILARITY (Embedding, if available):
    Embed candidate_name. Compute cosine similarity against entity canonical_name embeddings.
    If similarity >= 0.90: propose entity merge for governance review.
    DO NOT auto-merge without explicit governance approval.

  Step 4 — NEW ENTITY CREATION (if no match found):
    Generate entity_id (UUIDv7).
    Insert into entities with canonical_name = candidate_name, status = 'ACTIVE'.
    Insert into entity_aliases with alias_type = 'FORMAL_NAME', confidence = 1.0.

  Merge Algorithm (when two entities are confirmed duplicates):
    1. Keep the entity with the lower entity_id (first observed) as the CANONICAL.
    2. Set duplicate.status = 'MERGED', duplicate.merged_into = canonical.entity_id.
    3. Update all entity_aliases.entity_id references to canonical.
    4. Update all entity_attributes.entity_id references to canonical.
    5. Update all experiences.participants JSON arrays (replace old_id with canonical).
    6. Write audit_events record for the merge.
    INVARIANT: Never delete the merged entity record. The historical reference must remain.


3.4 RETRIEVAL ALGORITHM STACK (SQL + FTS5 + GRAPH + VECTOR)
------------------------------------------------------------

Retrieval uses a multi-layer cascade. Each layer contributes candidates;
a final ranking step merges and scores the unified candidate set.

LAYER 1 — STRUCTURED SQL RETRIEVAL (always available)
  Used for: Factual, Temporal, Entity-specific, Bitemporal queries.
  Algorithm:
    SELECT experience_id, permanent_importance, diva_time_recorded,
           last_accessed_at, access_count
    FROM experiences
    WHERE domain_partition = :requester_partition
      AND validity_status = 'CURRENT'
      AND (:entity_filter IS NULL OR participants LIKE '%' || :entity_filter || '%')
      AND (:time_start IS NULL OR world_time_start >= :time_start)
      AND (:time_end IS NULL OR world_time_end <= :time_end OR world_time_end IS NULL)
    ORDER BY permanent_importance DESC, diva_time_recorded DESC
    LIMIT :candidate_limit;   -- Default: 50 candidates before ranking

LAYER 2 — FTS5 FULL-TEXT RETRIEVAL (always available)
  Used for: Keyword matching, name lookups, exact phrase retrieval.
  Algorithm:
    SELECT memory_id, rank FROM memories_fts
    WHERE memories_fts MATCH :query_tokens
    ORDER BY rank LIMIT 50;
  FTS5 returns BM25 scores (negative; lower = better match).
  Normalize to [0, 1]: score = 1 / (1 + abs(bm25_rank)).
  Configuration: porter unicode61 tokenizer with prefix queries enabled.

LAYER 3 — GRAPH SPREADING ACTIVATION (available; depends on NetworkX projection)
  Used for: Associative retrieval, related-concept queries.
  Algorithm:
    1. Load adjacency data from memory_relationships into NetworkX DiGraph G.
       G is a cached in-memory projection, refreshed every N minutes or on change.
    2. For each seed_id (from query context or seed memories):
       Run spreading activation:
         activation[seed_id] = 1.0
         For each neighbor n of seed_id:
           activation[n] = max(activation[n], activation[seed_id] * edge_weight[seed_id→n] * decay)
         decay = 0.5 (configurable)
         MAX_HOPS = 3 (configurable, hard limit)
    3. Collect all nodes with activation >= SPREAD_THRESHOLD (default: 0.1).
    4. Return as candidate set with spreading activation score.
  Data Structure: NetworkX DiGraph (in-memory, NOT source of truth).
    Node attributes: {memory_id, permanent_importance, development_status}
    Edge attributes: {relationship_type, confidence, weight}
    Weight for spreading: edge.confidence × relationship_type_weight_table[relationship_type]
      relationship_type_weight_table:
        CAUSED_BY: 0.9; PART_OF: 0.8; SIMILAR_TO: 0.6; ASSOCIATED_WITH: 0.4;
        CO_OCCURS_WITH: 0.2; CONTRADICTS: -0.3 (negative activation)

LAYER 4 — VECTOR KNN RETRIEVAL (optional; requires sqlite-vec and embedding provider)
  Used for: Semantic similarity queries, natural language question retrieval.
  Algorithm:
    1. Embed query text using embedding provider (EmbeddingProvider.embed([query])).
    2. Execute KNN query against memory_embeddings vec0 table:
       SELECT memory_id, distance FROM memory_embeddings
       WHERE embedding MATCH :query_embedding AND k = 50;
    3. Convert cosine distance to similarity: similarity = 1.0 - distance.
    4. If embedding provider unavailable: skip this layer entirely; retrieve empty set.

HyDE PROJECTION (Hypothetical Document Embeddings):
  When FTS5 returns weak results and embedding provider is available:
  1. Generate a hypothetical answer document H for query Q (via LLM or template).
  2. Embed H to get h_emb.
  3. Use h_emb as the VECTOR query instead of q_emb.
  CRITICAL INVARIANT: H is used ONLY as a query projection vector.
    H is NEVER stored in the database.
    H is NEVER returned to the requesting engine as evidence.
    H is NEVER treated as a memory record.
    H exists only ephemerally during the retrieval process.


3.5 CANDIDATE RANKING ALGORITHM
---------------------------------

After collecting candidates from Layers 1-4, a unified scoring function ranks them.

UNIFIED RETRIEVAL SCORE:
  S_unified(M) = w_sql  × s_sql(M)
               + w_fts  × s_fts(M)
               + w_graph × s_graph(M)
               + w_vec  × s_vec(M)
               + w_act  × s_activation(M)
               + w_imp  × I_total(M, t)
               + w_perm × s_permission(M)

  Default weights: w_sql=0.15, w_fts=0.25, w_graph=0.15, w_vec=0.25, w_act=0.15, w_imp=0.05
  Weights sum to 1.0. Configurable per retrieval_intent type.
  s_permission(M) = 0.0 if access denied; this is a HARD ZERO that eliminates candidates.

  After scoring:
    1. Filter out candidates with s_permission = 0.0.
    2. Filter out candidates where validity_status ∈ (RETRACTED, REFUTED)
       UNLESS retrieval_intent = CONTRADICTION (which explicitly needs refuted records).
    3. Sort by S_unified DESC.
    4. Apply token_budget_limit: greedy inclusion from top-ranked until budget exhausted.

TOKEN BUDGET ASSEMBLY (Greedy Knapsack):
  Input: Ranked candidates [M1, M2, ..., Mn], token_budget (provided by requesting engine)
  Algorithm:
    result = []
    remaining_budget = token_budget
    for M in ranked_candidates:
      token_cost = estimate_tokens(M.content)  # heuristic: 1 token ≈ 4 chars
      if token_cost <= remaining_budget:
        result.append(M)
        remaining_budget -= token_cost
      if remaining_budget < MIN_REMAINING (default: 100): break
    return result


3.6 RETRIEVAL INTENT ROUTING
-------------------------------

The retrieval intent determines which layers are activated and how weights are adjusted.

INTENT         | SQL | FTS5 | GRAPH | VECTOR | Notes
---------------|-----|------|-------|--------|--------------------------------
FACTUAL        |  ✓  |  ✓   |   ✗   |   ✓    | entity+predicate SQL query
EPISODIC       |  ✓  |  ✓   |   ✓   |   ✓    | temporal filter + spreading
TEMPORAL       |  ✓  |  ✗   |   ✗   |   ✗    | bitemporal query only
ASSOCIATIVE    |  ✗  |  ✓   |   ✓   |   ✓    | spreading activation primary
AUTOBIOGRAPHICAL| ✓  |  ✓   |   ✓   |   ✓    | filter on AUTOBIOGRAPHICAL type
REFLECTIVE     |  ✓  |  ✓   |   ✓   |   ✓    | filter on REFLECTIVE type
RELATIONSHIP   |  ✓  |  ✓   |   ✓   |   ✗    | entity_id pair filter
CONTRADICTION  |  ✓  |  ✗   |   ✗   |   ✗    | claim_relationships CONTRADICTS


3.7 CONSOLIDATION VERIFICATION ALGORITHM (SEVEN-GATE PROTOCOL)
----------------------------------------------------------------

Consolidation requires passing ALL SEVEN GATES before the result is committed.
Each gate is an independent verifier. Failure at any gate rejects the consolidation.

GATE 1: ENTITY PRESERVATION
  Rule: Every entity_id referenced in source memory records must appear in the
        consolidated representation's entity references or be explicitly excluded.
  Algorithm:
    source_entities = UNION of participants JSON arrays from all source experiences
    result_entities = entity IDs referenced in consolidated representation
    missing = source_entities - result_entities
    If |missing| > 0: FAIL with list of missing entity_ids.

GATE 2: CONTRADICTION PRESERVATION
  Rule: If source memories contain CONTRADICTS claim_relationships, the consolidated
        representation must either preserve the conflict or explicitly note unresolved status.
  Algorithm:
    contradictions = SELECT * FROM claim_relationships
      WHERE claim_id_source IN :source_claim_ids
        AND relationship_type = 'CONTRADICTS'
    For each contradiction: check that consolidated result preserves it in content JSON.
    If any contradiction is silently absent: FAIL.

GATE 3: CLAIM COVERAGE
  Rule: Every claim from source memories must be either:
        a) Covered by the consolidated representation, OR
        b) Recorded as a residual_claim (too specific to generalize safely).
  Algorithm:
    source_claims = SELECT claim_id FROM claims
      WHERE source_experience_id IN :source_memory_ids
        AND lifecycle = 'ACTIVE'
    For each claim: check if claim_id appears in coverage.covered_claim_ids
                    OR in residual_claims for this job.
    Coverage_pct = |covered + residual| / |source_claims|
    If coverage_pct < 1.0: FAIL with uncovered claim_ids.

GATE 4: SOURCE TRACEABILITY
  Rule: Every piece of information in the consolidated representation must have a
        traceable derivation_link back to a source memory or claim.
  Algorithm:
    For each fact in consolidated content (JSON keys): check corresponding derivation_links.
    If any fact lacks a derivation_link: FAIL.

GATE 5: RESIDUAL INFORMATION PRESERVATION
  Rule: Claims that could not be safely generalized must be preserved as residual_claims.
        No claim may be silently discarded.
  Algorithm:
    discarded = source_claims - covered_claims - residual_claims
    If |discarded| > 0: FAIL with list of discarded claim_ids.

GATE 6: TEMPORAL AND CONTEXTUAL PRESERVATION
  Rule: The consolidated representation must specify the temporal scope and context
        conditions under which it applies. Claims that apply to specific time windows
        must not be presented as timeless generalizations.
  Algorithm:
    If consolidated content.temporal_scope is NULL or empty string: FAIL.
    If any source claim has non-NULL world_time_start:
      Verify consolidated content includes temporal_scope JSON field.

GATE 7: EPISTEMIC PRESERVATION
  Rule: The epistemic type of claims must NOT be upgraded through summarization.
        INTERPRETATION cannot become OBSERVATION.
        REPORTED cannot become OBSERVATION.
        INFERENCE cannot become OBSERVATION.
        OPINION cannot become any factual type.
  Algorithm:
    For each claim in consolidated content:
      original_epistemic = lookup original claim epistemic_type
      consolidated_epistemic = claim.epistemic_type in content
      If EPISTEMIC_RANK[consolidated_epistemic] > EPISTEMIC_RANK[original_epistemic]: FAIL.
    EPISTEMIC_RANK: OBSERVATION=5, REPORTED=3, INFERENCE=4, INTERPRETATION=2, OPINION=1, UNKNOWN=0

ALL 7 GATES PASSED → Write consolidated representation to memory_representations.
                    → Update consolidation_jobs.all_gates_passed = 1.
                    → Update retention_records for source memories to CONSOLIDATED.
                    → Emit "memory.consolidation_verified" outbox event.
ANY GATE FAILS    → Reject consolidation job. Record failure_reason.
                    → Emit "memory.consolidation_rejected" outbox event.
                    → Schedule RESIDUAL_ANALYSIS development job for unaccounted claims.


3.8 INCREMENTAL CONSOLIDATION PROCESSING LOOP
----------------------------------------------

Full-corpus consolidation is NEVER attempted in a single pass.
Memory uses incremental consolidation to avoid catastrophic history rewriting.

LOOP:
  Trigger: Event "memory.pattern_detected" OR scheduled background job (every 6h).

  Step 1 — ELIGIBLE EXPERIENCE IDENTIFICATION:
    SELECT e.experience_id FROM experiences e
    JOIN retention_records r ON r.memory_id = e.experience_id
    WHERE r.retention_status = 'ACTIVE'
      AND r.consolidation_eligible = 1
      AND e.development_status = 'ASSOCIATED'
      AND e.permanent_importance >= 0.3
    ORDER BY r.development_priority DESC
    LIMIT 20;  -- Process in small batches

  Step 2 — RELATED REPRESENTATION LOOKUP:
    For each eligible experience: find existing memory_representations that reference it.
    Check if an existing CONSOLIDATED representation already covers this group.

  Step 3 — INCREMENTAL PROPOSAL GENERATION:
    Generate a consolidation proposal covering only the NEWLY ELIGIBLE experiences
    plus the most relevant existing consolidated representation (not the entire corpus).

  Step 4 — SEVEN-GATE VERIFICATION (Section 3.7)

  Step 5 — REPRESENTATION VERSION UPDATE:
    If gates pass: create new memory_representations record with version = old + 1.
    Set old representation.superseded_at = now().
    new_repr.parent_representation_id = old_repr.representation_id.

  Step 6 — SOURCE MEMORY RETENTION UPDATE:
    If all source memories are fully covered and have no active dependencies:
      Set retention_records.retention_status = 'CONSOLIDATED'.
      Set retention_records.archival_eligible = 1.
      Trigger DEPENDENCY CHECK before archival.


3.9 MEMORY DEVELOPMENT LIFECYCLE STATE MACHINE
-----------------------------------------------

The DevelopmentStatus of a memory record follows a strict finite state machine.

States:
  RAW → ORGANIZED → ASSOCIATED → {PROPOSED, ACCEPTED}
  PROPOSED → UNDER_REVIEW → {ACCEPTED, DISPUTED}
  DISPUTED → {ACCEPTED, SUPERSEDED}
  ACCEPTED → SUPERSEDED  (when a newer version is created)
  Any state → ARCHIVED  (only via Retention Engine with governance approval)

Transition Rules:
  RAW → ORGANIZED:          Memory Intake or background INDEXING job completes.
  ORGANIZED → ASSOCIATED:   Entity links and temporal sequence established.
  ASSOCIATED → PROPOSED:    Memory Development generates a generalization candidate.
  ASSOCIATED → ACCEPTED:    Simple organizational structure needs no proposal (risk-based).
  PROPOSED → UNDER_REVIEW:  When a specialized engine review is requested.
  UNDER_REVIEW → ACCEPTED:  Governance review approves the proposal.
  UNDER_REVIEW → DISPUTED:  Contradicting evidence found during review.
  DISPUTED → ACCEPTED:      Contradiction resolved; proposal validated.
  ACCEPTED → SUPERSEDED:    A new version replaces this record.

FSM is implemented as a lookup table:
  VALID_TRANSITIONS = {
    'RAW': ['ORGANIZED'],
    'ORGANIZED': ['ASSOCIATED', 'ARCHIVED'],
    'ASSOCIATED': ['PROPOSED', 'ACCEPTED', 'ARCHIVED'],
    'PROPOSED': ['UNDER_REVIEW', 'ACCEPTED', 'ARCHIVED'],
    'UNDER_REVIEW': ['ACCEPTED', 'DISPUTED'],
    'DISPUTED': ['ACCEPTED', 'SUPERSEDED', 'ARCHIVED'],
    'ACCEPTED': ['SUPERSEDED', 'ARCHIVED'],
    'SUPERSEDED': ['ARCHIVED'],
  }
  Any transition not in VALID_TRANSITIONS raises InvalidStateTransitionError.


3.10 BOUNDED DEVELOPMENT WORKFLOW (ANTI-INFINITE-RECURSION)
------------------------------------------------------------

PROBLEM: Without bounds, Memory detecting a pattern could trigger Thought to investigate,
which produces an interpretation, which triggers Memory to detect another pattern, and so on.

SOLUTION: Every development operation carries anti-recursion metadata.

STRUCTURAL BOUNDS on DevelopmentRequest:
  parent_operation_id:    UUID | None  — Chain of operations
  processing_depth:       int           — Current depth (starts at 0)
  max_processing_depth:   int           — Hard cap (default: 5; never exceeds 10)
  idempotency_key:        str           — Prevents re-processing identical inputs
  resource_budget:        ResourceBudget— CPU ms, token count, wall-clock seconds

DEPTH ENFORCEMENT:
  def schedule_development_job(request: DevelopmentRequest) -> None:
      if request.processing_depth >= request.max_processing_depth:
          log_warning("Max processing depth reached; scheduling deferred for next cycle")
          create_low_priority_job(request, scheduled_at=now() + timedelta(hours=24))
          return
      create_background_job(request)

IDEMPOTENCY ENFORCEMENT:
  idempotency_key = SHA-256(operation_type + sorted(target_memory_ids) + development_objective)
  Before creating any DevelopmentRequest: check background_jobs.idempotency_key.
  If exists AND status ∈ (PENDING, RUNNING, COMPLETED): return existing job_id.

RESOURCE BUDGET STRUCTURE (ResourceBudget):
  max_cpu_ms:          int   — Maximum CPU time in milliseconds (default: 5000)
  max_tokens:          int   — Maximum LLM tokens if LLM used (default: 4096)
  max_wall_clock_secs: int   — Maximum wall-clock seconds (default: 30)
  max_db_reads:        int   — Maximum SQL read queries (default: 1000)

CIRCUIT BREAKER: If the same (source_entity_set, operation_type) combination has triggered
more than N (default: 5) development jobs in the past 24h, suppress further jobs for
that combination for 24h (write to a cooldown table).


3.11 BACKGROUND JOB PROCESSING & IDEMPOTENCY PROTOCOL
-------------------------------------------------------

All background processing follows the At-Least-Once Delivery with Idempotent Consumers pattern.

JOB LIFECYCLE:
  PENDING → (worker acquires lease) → RUNNING → COMPLETED | FAILED
  FAILED: If attempt_count < max_attempts: status → PENDING (retry with backoff)
           If attempt_count >= max_attempts: status → DEAD_LETTER (requires manual review)

LEASE PROTOCOL:
  Worker acquire:
    BEGIN IMMEDIATE;
    SELECT job_id FROM background_jobs
      WHERE status = 'PENDING'
        AND (scheduled_at IS NULL OR scheduled_at <= CURRENT_TIMESTAMP)
      ORDER BY priority ASC, created_at ASC LIMIT 1 FOR UPDATE;
    INSERT INTO background_leases VALUES (lease_id, job_id, worker_id, now, now+30s, now);
    UPDATE background_jobs SET status = 'RUNNING', started_at = now WHERE job_id = ?;
    COMMIT;

  Worker heartbeat: UPDATE background_leases SET heartbeat_at = now, expires_at = now+30s
                    WHERE lease_id = ? AND worker_id = ?;  (every 10 seconds)

  Lease expiry recovery: Scheduled monitor checks for leases WHERE expires_at < now.
    If expired: set job status = PENDING, delete expired lease, increment attempt_count.

IDEMPOTENCY: Every job handler must be idempotent.
  At start: check if already-processed results exist for this job's idempotency_key.
  If yes: skip processing; mark COMPLETED immediately; write idempotency audit record.


3.12 OUTBOX TRANSACTIONAL EVENT DISPATCH
-----------------------------------------

The transactional outbox pattern ensures that committed database operations and their
corresponding events are NEVER decoupled. No "fire-and-forget" event emission is permitted.

Write Path (always within the same transaction as the data operation):
  BEGIN;
  -- Insert the memory record (experience, claim, etc.)
  INSERT INTO experiences (...) VALUES (...);
  -- Insert the outbox event in the SAME transaction
  INSERT INTO outbox_events (outbox_id, event_name, event_payload, source_engine, created_at, published)
    VALUES (uuid7(), 'memory.experience_persisted', json_payload, 'MEMORY_INTAKE', now(), 0);
  COMMIT;
  -- If COMMIT fails: neither the experience nor the event is written.
  -- If COMMIT succeeds: both are durably written.

OutboxWorker (async background coroutine):
  While running:
    SELECT outbox_id, event_name, event_payload FROM outbox_events
      WHERE published = 0 ORDER BY created_at ASC LIMIT 20;
    For each event:
      Publish to in-process AsyncIO event bus (broadcast to subscribed handlers).
      BEGIN;
      UPDATE outbox_events SET published = 1, published_at = now() WHERE outbox_id = ?;
      COMMIT;
      If publish or update fails: increment publish_attempts; sleep exponential backoff.
    Sleep 100ms;

COMPLETE EVENT CATALOG:

  Intake Events:
    memory.experience_received        — After passing intake validation
    memory.experience_persisted       — After SQLite commit of experience record
    memory.experience_filtered        — When intake decides NOT to create experience

  Claim Events:
    memory.claim_created              — New claim persisted
    memory.claim_disputed             — Contradiction detected; evidence_status = DISPUTED
    memory.claim_corrected            — New version supersedes previous claim

  Pattern Events:
    memory.pattern_detected           — Pattern frequency threshold exceeded
    memory.development_proposed       — DevelopmentResult submitted
    memory.development_accepted       — Memory Governance accepts a proposal
    memory.development_rejected       — Memory Governance rejects a proposal

  Consolidation Events:
    memory.consolidation_started      — Consolidation job created
    memory.consolidation_verified     — All 7 gates passed
    memory.consolidation_rejected     — Any gate failed

  Retention Events:
    memory.archive_eligible           — Retention record flagged archival_eligible=1
    memory.memory_archived            — Cold archive write confirmed

  Continuity Events:
    memory.checkpoint_created         — Continuity checkpoint written
    memory.checkpoint_restored        — Restoration completed
    memory.restoration_failed         — Restoration could not be completed

PART 4 — INDEXING STRATEGY & SEARCH ARCHITECTURE
================================================================================

4.1 PRIMARY RELATIONAL INDEXES (B-TREE)
-----------------------------------------

SQLite B-tree indexes are created on every column combination used in WHERE clauses,
JOIN conditions, and ORDER BY expressions appearing in hot query paths.

Covering indexes (include all queried columns) are used where query pattern warrants:

  CREATE INDEX idx_exp_active_partition ON experiences
    (domain_partition, validity_status, development_status, permanent_importance DESC)
    WHERE validity_status = 'CURRENT' AND retention_status = 'ACTIVE';

  CREATE INDEX idx_claims_entity_pred ON claims
    (subject_entity_id, predicate, lifecycle, evidence_status)
    WHERE lifecycle = 'ACTIVE';

  CREATE INDEX idx_claims_world_time ON claims
    (world_time_start, world_time_end)
    WHERE world_time_start IS NOT NULL;

  CREATE INDEX idx_outbox_pending ON outbox_events (created_at)
    WHERE published = 0;

  CREATE INDEX idx_jobs_runnable ON background_jobs
    (priority ASC, created_at ASC)
    WHERE status = 'PENDING';

Partial indexes (WHERE clause on index) are used extensively to keep index size small
and maintain near-constant lookup time as tables grow.

4.2 FTS5 FULL-TEXT INDEX CONFIGURATION
-----------------------------------------

FTS5 is configured with:
  tokenize = 'porter unicode61 remove_diacritics 2'
    - porter: English stemming (run/runs/running → run)
    - unicode61: full Unicode case folding
    - remove_diacritics 2: strip accents for accent-insensitive matching

FTS5 table covers:
  experience_summary       — Searchable event description
  canonical_statements     — Space-joined claim statements for this memory
  entity_names             — Space-joined entity canonical names and aliases

QUERY PATTERNS:

  Phrase query:         memories_fts MATCH '"machine learning"'
  Prefix query:         memories_fts MATCH 'algorith*'
  Proximity query:      memories_fts MATCH 'NEAR("neural" "network", 5)'
  Boolean:              memories_fts MATCH 'python AND debugging'
  Column-scoped:        memories_fts MATCH 'entity_names : Alex'

FTS5 Content Synchronization:
  FTS5 is maintained as an external content table (content='experiences').
  Synchronization is NOT automatic — a background INDEXING job runs:
    INSERT INTO memories_fts (rowid, memory_id, experience_summary, ...)
    SELECT rowid, experience_id, experience_summary, ... FROM experiences
    WHERE experience_id NOT IN (SELECT memory_id FROM memories_fts_content)
      AND development_status >= 'ORGANIZED';

  On experience update (status changes only — content is immutable):
    DELETE FROM memories_fts WHERE memory_id = :experience_id;
    INSERT INTO memories_fts ... (re-index with updated metadata)

  FTS5 index is fully REBUILDABLE from experiences + claims tables.
  Rebuild command: INSERT INTO memories_fts(memories_fts) VALUES ('rebuild');

4.3 VECTOR INDEX CONFIGURATION (sqlite-vec)
--------------------------------------------

sqlite-vec provides C-extension KNN search within SQLite.
The vec0 virtual table stores float32 embeddings with cosine distance by default.

  CREATE VIRTUAL TABLE memory_embeddings USING vec0(
    memory_id    TEXT PRIMARY KEY,
    embedding    float[384]        -- Dimension matches embedding model output
  );

Embedding model: BAAI/bge-small-en-v1.5 (384 dimensions, ONNX via FastEmbed)
  - Inference time: < 10ms on CPU for single text
  - Memory footprint: ~65 MB ONNX model loaded
  - MTEB retrieval score: competitive for local embedded use

Fallback when sqlite-vec unavailable:
  Store raw float32 bytes in memory_embeddings_fallback.embedding BLOB.
  KNN computed in-process using numpy:
    distances = 1 - (query_vec @ stored_vecs.T) / (||query|| × ||stored||)
  Performance degrades linearly with corpus size; acceptable up to ~50K records.

HNSW parameters (when using sqlite-vec 0.1.6+ with HNSW support):
  M = 16          (number of connections per node at non-zero layers)
  ef_construction = 200  (candidates during index build)
  ef_search = 50  (candidates during search; tunable at query time)

Embedding Generation Job:
  Trigger: 'memory.experience_persisted' event consumed by EmbeddingWorker.
  For each new experience:
    text = experience.experience_summary + " " + joined_canonical_statements
    embedding = await embedding_provider.embed([text])
    INSERT OR REPLACE INTO memory_embeddings (memory_id, embedding) VALUES (?, ?);
  On provider unavailability: job returns to PENDING with 60s delay.

4.4 GRAPH INDEX (ADJACENCY LIST + NetworkX PROJECTION)
-------------------------------------------------------

Persistent graph state lives in memory_relationships and claim_relationships tables
as relational adjacency lists. This is the SOURCE OF TRUTH.

NetworkX is a cached IN-MEMORY projection used for:
  - Spreading activation algorithm (3.6)
  - Community detection (Louvain algorithm for concept clustering)
  - PageRank for entity importance ranking
  - Shortest path between memory records (Dijkstra)
  - Cycle detection in contradiction graphs

NetworkX graph is rebuilt from SQLite on:
  - Application startup
  - Every GRAPH_REFRESH_INTERVAL (default: 300 seconds)
  - After any batch of > 50 new memory_relationships records are written

Graph Construction Query:
  SELECT source_memory_id, target_memory_id, relationship_type, confidence
  FROM memory_relationships WHERE superseded = 0 AND domain_partition = :partition;

Edge weight in NetworkX:
  weight = confidence × RELATIONSHIP_WEIGHT_TABLE[relationship_type]
  RELATIONSHIP_WEIGHT_TABLE:
    EXPERIENCED_BEFORE: 0.3, EXPERIENCED_AFTER: 0.3
    CAUSED_BY: 0.9,     CAUSED: 0.9
    PART_OF: 0.8,       SIMILAR_TO: 0.6
    ASSOCIATED_WITH: 0.4, CO_OCCURS_WITH: 0.2
    CONTRADICTS: -0.3   (negative — suppresses activation flow)
    DEVELOPED_FROM: 0.7, INSTANCE_OF: 0.5

Memory constraint: NetworkX graph is capped at MAX_GRAPH_NODES = 100,000.
If corpus exceeds this: graph is built from TOP-N most important nodes only
(ordered by permanent_importance DESC).

PART 5 — ENGINE SUBSYSTEM SPECIFICATIONS
================================================================================

5.1 SUBSYSTEM 1: MEMORY INTAKE
--------------------------------

Service Name: MemoryIntakeService
Runs as: Async coroutine handler; invoked per submission request.
Data ownership: input_events table (sole writer).

Responsibilities:
  - Accept submissions from authorized source engines via submit_experience() and
    submit_knowledge_contribution() interface methods.
  - Execute the 7-stage intake pipeline (Section 3.1) synchronously up to Stage 3.
  - Persist input_event record (always, regardless of experience worthiness decision).
  - Conditionally persist experience record (Stage 3 filter decision).
  - Schedule background jobs for entity extraction, claim extraction, indexing, embedding.
  - Emit transactional outbox events within the same SQLite transaction as the write.

Internal components:
  - IntakeValidator:       Schema validation, hash verification, permission checks.
  - EpistemicPreserver:    Ensures epistemic_type is never silently downgraded.
  - WorthinessScorer:      Scores input against worthiness criteria (Section 3.1 Stage 3).
  - EntityExtractor:       Deterministic entity candidate extraction (regex + alias lookup).
  - IntakeJobScheduler:    Creates background_jobs records for async processing.

Key invariants enforced:
  MEM-001: Original experiences never silently overwritten (input_events is append-only).
  MEM-002: Every persisted claim has provenance (source_engine + session always required).
  MEM-003: Inferences never silently become observations (epistemic_type preserved).


5.2 SUBSYSTEM 2: EXPERIENCE STORE
-----------------------------------

Service Name: ExperienceStoreService
Data ownership: experiences, experience_payloads tables (sole writer).

Responsibilities:
  - Provide the canonical, immutable record of what happened.
  - Store full event payloads with integrity hashes.
  - Support temporal ordering queries and bitemporal projections.
  - Track development_status, validity_status, and retention_status transitions.

Status update protocol:
  Statuses are NEVER updated by direct SQL UPDATE on the experiences table.
  Instead: status changes are written as audit_events records.
  A SQL view (experiences_current_view) derives the current status from the
  latest audit_event per experience_id.

  Alternative (simpler for initial implementation): Direct UPDATE with mandatory
  audit_event written in the same transaction. Upgrade to audit-only later.

5.3 SUBSYSTEM 3: KNOWLEDGE STORE
----------------------------------

Service Name: KnowledgeStoreService
Data ownership: claims, claim_assessments, claim_versions, evidence_references tables.

Responsibilities:
  - Maintain the distinction between claims and beliefs (see Section 1.2).
  - Accept atomic claim submissions with explicit epistemic typing.
  - Accept ClaimAssessment contributions from specialized engines.
  - Maintain ClaimVersion history for all status changes.
  - Detect and record contradictions between claims on insertion.
  - Provide claim retrieval by entity, predicate, evidence status, and world time.

Claim creation rules:
  1. Compute provenance_hash = SHA-256(canonical_statement + source_engine + diva_time_recorded).
  2. If provenance_hash already exists in claims table: return existing claim_id (idempotent).
  3. Write claim with lifecycle = ACTIVE, evidence_status = UNVERIFIED.
  4. Run contradiction check (Section 3.2) within same transaction.
  5. Write outbox event "memory.claim_created".

Assessment submission rules:
  1. Only the engine that OWNS the domain may submit assessments for that domain.
     e.g. Only "EMOTION" engine may submit appraisal_type = "EMOTIONAL" assessments.
  2. Previous assessments from the same engine for the same claim are marked superseded=1.
  3. New assessment record created with version = previous.version + 1.
  4. evidence_status of the claim is RECALCULATED from all active evidence_references:
     - If any OPPOSES: DISPUTED
     - If 2+ SUPPORTS: CORROBORATED
     - If 1 SUPPORTS: SUPPORTED
     - Else: UNVERIFIED

5.4 SUBSYSTEM 4: ENTITY & ASSOCIATION
---------------------------------------

Service Name: EntityAssociationService
Data ownership: entities, entity_aliases, entity_attributes, memory_relationships,
                claim_relationships tables.

Responsibilities:
  - Maintain canonical entity registry with alias resolution.
  - Provide entity resolution pipeline (Section 3.3).
  - Manage typed graph relationships between memory records.
  - Enforce: CO_OCCURS_WITH does NOT imply causation.
  - Maintain relationship confidence scores and version history.

Association creation rules:
  1. Both source and target memory IDs must exist in experiences or memory_representations.
  2. relationship_type must be in the defined ClaimRelationshipType enum.
  3. CAUSAL relationship types (CAUSED_BY, CAUSED) may only be established by
     development proposals reviewed by Thought Engine — not auto-created by Memory.
  4. Write audit_event for every new or superseded relationship.

NetworkX projection refresh: EntityAssociationService triggers graph refresh
after every batch of > 10 new memory_relationships records within a 60-second window.

5.5 SUBSYSTEM 5: MEMORY DEVELOPMENT
--------------------------------------

Service Name: MemoryDevelopmentService
Data ownership: development_requests, development_proposals, development_reviews tables.

Responsibilities:
  - Execute Path A (independent deterministic) development operations.
  - Coordinate Path B (collaborative) development by routing requests to specialized engines.
  - Manage development lifecycle state machine (Section 3.9).
  - Enforce bounded development (Section 3.10): depth limits, idempotency, budget tracking.
  - Evaluate incoming DevelopmentResult submissions from specialized engines.
  - Route evaluation decisions to Memory Governance for final authority.

Path A operations executed internally (no cross-engine request):
  DEDUPLICATION, ENTITY_LINKING, PATTERN_DETECTION, CONTRADICTION_CHECK,
  TEMPORAL_SEQUENCE, DEPENDENCY_ANALYSIS.

Path B operations requiring specialized engines:
  CAUSAL_INVESTIGATION → Thought Engine
  EMOTIONAL_REAPPRAISAL → Emotion Engine
  SOCIAL_INTERPRETATION → Social Cognition Engine
  PROCEDURAL_EXTRACTION → Learning Engine
  MOTIVATIONAL_RELEVANCE → Motivation Engine

Routing mechanism: Emit "memory.development_requested" event with
  {request_id, operation_type, target_engine, development_objective}.
  Target engine subscribes to this event and responds via submit_development_result().
  No direct synchronous method call between engines — event-driven only.

Risk-based acceptance (Decision 2):
  Simple organizational structures (TEMPORAL_SEQUENCE, ENTITY_LINKING, DEDUPLICATION)
  with fully deterministic validation → ACCEPT internally after Gate checks.
  Generalization, causal, emotional, or social proposals → always require specialized review.


5.6 SUBSYSTEM 6: RETRIEVAL ENGINE
-----------------------------------

Service Name: RetrievalEngineService
Data ownership: retrieval_events table (sole writer for retrieval logs).

Responsibilities:
  - Accept RetrievalRequest from authorized engines via retrieve_memories() interface.
  - Route to appropriate layer stack based on retrieval_intent (Section 3.6).
  - Execute multi-layer candidate retrieval (Section 3.4).
  - Apply unified ranking algorithm (Section 3.5).
  - Apply access control filter (zero score for unauthorized records).
  - Assemble token-budget-constrained context package.
  - Identify retrieval gaps, contradictions, and patterns exposed during retrieval.
  - If gaps detected: schedule development job (Decision 3 — GENERATE PROPOSALS).
  - Log retrieval event; update access_count on retrieved experiences.

Retrieval gap detection:
  After ranking: if top result S_unified < CONFIDENCE_THRESHOLD (default: 0.4):
    Create DevelopmentRequest with operation_type = PATTERN_DETECTION
    and development_objective = "Low-confidence retrieval for query: {query_hash}"
    with priority = 8 (background, non-urgent).
  Retrieval NEVER directly modifies or consolidates knowledge records.


5.7 SUBSYSTEM 7: CONSOLIDATION ENGINE
---------------------------------------

Service Name: ConsolidationEngineService
Data ownership: consolidation_jobs, consolidation_coverage, residual_claims tables.

Responsibilities:
  - Execute incremental consolidation processing loop (Section 3.8).
  - Run seven-gate verification protocol (Section 3.7) for every consolidation candidate.
  - Coordinate with Memory Development for generalization proposals.
  - Coordinate with specialized engines for collaborative consolidation input.
  - Create new memory_representations records upon successful consolidation.
  - Record residual_claims for every claim that could not be generalized.
  - Never delete or archive source memories without full gate verification.

Consolidation triggers:
  - Pattern detection threshold exceeded (N related experiences detected).
  - Scheduled background sweep (default: every 6 hours).
  - Explicit request from Learning Engine or Cognitive Integration.
  - Retrieval gap analysis identifies knowledge fragmentation.

Gate failure handling:
  If any gate fails:
    - Record failure_reason with specific gate number and failing claim/entity IDs.
    - Schedule RESIDUAL_ANALYSIS development job.
    - Emit "memory.consolidation_rejected" event.
    - Do NOT retry within 24 hours (cooldown prevents repeated failed attempts).


5.8 SUBSYSTEM 8: RETENTION ENGINE
-----------------------------------

Service Name: RetentionEngineService
Data ownership: retention_records, archive_records, memory_dependencies tables.

Responsibilities:
  - Evaluate memory importance and retention eligibility.
  - Manage dependency tracking to prevent premature archival.
  - Determine archival eligibility only when ALL conditions are satisfied.
  - Coordinate cold archive write with governance approval.
  - Ensure archival is ALWAYS reversible (archive records stored permanently).

Retention invariants:
  MEM-010: Archival must be reversible and dependency-aware.
  NEVER archive a memory that has active dependency records.
  NEVER archive a memory that is referenced as source_evidence by an ACTIVE claim.
  NEVER archive a memory whose permanent_importance >= 0.8.
  NEVER archive autonomously — always write governance audit_event first.

Archival eligibility criteria (ALL must be true):
  1. retention_status = 'CONSOLIDATED' (fully covered by a consolidated representation).
  2. dependency_count = 0 (no other record depends on this one).
  3. permanent_importance < ARCHIVE_IMPORTANCE_CEILING (default: 0.8).
  4. Last accessed more than ARCHIVE_MIN_AGE_DAYS (default: 90) ago.
  5. No active development_requests reference this memory.
  6. No active consolidation_jobs reference this memory.

Importance is NOT subject to calendar decay.
Memory is not archived simply because it is old.


5.9 SUBSYSTEM 9: MEMORY CONTINUITY
-------------------------------------

Service Name: MemoryContinuityService
Data ownership: continuity_checkpoints table.

Responsibilities:
  - Persist authorized snapshots of state OWNED by other engines.
  - Create checkpoints on explicit request or on session lifecycle events.
  - Restore checkpoints by notifying owning engines with snapshot references.
  - Validate schema versions before restoration.
  - Maintain separate checkpoint partitions for COGNITIVE and AUTONOMOUS domains.

Memory Continuity does NOT:
  - Own or interpret the content of Attention Engine state.
  - Own or interpret the content of Activity Controller task state.
  - Own or interpret working memory slot contents.
  - Directly reconstruct state without notifying the owning engine.

Restoration Protocol:
  1. Query latest valid checkpoint for domain_partition + schema_version.
  2. Validate: schema_version >= MIN_SUPPORTED_VERSION (migration gate).
  3. For each snapshot_ref in checkpoint:
     Emit event "memory.restoration_requested" with {snapshot_ref, owning_engine}.
  4. Each owning engine receives the event and independently validates its snapshot.
  5. Owning engine emits "engine.state_restored" or "engine.state_restoration_failed".
  6. MemoryContinuityService records restoration_succeeded based on engine responses.
  7. If restoration_succeeded = False for any critical snapshot: emit warning event;
     start in degraded mode (engines use safe initial state).

Autonomous checkpoints are stored in a SEPARATE row (domain_partition = 'AUTONOMOUS').
Cognitive engines cannot read autonomous checkpoints and vice versa.


5.10 SUBSYSTEM 10: MEMORY GOVERNANCE
--------------------------------------

Service Name: MemoryGovernanceService
Data ownership: access_policies, audit_events, schema_versions tables.

Responsibilities:
  - Enforce ALL access control policies on reads and writes.
  - Assign persistent UUIDs to accepted development proposals (external engines cannot
    supply their own database UUIDs for proposed records).
  - Validate schema compatibility on all incoming data.
  - Maintain immutable audit log for all persistent state changes.
  - Review development proposals above the risk-based acceptance threshold.
  - Enforce version validation on continuity checkpoint restoration.

Governance is the FINAL AUTHORITY on all persistent memory state changes.
No subsystem may bypass Governance when making persistent changes.

Access enforcement design:
  - Every read request to RetrievalEngineService passes through check_access_policy().
  - Every write request passes through check_write_policy().
  - Access denied → returns empty set for reads, raises MemoryAccessDeniedError for writes.
  - ALL policy decisions are logged to audit_events regardless of outcome.

check_access_policy(requesting_engine, target_resource, access_mode):
  1. Find matching policy: SELECT * FROM access_policies
     WHERE resource_type IN (:resource_type, 'ALL')
       AND domain_partition = :target_partition
       AND active = 1
       AND (expires_at IS NULL OR expires_at > now())
     ORDER BY resource_type DESC LIMIT 1;
  2. If no policy found: DENY by default (allowlist model).
  3. If policy found: check requesting_engine IN permitted_engines JSON array.
  4. Check access_mode IN access_modes JSON array.
  5. Write audit_events record (success or denial).
  6. Return ALLOW or DENY.

6.3 MEMORY DEVELOPMENT PROTOCOL (THREE OPERATION KINDS)
---------------------------------------------------------

KIND A — INDEPENDENT OPERATIONS (Memory executes without other engines):
  Triggered by: background_jobs with types:
    DEDUPLICATION, ENTITY_LINKING, PATTERN_DETECTION, CONTRADICTION_CHECK,
    TEMPORAL_SEQUENCE, DEPENDENCY_ANALYSIS, FTS5_INDEXING, EMBEDDING_GENERATION

  Lifecycle:
    Job PENDING → Worker acquires lease → Job RUNNING
    → MemoryDevelopmentService.execute_independent(job)
    → If simple organizational result: Governance risk-based auto-accept
    → Write development_reviews record (reviewer = "MEMORY_GOVERNANCE_AUTO")
    → Write accepted records with Governance-assigned UUIDs
    → Job COMPLETED

KIND B — COLLABORATIVE OPERATIONS (Memory requests specialized engine):
  Triggered by: Memory Development detecting a pattern requiring domain expertise.

  Lifecycle:
    MemoryDevelopmentService creates development_requests record (status=PENDING)
    → Emits outbox event "memory.development_requested" with {request_id, target_engine}
    → Target engine subscribes and processes asynchronously
    → Target engine calls submit_development_result(result: DevelopmentResult)
    → Memory Governance validates:
        a. originating_engine matches expected target_engine for this request_id
        b. All proposed claims reference valid source_memory_ids
        c. No external UUIDs supplied for proposed records (Memory assigns UUIDs)
        d. Epistemic invariants not violated (MEM-003)
        e. result_status is not auto-accepting governance bypass
    → Decision: ACCEPT (create records) | REJECT (record reason) | DEFER (future cycle)
    → Write development_reviews record
    → If ACCEPT: assign permanent UUIDs; write memory_representations / claims / relationships
    → Emit appropriate outbox event

KIND C — INTEGRATION OPERATIONS (Memory receives and integrates):
  After Kind B result is accepted: Memory creates derivation_links, updates representation
  lineage, records provenance, emits "memory.development_accepted" event.

7.1 MEMORY OWNERSHIP DIMENSIONS
---------------------------------

Four independent dimensions MUST NOT be conflated:

Dimension 1 — OWNER DOMAIN:
  Which Diva subsystem/domain owns this record?
  Values: 'COGNITIVE' | 'AUTONOMOUS' | 'SHARED'
  Stored in: experiences.domain_partition, claims.domain_partition

Dimension 2 — SUBJECT:
  Whom or what does this record describe?
  Stored as: subject_entity_id FK in claims; participants JSON in experiences
  Example: An autonomous experience may describe the USER — that does not give
           the cognitive domain automatic access to it.

Dimension 3 — ORIGIN:
  Where did this information come from?
  Stored as: source_engine field in all records

Dimension 4 — ACCESS SCOPE:
  Which engines are authorized to access this record?
  Defined in: access_policies table (allowlist model)

These dimensions are ORTHOGONAL. All four must be checked independently.


7.2 ACCESS POLICY ENFORCEMENT ARCHITECTURE
--------------------------------------------

The Memory Engine implements an ALLOWLIST authorization model. No access is
permitted unless explicitly granted by an active access_policy record.

check_access_policy(requesting_engine, target_resource_id, resource_type, access_mode):
  Step 1 — POLICY LOOKUP:
    SELECT * FROM access_policies
    WHERE resource_type IN (:resource_type, 'ALL')
      AND domain_partition = :target_partition
      AND active = 1
      AND (expires_at IS NULL OR expires_at > CURRENT_TIMESTAMP)
    ORDER BY resource_type DESC   -- specific resource > 'ALL' wildcard
    LIMIT 1;

  Step 2 — ENGINE ALLOWLIST CHECK:
    If no policy found: DENY (default deny — no open access).
    If policy found: check requesting_engine IN json_each(permitted_engines).

  Step 3 — MODE CHECK:
    Check access_mode IN json_each(access_modes).
    access_modes values: 'READ' | 'WRITE' | 'DELETE' | 'ARCHIVE'

  Step 4 — AUDIT:
    Always write to audit_events regardless of outcome:
      {event_type: 'ACCESS_GRANTED' | 'ACCESS_DENIED',
       target_id, target_type, actor_engine, actor_session, policy_id, event_at}

  Step 5 — RETURN:
    ALLOW → proceed; DENY → raise MemoryAccessDeniedError (never return partial data).

WRITE POLICY ENFORCEMENT:
  check_write_policy(requesting_engine, record_type, domain_partition):
    Uses the same policy lookup with access_mode = 'WRITE'.
    Additional invariant: If record_type = 'CLAIM' and requesting_engine != 'MEMORY_GOVERNANCE':
      Engine may SUBMIT a proposed claim via submit_knowledge_contribution() ONLY.
      Engine may NOT write directly to the claims table.
      MemoryGovernanceService is the SOLE direct writer to claims.

ACCESS POLICY SEED DATA (applied at Milestone 01):
  Policy 1: PERCEPTION engine → READ/WRITE to COGNITIVE partition experiences.
  Policy 2: THOUGHT engine → READ COGNITIVE; SUBMIT development proposals.
  Policy 3: EMOTION engine → READ COGNITIVE; WRITE emotional appraisals.
  Policy 4: SOCIAL COGNITION → READ COGNITIVE; WRITE social appraisals.
  Policy 5: LEARNING engine → READ COGNITIVE; SUBMIT development proposals.
  Policy 6: MOTIVATION engine → READ COGNITIVE; READ goal-related claims.
  Policy 7: COGNITIVE INTEGRATION → READ COGNITIVE; WRITE checkpoints.
  Policy 8: AUTONOMOUS engines → READ/WRITE AUTONOMOUS partition ONLY.
  Policy 9: MEMORY GOVERNANCE → READ/WRITE ALL partitions (admin access).
  Policy 10: FEEDBACK engine → READ COGNITIVE; SUBMIT evaluation results.
  Policy 11: INTERACTION engine → READ COGNITIVE; WRITE interaction experiences.
  Policy 12: AUTONOMOUS ACTIVITY → READ/WRITE AUTONOMOUS; READ SHARED.
  Policy 13: SHARED resources → READ by any engine with explicit grant.
  Policy 14: MEMORY DEVELOPMENT SERVICE → READ ALL; WRITE development records.


7.3 AUDIT EVENT MODEL
-----------------------

The audit_events table is an IMMUTABLE, APPEND-ONLY ledger of all state changes.
No existing audit record is ever modified or deleted.

Audit Event Types (complete catalog):
  EXPERIENCE_CREATED         — New experience row committed.
  EXPERIENCE_STATUS_CHANGED  — development_status or validity_status updated.
  CLAIM_CREATED              — New claim row committed by Governance.
  CLAIM_STATUS_CHANGED       — lifecycle or evidence_status updated.
  CLAIM_ASSESSMENT_ADDED     — New ClaimAssessment submitted by engine.
  CLAIM_VERSION_CREATED      — New claim_versions row for state change.
  ENTITY_CREATED             — New entity row committed.
  ENTITY_MERGED              — Two entities merged (merged_into set).
  RELATIONSHIP_CREATED       — New memory_relationship or claim_relationship added.
  RELATIONSHIP_SUPERSEDED    — Relationship marked superseded=1.
  DEVELOPMENT_REQUESTED      — DevelopmentRequest created.
  DEVELOPMENT_ACCEPTED       — DevelopmentResult accepted; records assigned UUIDs.
  DEVELOPMENT_REJECTED       — DevelopmentResult rejected; reason recorded.
  CONSOLIDATION_STARTED      — ConsolidationJob created.
  CONSOLIDATION_COMPLETED    — All 7 gates passed; representation created.
  CONSOLIDATION_REJECTED     — Any gate failed.
  MEMORY_ARCHIVED            — Retention record transitioned to ARCHIVED.
  MEMORY_RESTORED            — Cold archive payload successfully restored.
  CHECKPOINT_CREATED         — ContinuityCheckpoint committed.
  CHECKPOINT_RESTORED        — Restoration completed successfully.
  CHECKPOINT_FAILED          — Restoration could not be completed.
  ACCESS_GRANTED             — Access policy check: ALLOW outcome.
  ACCESS_DENIED              — Access policy check: DENY outcome.
  POLICY_CREATED             — New access_policy row committed.
  POLICY_EXPIRED             — Policy active=0 set after expires_at < now.
  SCHEMA_MIGRATED            — schema_versions migration successfully applied.

Audit Record Structure:
  audit_id:      UUID (UUIDv7, monotonically ordered for time-sorted queries)
  event_type:    One of the catalog types above.
  target_id:     UUID of the affected record.
  target_type:   'EXPERIENCE' | 'CLAIM' | 'ENTITY' | 'RELATIONSHIP' | etc.
  actor_engine:  Engine name that initiated the action.
  actor_session: Session UUID during which the action occurred.
  old_state:     JSON snapshot of record before change (NULL for CREATE events).
  new_state:     JSON snapshot of record after change.
  policy_id:     FK to access_policies record that authorized this action (NULL for system).
  event_at:      ISO-8601 UTC timestamp.

AUDIT INVARIANTS:
  - Every write operation MUST produce a corresponding audit_events entry.
  - Audit events are written IN THE SAME TRANSACTION as the data operation.
  - If the data transaction rolls back, the audit event also rolls back.
  - Audit records are never updated; corrections append new CORRECTION-type events.
  - Audit log is queryable but never the source of truth for memory state.

7.4 COGNITIVE vs. AUTONOMOUS MEMORY PARTITION INVARIANTS

MEM-014: Autonomous and cognitive memory must remain isolated by default.

Implementation:
  - Every table that holds memory data has a domain_partition column.
  - Every READ query includes: AND domain_partition = :requester_partition
    OR domain_partition = 'SHARED'.
  - Every WRITE operation sets domain_partition = requester's partition.
  - Cross-domain sharing requires: an explicit access_policies record,
    an audit_events entry, and Memory Governance approval.
  - Continuity checkpoints are stored and restored per domain partition separately.

9.1 MUST-PASS CONDITIONS (45 TESTABLE INVARIANT CHECKPOINTS)
--------------------------------------------------------------

EXPERIENCE INTEGRITY (MEM-001 group):
  [MEM-001-A] Submitting the same experience payload twice produces exactly one
              experience record (idempotency via content_hash deduplication).
  [MEM-001-B] No field of an existing experience record is modified after initial commit.
              Validation: SELECT COUNT(*) FROM audit_events WHERE event_type = 'EXPERIENCE_UPDATED'
              must return 0 (updates only allowed via versioned state transitions).
  [MEM-001-C] The input_events record for a session is preserved even when the
              experience worthiness filter decides NOT to create an experience record.

PROVENANCE INTEGRITY (MEM-002 group):
  [MEM-002-A] Every row in the claims table has non-null source_engine and provenance_hash.
  [MEM-002-B] Every row in the evidence_references table has at least one of
              source_memory_id or source_claim_id as non-null.
  [MEM-002-C] Every memory_representation record has at least one derivation_links row
              pointing to a valid source record.

EPISTEMIC INTEGRITY (MEM-003 group):
  [MEM-003-A] A claim submitted with epistemic_type=INTERPRETATION is stored as
              INTERPRETATION. No downstream process may change it to OBSERVATION.
  [MEM-003-B] A claim submitted with epistemic_type=REPORTED is stored as REPORTED.
  [MEM-003-C] Gate 7 of consolidation verification rejects any consolidated representation
              where EPISTEMIC_RANK(consolidated) > EPISTEMIC_RANK(source) for any claim.
  [MEM-003-D] A REPORTED claim about another person never becomes an OBSERVATION
              even after multiple corroborating REPORTED claims.

DEVELOPMENT INTEGRITY (MEM-004, MEM-015, MEM-016 group):
  [MEM-004-A] Every accepted DevelopmentResult has a corresponding development_reviews
              record with reviewer = 'MEMORY_GOVERNANCE' or a specialized engine.
  [MEM-004-B] No development operation sets evidence_status = CORROBORATED without
              at least 2 independent evidence_references with relationship = SUPPORTS.
  [MEM-015-A] No engine may write directly to memory_representations or claims tables.
              Validation: all writes go through MemoryGovernanceService check_write_policy().
  [MEM-015-B] A DevelopmentResult submitted by Emotion Engine cannot contain claims with
              epistemic_type = OBSERVATION (Emotion Engine produces INTERPRETATION only).
  [MEM-016-A] Every accepted development operation has ≥ 1 derivation_links row.
  [MEM-016-B] Every new memory_representation version has parent_representation_id
              pointing to its predecessor (except root version = 1).

CONTRADICTION INTEGRITY (MEM-005 group):
  [MEM-005-A] Two claims with identical subject_entity_id + predicate but different
              object_value with overlapping world_time ranges produce a CONTRADICTS
              claim_relationship record.
  [MEM-005-B] Both claims in a contradiction remain lifecycle = ACTIVE until explicitly
              resolved; neither is auto-deleted or auto-superseded.
  [MEM-005-C] Contradiction detection handles circular contradiction chains (A CONTRADICTS B
              CONTRADICTS A) without infinite loop or stack overflow.

KNOWLEDGE EVOLUTION (MEM-006 group):
  [MEM-006-A] Submitting a corrected claim creates: (1) new claim with lifecycle=ACTIVE,
              (2) CORRECTS relationship from new to old, (3) old claim lifecycle=SUPERSEDED.
  [MEM-006-B] The original experience record from which the old claim was derived remains
              unchanged after the correction is applied.
  [MEM-006-C] An emotional appraisal reappraisal (from Emotion Engine) creates a new
              appraisal_history record; previous appraisal marked superseded=1.

DOMAIN SEPARATION (MEM-007, MEM-014 group):
  [MEM-007-A] Memory Engine does not store Emotion Engine's internal PAD vector state.
              Memory stores Emotion's submitted appraisals in memory_appraisals table only.
  [MEM-007-B] Memory Engine does not store Attention Engine's lease allocation state.
              Memory stores Attention's submitted snapshot references in checkpoints only.
  [MEM-014-A] A COGNITIVE-partition query returns zero rows from AUTONOMOUS-partition tables.
  [MEM-014-B] An AUTONOMOUS engine calling retrieve_memories() with COGNITIVE records
              receives empty result and an ACCESS_DENIED audit_event entry.
  [MEM-014-C] COGNITIVE and AUTONOMOUS continuity_checkpoints have separate rows with
              distinct domain_partition values; neither can be restored by the other domain.

ACCESS CONTROL (MEM-008 group):
  [MEM-008-A] An engine not listed in access_policies.permitted_engines for a resource
              receives MemoryAccessDeniedError and an audit_events record.
  [MEM-008-B] An expired access policy (expires_at < now) is treated as non-existent.
  [MEM-008-C] Every successful write operation produces an audit_events record.
  [MEM-008-D] Every denied write attempt produces an audit_events record.

CONSOLIDATION INTEGRITY (MEM-009 group):
  [MEM-009-A] Consolidation job for N source memories produces consolidation_coverage
              rows with |covered + residual| == |source claims| (100% coverage).
  [MEM-009-B] A consolidation job with Gate 2 failure (contradiction dropped) is REJECTED;
              consolidation_jobs.all_gates_passed = 0 and failure_reason is non-null.
  [MEM-009-C] Source memories remain in retention_status = 'ACTIVE' until ALL gates pass.

RETENTION & ARCHIVAL (MEM-010 group):
  [MEM-010-A] A memory with dependency_count > 0 cannot have retention_status = ARCHIVED.
  [MEM-010-B] An archived memory's payload remains recoverable: archive record stores
              checksum; restoration verifies checksum before returning payload.
  [MEM-010-C] Archival of a memory with permanent_importance >= 0.8 is REJECTED.

RETRIEVAL CORRECTNESS (MEM-011, MEM-012 group):
  [MEM-011-A] Retrieval of an entity attribute returns HISTORICAL label when querying
              a time window where a newer value has superseded the old one.
  [MEM-011-B] Retrieval of a REFUTED claim includes refuted_status in the response
              metadata; refuted claims are NEVER returned as current knowledge.
  [MEM-012-A] retrieve_memories() completes successfully when embedding_provider is None
              (using SQL + FTS5 layers only; no exception raised).
  [MEM-012-B] retrieve_memories() completes successfully when FTS5 index is empty
              (SQL layer returns results; no exception raised).

BACKGROUND JOB INTEGRITY (MEM-013 group):
  [MEM-013-A] Re-running a completed DEDUPLICATION job with identical input produces
              no new duplicate records (idempotency via idempotency_key).
  [MEM-013-B] A worker that crashes mid-job has its lease expire; job returns to PENDING
              within lease_expiry_seconds (default: 30s).
  [MEM-013-C] A job that exceeds max_attempts transitions to DEAD_LETTER status and
              emits a governance alert event rather than silently failing.

BOUNDED DEVELOPMENT (MEM-018 group):
  [MEM-018-A] A DevelopmentRequest at max_processing_depth=5 does not schedule child
              requests; instead schedules a low-priority deferred job.
  [MEM-018-B] The same (target_memory_ids, operation_type) combination does not generate
              more than N=5 jobs in a 24-hour window (circuit breaker active).
  [MEM-018-C] Retrieval gap detection schedules a development job at priority=8 (background)
              and does NOT block the retrieval response.

APPENDIX A — DEFERRED CAPABILITIES (POST-SHARED LLM INFRASTRUCTURE)
================================================================================

The following capabilities are explicitly deferred. They require the Shared LLM
Infrastructure to be built first. Memory Engine functions fully without them.

1. Automated continuous semantic memory consolidation with LLM-generated summaries.
2. Free-form natural language retrieval queries beyond FTS5 keyword matching.
3. Cross-modal memory synthesis (audio/visual with textual records).
4. Deep self-supervised contradiction resolution across multi-year records.
5. Advanced generalization proposals using LLM reasoning across distant episodes.
6. Automated semantic deduplication at scale (beyond hash + FTS5 similarity).
7. Zero-shot semantic entity linking against large external knowledge graphs.
8. Automated narrative episodic memory generation from structured event logs.
9. Dynamic weight tuning for retrieval scoring based on retrieval quality feedback.
10. HyDE-enhanced retrieval with locally hosted generative models (currently ephemeral
    templates only; requires reliable local reasoning provider first).

APPENDIX B — TECHNOLOGY STACK DECISION MATRIX (FINAL)
================================================================================

Layer                 | Technology                    | Why This / Why Not Alternative
----------------------|-------------------------------|--------------------------------
Core Language         | Python 3.12+ AsyncIO          | Diva's primary runtime; rich ecosystem
Primary Database      | SQLite 3.45+ WAL Mode         | Embedded ACID; zero network; FTS5 built-in
Vector Search         | sqlite-vec (C extension)      | Native KNN in SQLite; no external process
  Fallback            | NumPy in-process cosine KNN   | No extension required; linear scale
Full-Text Search      | SQLite FTS5 BM25              | Microsecond queries; porter stemmer
Graph Processing      | Adjacency SQL + NetworkX      | SQL for persistence; NetworkX for analysis
Embedding Model       | BAAI/bge-small-en-v1.5        | 384-dim; <10ms CPU; ONNX via FastEmbed
  Alternative         | nomic-embed-text-v1.5         | 768-dim; better for domain-specific text
Embedding Runtime     | FastEmbed (ONNX Runtime)      | No PyTorch; pure C++ ONNX; <65MB footprint
Data Validation       | Pydantic v2 (frozen models)   | Compile-time + runtime type safety
Background Jobs       | Asyncio + SQLite queue        | Crash-safe; no external broker required
Event Bus             | In-process AsyncIO pub/sub    | Zero-latency; no network; suitable for
                      | + transactional outbox        | single-process initial deployment
Compression (archive) | ZSTD                          | Best compression/speed ratio for text
Hashing               | SHA-256 (hashlib)             | Tamper detection; no crypto overhead
UUID Generation       | UUIDv7 (monotonic ordered)    | Time-ordered; B-tree friendly; sorted by default
Schema Migrations     | Custom versioned migration fw | Full control; no dependency on Alembic/etc.

NOT USED:
  - PostgreSQL: Overkill for single-process local deployment; network overhead.
  - Redis: No external process; SQLite outbox covers persistence needs.
  - Celery: Too heavy; SQLite + asyncio job queue is sufficient and simpler.
  - LanceDB: sqlite-vec preferred; keeps everything in one file.
  - ChromaDB / Qdrant: External process; defeats zero-dependency goal.
  - PyTorch directly: FastEmbed ONNX runtime is lighter and faster for inference only.
