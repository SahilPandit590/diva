EXECUTIVE SUMMARY & GOVERNING PRINCIPLES
================================================================================

The Feedback Engine is the system-wide retrospective evaluator. It receives
outcome data from every engine and external source, compares what happened to
what was intended, identifies contributing factors, assesses evidence quality,
detects recurring patterns, and produces structured feedback records that are
dispatched to the Learning Engine and other consumers.

THE FIVE NON-NEGOTIABLE AXIOMS:
1. FEEDBACK IS NOT LEARNING.
   Feedback produces evaluated evidence. Learning decides what changes.
2. SUCCESS IS NOT QUALITY.
   An objective achieved through a poor process still merits efficiency feedback.
3. CORRELATION IS NOT CAUSATION.
   Two events co-occurring is not proof one caused the other.
4. NEGATIVE FEEDBACK IS NOT THE ONLY USEFUL FEEDBACK.
   Successes, improvements, and effective strategies must also be captured.
5. EVERY EVALUATION MUST BE TRACEABLE.
   From raw signal to final feedback record, the full provenance chain persists.

TRIPLE-EVALUATOR SEPARATION:
- Feedback Engine: Retrospective — What happened? How well?
- Learning Engine: Developmental — Should we change something?
- Cognitive Integration: Prospective — What should Diva do next?

OWNERSHIP BOUNDARY: The Feedback Engine NEVER directly modifies any other
engine's parameters, personality, emotions, motivations, memory, or behavior.
It evaluates and dispatches structured evidence. Period.

PART 1 — HOW THE ENGINE RUNS: OVERALL EXECUTION MODEL
================================================================================

1.1 EVENT-DRIVEN ASYNC PIPELINE
   The engine runs as an asynchronous event-driven pipeline with three tiers:

   TIER 1 — HOT PATH (synchronous, <50 ms):
   Receives raw outcome signals, validates schema, deduplicates, and queues
   for processing. This is the Feedback Input Handler + Source Validator.

   TIER 2 — WARM PATH (async, <500 ms):
   Normalizes feedback, classifies it, runs deterministic expected-vs-actual
   comparison, computes quality metrics, and assesses confidence. This is the
   core evaluation pipeline.

   TIER 3 — COLD PATH (async, background):
   Runs LLM-assisted causal analysis for complex failures, performs pattern
   detection across accumulated history, evaluates inter-engine coordination,
   and dispatches structured feedback to recipients. Runs with configurable
   delay to batch related events.

   Pipeline Flow:
   ```
   [Raw Signal]
        │
        ▼
   ┌─────────────────┐
   │ Input Handler    │── Schema validation, dedup, timestamp
   └────────┬────────┘
            ▼
   ┌─────────────────┐
   │ Source Validator  │── Provenance check, source reliability lookup
   └────────┬────────┘
            ▼
   ┌─────────────────┐
   │ Normalizer       │── Convert to standard FeedbackRecord
   └────────┬────────┘
            ▼
   ┌─────────────────┐
   │ Classifier       │── Assign categories (may be multiple)
   └────────┬────────┘
            ▼
   ┌───────────────────────────────────┐
   │ Outcome Evaluator                 │── Expected vs. actual comparison
   │   ├─ Quality Assessment Module    │── Correctness, completeness, efficiency
   │   ├─ Failure Analysis Module      │── If outcome indicates failure
   │   └─ Causal Attribution Module    │── Contributing factor identification
   └────────┬──────────────────────────┘
            ▼
   ┌─────────────────┐
   │ Confidence       │── Evidence reliability scoring
   │ Assessment       │
   └────────┬────────┘
            ▼
   ┌─────────────────┐
   │ Pattern Recog.   │── Cross-experience trend detection
   └────────┬────────┘
            ▼
   ┌─────────────────┐
   │ Coordination     │── Inter-engine cooperation evaluation
   │ Evaluator        │
   └────────┬────────┘
            ▼
   ┌─────────────────┐
   │ Feedback         │── Assembles structured FeedbackContribution
   │ Generator        │
   └────────┬────────┘
            ▼
   ┌─────────────────┐          ┌──────────────┐
   │ Priority Mgr     │──────▶  │ Distribution │──▶ Learning, Engines
   └─────────────────┘          │ Manager      │
                                └──────────────┘
   ```

1.2 CONCURRENCY MODEL
   - Single writer thread for SQLite (all persistence goes through one
     asyncio task with a serialized write queue).
   - Multiple reader tasks for concurrent evaluation pipelines.
   - Pattern Recognition and Coordination Evaluator run as periodic
     background tasks (every N feedback records or configurable interval).
   - LLM calls are async with timeout ($T_{llm} = 10,000$ ms) and fallback
     to deterministic-only evaluation.

1.3 RESOURCE AWARENESS
   - Internal State Engine provides $E_{cog}$ (cognitive energy).
   - When $E_{cog} < 0.30$: Defer TIER 3 processing (pattern analysis,
     coordination evaluation). Process only TIER 1 + TIER 2.
   - When $E_{cog} < 0.15$: Defer TIER 2 as well; only ingest and queue.
   - Critical safety feedback always processed regardless of energy.

1.4 STARTUP AND RECOVERY
   1. Load all SQLite tables and verify referential integrity.
   2. Identify feedback records in non-terminal lifecycle states
      (RECEIVED, VALIDATING, PROCESSING, EVALUATED, PENDING_EVIDENCE).
   3. For records in PROCESSING: Roll back to VALIDATING; re-process.
   4. For records in EVALUATED but not DISTRIBUTED: Resume distribution.
   5. Rebuild in-memory indexes (activity-to-feedback mapping, pattern caches).
   6. Resume processing from latest timestamp.

PART 2 — ALGORITHMS, DATA STRUCTURES & SERVICE SPECIFICATIONS
================================================================================

--------------------------------------------------------------------------------
A. SEVENTEEN LOGICAL SERVICES
--------------------------------------------------------------------------------

SERVICE 1: FEEDBACK INPUT HANDLER
  Purpose: Receives raw outcome signals from all sources, validates schema.
  Algorithm: Schema validation against per-source JSON schemas. O(1) per record.
  Deduplication: Content-hash of (source_engine, source_event_id, activity_id).
    Uses a Bloom filter (false positive rate 0.01%) backed by a SQLite
    dedup_hashes table for authoritative checks on Bloom hits.
  Output: Validated raw signal passed to Source Validator.
  Error: Malformed signals rejected with REJECTED lifecycle state and logged.

SERVICE 2: FEEDBACK SOURCE VALIDATOR
  Purpose: Verifies provenance and assigns source reliability scores.
  Algorithm: Lookup source_engine in `source_reliability_registry`.
    Source reliability $Rel_s \in [0.0, 1.0]$:
    - Internal engines: $Rel_s = 0.90$ (high baseline; Diva's own subsystems).
    - Explicit user feedback: $Rel_s = 0.85$ (high but subjective).
    - API/tool results: $Rel_s = 0.80$ (objective but context-limited).
    - Third-party evaluations: $Rel_s = 0.70$ (variable quality).
    - Unverified sources: $Rel_s = 0.50$ (uncertain).
  Reliability may be adjusted by pattern analysis over time (e.g., if a
  particular source repeatedly produces contradicted feedback, $Rel_s$ decays).
  Output: Source-annotated signal with $Rel_s$ attached.

SERVICE 3: FEEDBACK NORMALIZER
  Purpose: Converts heterogeneous raw signals into standard FeedbackRecord.
  Algorithm: Per-source-type adapter pattern. Each adapter maps source-specific
    fields to the canonical FeedbackRecord schema.
    Adapters defined for: ExternalUser, ToolExecution, EngineOutcome,
    AutonomousActivity, InteractionOutcome, DecisionOutcome.
  Timestamp normalization: All timestamps converted to ISO-8601 UTC.
  Missing fields: Filled with defaults and flagged as `incomplete = True`.
  Output: Normalized FeedbackRecord with lifecycle state = VALIDATING.

SERVICE 4: FEEDBACK CLASSIFIER
  Purpose: Assigns one or more feedback categories from the 15-category taxonomy.
  Algorithm: Rule-based classification with LLM fallback for ambiguous cases.
    Rule Engine:
    - If error_code present → EXECUTION_FEEDBACK.
    - If user_rating present → QUALITY_FEEDBACK.
    - If safety_violation flag → SAFETY_FEEDBACK.
    - If unexpected_result flag → UNEXPECTED_OUTCOME.
    - If originating_engine = EMOTION → EMOTIONAL_FEEDBACK.
    - If originating_engine = SOCIAL → SOCIAL_FEEDBACK.
    - If multiple rules match → Assign ALL matching categories.
    LLM Fallback: When no deterministic rule matches, dispatch to shared LLM
    with interaction context. LLM returns candidate categories with confidences.
    Accept categories with $C \ge 0.40$.
  Category Enum: SUCCESS, FAILURE, PARTIAL_SUCCESS, QUALITY, ACCURACY,
    EFFICIENCY, BEHAVIORAL, SOCIAL, EMOTIONAL, COGNITIVE, EXECUTION,
    LEARNING, COORDINATION, SAFETY, UNEXPECTED_OUTCOME.
  Polarity: Each category assignment carries polarity (POSITIVE, NEGATIVE,
    NEUTRAL, MIXED).
  Output: Multi-category classified FeedbackRecord.

SERVICE 5: OUTCOME EVALUATOR
  Purpose: Compares expected outcomes against actual outcomes. This is the
  most important service in the engine.
  
  Algorithm — Multi-Objective Outcome Comparison:
  Input: Tuple of (objective_id, expected_outcome, actual_outcome, importance_weight).
  
  For each objective $i$:
    1. Compute completion score:
       $completion_i = \text{similarity}(expected_i, actual_i) \in [0.0, 1.0]$
       For numerical objectives: $completion_i = 1 - \frac{|expected - actual|}{\max(|expected|, 1)}$ clamped to [0,1].
       For boolean objectives: $completion_i \in \{0.0, 1.0\}$.
       For qualitative objectives: LLM-assessed similarity score.
    2. Classify per-objective outcome:
       $completion_i \ge 0.90$ → FULLY_MET.
       $0.50 \le completion_i < 0.90$ → PARTIALLY_MET.
       $completion_i < 0.50$ → NOT_MET.
    3. Detect unexpected results:
       If actual outcome contains elements NOT in expected → flag UNEXPECTED_POSITIVE or UNEXPECTED_NEGATIVE.
  
  Aggregate outcome:
    $O_{aggregate} = \frac{\sum_i w_i \cdot completion_i}{\sum_i w_i}$
    where $w_i$ is the importance weight of objective $i$.
  
  Overall classification:
    $O_{aggregate} \ge 0.90$ → SUCCESS.
    $0.50 \le O_{aggregate} < 0.90$ → PARTIAL_SUCCESS.
    $O_{aggregate} < 0.50$ → FAILURE.
  
  Critical rule: Quality and Efficiency are evaluated INDEPENDENTLY of completion.
  A fully completed task can still have poor quality or low efficiency.
  
  Output: OutcomeComparison with per-objective and aggregate results.

SERVICE 6: QUALITY ASSESSMENT MODULE
  Purpose: Evaluates the quality of a result independently of completion.
  
  Algorithm — Six-Dimension Quality Assessment:
  For each outcome, compute scores across six quality dimensions:
    1. CORRECTNESS: $Q_{correct} \in [0.0, 1.0]$ — factual accuracy.
    2. COMPLETENESS: $Q_{complete} \in [0.0, 1.0]$ — coverage of requirements.
    3. CONSISTENCY: $Q_{consist} \in [0.0, 1.0]$ — internal logical coherence.
    4. USEFULNESS: $Q_{useful} \in [0.0, 1.0]$ — practical value to the requester.
    5. EFFICIENCY: $Q_{effic} \in [0.0, 1.0]$ — resource consumption vs. expected budget.
       $Q_{effic} = \max(0, 1 - \frac{\text{actual\_cost} - \text{expected\_cost}}{\text{expected\_cost}})$
    6. ROBUSTNESS: $Q_{robust} \in [0.0, 1.0]$ — resilience to edge cases.
  
  Aggregate quality:
    $Q_{total} = \sum_d w_d \cdot Q_d$ with domain-specific weights summing to 1.0.
    Default: $w_{correct}=0.25, w_{complete}=0.20, w_{consist}=0.15, w_{useful}=0.20, w_{effic}=0.10, w_{robust}=0.10$.
  
  LLM Integration: Correctness and Usefulness dimensions use LLM assessment
  when the outcome is qualitative. Efficiency and Consistency use deterministic
  computation.
  
  Output: QualityAssessment with per-dimension scores.

SERVICE 7: FAILURE ANALYSIS MODULE
  Purpose: Investigates why an activity failed or underperformed.
  
  Algorithm — Multi-Hypothesis Failure Analysis:
  1. Extract observable failure indicators:
     - Error codes, exception types, timeout flags.
     - Completion gaps from Outcome Evaluator.
     - Quality dimension scores below threshold ($Q_d < 0.40$).
  
  2. Generate failure hypotheses:
     Deterministic hypotheses from error codes:
       - TIMEOUT → Hypothesis: Resource limitation ($C = 0.70$).
       - EXTERNAL_ERROR → Hypothesis: External service failure ($C = 0.80$).
       - VALIDATION_ERROR → Hypothesis: Incorrect input or assumption ($C = 0.65$).
     
     LLM-assisted hypotheses for complex failures:
       - Dispatch failure context + activity history to shared LLM.
       - LLM returns ranked hypotheses with confidence scores.
       - Accept hypotheses with $C \ge 0.20$.
  
  3. Root cause vs. proximate cause:
     Each FailureHypothesis is tagged as:
       - PROXIMATE: The immediate trigger (e.g., "operation timed out").
       - ROOT: The underlying cause (e.g., "insufficient processing resources
         due to concurrent high-priority tasks").
       - CONTRIBUTING: A factor that worsened the outcome but didn't cause it alone.
     Requires $\ge 2$ supporting evidence items for ROOT classification.
  
  4. Cross-reference with historical failures:
     Query `failure_records` for the same activity type, same affected engine.
     If $\ge 3$ similar failures exist: Link to existing FailurePattern.
  
  Output: Set of FailureHypothesis records with cause type and confidence.

SERVICE 8: CAUSAL ATTRIBUTION MODULE
  Purpose: Identifies which factors contributed to an outcome (positive or negative).
  
  Algorithm — Weighted Evidence Causal Graph:
  1. Collect temporal predecessors:
     All engine events within the causal window ($T_{window} = 60$ seconds
     before outcome, configurable per activity type).
  
  2. Build causal candidate graph:
     Nodes: Engine events, decisions, actions, external inputs.
     Edges: Temporal ordering + explicit dependency links from activity metadata.
  
  3. Score causal contribution:
     For each candidate node $n$:
       $Causal_n = w_{temporal} \cdot P_{temporal}(n) + w_{dependency} \cdot P_{dependency}(n) + w_{counterfactual} \cdot P_{counter}(n)$
     Where:
       - $P_{temporal}$: Temporal proximity weight (closer events score higher).
         $P_{temporal} = \exp(-\lambda_t \cdot \Delta t)$ with $\lambda_t = 0.05$.
       - $P_{dependency}$: 1.0 if explicit dependency link exists, 0.0 otherwise.
       - $P_{counter}$: Counterfactual plausibility — would outcome differ
         without this event? (LLM-assessed for complex cases, heuristic for simple).
     Default weights: $w_{temporal}=0.20, w_{dependency}=0.50, w_{counterfactual}=0.30$.
  
  4. Anti-blame safeguard:
     - No single node can receive $Causal > 0.80$ unless it has an explicit
       dependency link AND counterfactual score $\ge 0.70$.
     - Multiple contributing causes are the default; single-cause attribution
       requires exceptional evidence.
  
  5. Correlation vs. causation flag:
     If $P_{dependency} = 0$ AND $P_{counter} < 0.50$:
       Tag relationship as CORRELATION_ONLY (not causal).
  
  Output: CausalAttribution records with per-node contributions.

SERVICE 9: CONFIDENCE ASSESSMENT MODULE
  Purpose: Evaluates the reliability of the feedback evidence chain.
  
  Algorithm — Multi-Factor Confidence Computation:
  $C_{feedback} = \text{clamp}_{[0.0, 1.0]}\left(
    w_{source} \cdot Rel_s +
    w_{evidence} \cdot Q_{evidence} +
    w_{recency} \cdot R_{time} +
    w_{consistency} \cdot S_{consistency}
  \right)$
  
  Where:
    - $Rel_s$: Source reliability from Service 2.
    - $Q_{evidence}$: Evidence quality. $Q_{evidence} = \frac{n_{objective}}{n_{objective} + n_{subjective}}$
      where $n_{objective}$ = count of measurable/verifiable evidence items.
    - $R_{time}$: Recency factor. $R_{time} = \exp(-\lambda_r \cdot \Delta t_{hours})$
      with $\lambda_r = 0.01$ (slow decay; feedback stays relevant for days).
    - $S_{consistency}$: Cross-source consistency. If multiple sources report on
      same activity: $S = 1 - \text{variance}(\text{assessments})$.
      Single source: $S = 0.50$ (neutral).
  
  Default weights: $w_{source}=0.30, w_{evidence}=0.30, w_{recency}=0.20, w_{consistency}=0.20$.
  
  User satisfaction vs. factual accuracy:
    When user and system assessments conflict (user says wrong, system says correct),
    record BOTH as independent feedback dimensions. User satisfaction is a
    SUBJECTIVE dimension; factual accuracy is an OBJECTIVE dimension.
    They are NOT averaged into a single score.
  
  Output: FeedbackConfidence record with per-factor scores.

SERVICE 10: PATTERN RECOGNITION MODULE
  Purpose: Identifies recurring trends across accumulated feedback history.
  
  Algorithm — Sliding Window Pattern Detector:
  1. Maintain per-activity-type, per-engine, per-category accumulators.
  
  2. For each accumulator, track:
     - $n_{success}$: Count of positive feedback instances.
     - $n_{failure}$: Count of negative feedback instances.
     - $n_{total}$: Total instances.
     - $\bar{Q}$: Running mean quality score.
     - $\sigma_Q$: Running standard deviation of quality.
  
  3. Pattern detection triggers:
     Recurring Success: $n_{success} \ge 5$ AND $\frac{n_{success}}{n_{total}} \ge 0.80$.
     Recurring Failure: $n_{failure} \ge 3$ AND $\frac{n_{failure}}{n_{total}} \ge 0.60$.
     Improvement: Monotonic increase in $\bar{Q}$ over last 5 evaluations ($\Delta\bar{Q} \ge +0.05$).
     Regression: Monotonic decrease in $\bar{Q}$ over last 5 evaluations ($\Delta\bar{Q} \le -0.05$).
     Sudden Change: $|Q_{latest} - \bar{Q}| > 2\sigma_Q$ (outlier detection).
  
  4. Pattern lifecycle:
     EMERGING: Trigger threshold met but $n_{total} < 8$.
     ESTABLISHED: $n_{total} \ge 8$ AND pattern persists.
     FADING: No new supporting evidence for $\ge 15$ evaluations.
     CONTRADICTED: Counter-evidence exceeds supporting evidence.
  
  5. Context-dependent patterns:
     Patterns are segmented by context tags (activity_type, domain, engine).
     "Diva struggles with multi-step tasks" is a context-specific pattern,
     not a global failure indicator.
  
  Output: PerformanceTrend and SuccessPattern/FailurePattern records.

SERVICE 11: COORDINATION EVALUATOR
  Purpose: Evaluates inter-engine communication quality.
  
  Algorithm — Communication Trace Analysis:
  1. For each evaluated activity, collect the inter-engine communication trace:
     Ordered sequence of (source_engine, target_engine, payload_type, timestamp,
     was_acknowledged, response_time_ms).
  
  2. Evaluate communication quality:
     - Missing information: Expected inputs that were never delivered.
       Detection: Compare activity requirements with received inputs.
     - Duplicated processing: Same computation performed by multiple engines.
       Detection: Payload content hash comparison.
     - Excessive latency: Response time > expected SLA ($T_{sla}$ per engine pair).
       Detection: $response\_time > T_{sla} \cdot 1.5$.
     - Conflicting outputs: Multiple engines providing contradictory guidance.
       Detection: Semantic contradiction check (LLM-assisted for complex cases).
  
  3. Coordination quality score:
     $CoQ = 1.0 - \frac{n_{missing} + n_{duplicate} + n_{late} + n_{conflicting}}{n_{total\_communications}}$
     Clamped to [0.0, 1.0].
  
  4. Recurring coordination issues:
     If the same engine pair has $\ge 3$ coordination failures: Create
     CoordinationPattern record and dispatch to Learning Engine.
  
  Output: CoordinationAssessment with specific issue identifiers.

SERVICE 12: FEEDBACK GENERATOR
  Purpose: Assembles structured feedback contributions for recipients.
  
  Algorithm — Multi-Recipient Feedback Assembly:
  For each evaluated feedback record:
    1. Determine recipients based on category and affected engines.
    2. For each recipient, assemble a tailored FeedbackContribution:
       - For Learning Engine: Full `LearningFeedbackPackage` with evidence,
         confidence, outcome classification, contributing factors, pattern evidence.
         This maps directly to the `LearningContribution` schema defined in
         Learning Engine v2.5.0.
       - For originating engine: Outcome summary with quality dimensions.
       - For Cognitive Integration: Decision quality assessment.
       - For affected engines: Relevant contributing factor evidence.
    3. Attach evidence references, confidence, and provenance chain.
    4. Tag as OBSERVATION (not recommendation) — feedback describes what
       happened, not what should change.
  
  Output: Set of FeedbackContribution records ready for distribution.

SERVICE 13: FEEDBACK PRIORITIZATION MANAGER
  Purpose: Determines processing order and urgency.
  
  Algorithm — Multi-Factor Priority Score:
  $P_{feedback} = w_{severity} \cdot S + w_{recurrence} \cdot R + w_{confidence} \cdot C
                 + w_{consequence} \cdot K + w_{urgency} \cdot U$
  
  Where:
    - $S$: Severity (CRITICAL=1.0, HIGH=0.75, MEDIUM=0.50, LOW=0.25).
    - $R$: Recurrence indicator. $R = \min(1.0, n_{similar}/5)$.
    - $C$: Feedback confidence $C_{feedback}$.
    - $K$: Potential consequence magnitude.
    - $U$: Time-sensitivity (decays with age).
  
  Default weights: $w_{severity}=0.30, w_{recurrence}=0.25, w_{confidence}=0.15, w_{consequence}=0.15, w_{urgency}=0.15$.
  
  Priority tiers:
    $P \ge 0.80$: CRITICAL — Process immediately, bypass energy throttling.
    $0.60 \le P < 0.80$: HIGH — Process in current cycle.
    $0.40 \le P < 0.60$: MEDIUM — Process when resources available.
    $P < 0.40$: LOW — Queue for batch processing.
  
  Safety feedback always gets $P = 1.0$ (maximum priority).
  
  Output: Priority-sorted processing queue.

SERVICE 14: LEARNING INTEGRATION INTERFACE
  Purpose: Formats and dispatches feedback as LearningContribution to
  Learning Engine v2.5.0's FeedbackService ingress.
  
  Algorithm — LearningContribution Mapping:
  Maps Feedback Engine outputs to the standardized LearningContribution schema:
    - `contribution_id`: UUID from FeedbackContribution.
    - `source_engine`: The originating engine of the experience (NOT "FEEDBACK" —
      Feedback Engine acts as an intermediary, preserving the original source).
    - `source_event_id`: Original activity/event ID.
    - `contribution_type`: Mapped from feedback category:
      SUCCESS/FAILURE/PARTIAL → EMPIRICAL_OUTCOME.
      User correction → EXTERNAL_FEEDBACK.
      Cognitive evaluation → INTERNAL_REFLECTION.
      Quality gap → PREDICTION_ERROR.
    - `dimension_id`: Mapped from affected engine and category to Learning
      dimension registry (e.g., `thought.reasoning_accuracy`, `execution.task_completion`).
    - `evidence_references`: Provenance chain from Feedback Engine evidence records.
    - `observed_outcome`: Actual outcome data.
    - `expected_outcome`: Expected outcome data.
    - `valence`: POSITIVE_EVIDENCE / NEGATIVE_EVIDENCE / NEUTRAL_EVALUATIVE.
    - `significance`: From Feedback Engine's confidence × outcome gap magnitude.
    - `confidence`: $C_{feedback}$ from Confidence Assessment.
    - `is_quarantined`: True if Feedback confidence $< 0.40$ or if contradictory evidence exists.
    - `provenance`: Full causal chain from raw signal to evaluation.
  
  Delivery tracking: Every dispatch is recorded in feedback_distribution_records.
  Acknowledgement: Waits for Learning Engine's FeedbackService ACK. If no ACK
  within 5 seconds, retries up to 3 times. Persistent failure logged.
  
  Boundary: Feedback Engine NEVER sends `ParameterChangeRequest`. It sends
  evidence. Learning Engine decides whether to propose changes.
  
  Output: Dispatched LearningFeedbackPackage with delivery receipt.

SERVICE 15: FEEDBACK DISTRIBUTION MANAGER
  Purpose: Routes feedback contributions to all relevant recipients.
  
  Algorithm — Recipient Resolution & Delivery:
  1. Recipient resolution based on feedback category:
     SUCCESS/FAILURE/PARTIAL → Learning Engine + Originating Engine.
     QUALITY/ACCURACY → Learning Engine + Originating Engine.
     EFFICIENCY → Learning Engine + Internal State Engine.
     SOCIAL → Learning Engine + Social Cognition Engine.
     EMOTIONAL → Learning Engine + Emotion Engine.
     COORDINATION → Learning Engine + Both affected engines.
     SAFETY → Learning Engine + ALL engines (broadcast).
     UNEXPECTED → Learning Engine + Cognitive Integration.
  
  2. Deduplication: Content-hash of (feedback_id, recipient_engine).
     Prevents duplicate distribution from retries.
  
  3. Delivery confirmation: Each dispatch generates a FeedbackDistributionRecord
     tracking: dispatched_at, acknowledged_at, delivery_status.
  
  4. Anti-loop: Feedback about feedback is NOT generated. The Distribution
     Manager maintains a `feedback_about_feedback` blacklist. If the originating
     event was itself a feedback evaluation, distribution is limited to
     Learning Engine only (no recursive evaluation chains).
  
  Output: Delivery receipts for all recipients.

SERVICE 16: FEEDBACK LIFECYCLE MANAGER
  Purpose: Manages record state transitions and enforces the lifecycle FSM.
  
  Lifecycle State Machine:
  ```
  RECEIVED ──► VALIDATING ──► PROCESSING ──► EVALUATED
                   │               │              │
                   ▼               ▼              ▼
                REJECTED    PENDING_EVIDENCE  DISTRIBUTED ──► ACKNOWLEDGED
                                   │              │
                                   ▼              ▼
                              EVALUATED       CORRECTED ──► RESOLVED
                                                  │
                                                  ▼
                                              DISTRIBUTED
  ```
  
  Permitted transitions (enforced by CHECK constraint or application logic):
    RECEIVED → VALIDATING (always, on ingestion).
    VALIDATING → PROCESSING (validation passed) or REJECTED (validation failed).
    PROCESSING → EVALUATED (evaluation complete) or PENDING_EVIDENCE (insufficient data).
    PENDING_EVIDENCE → EVALUATED (evidence received) or CONFLICTED (contradictions).
    CONFLICTED → EVALUATED (conflict resolved with updated confidence).
    EVALUATED → DISTRIBUTED (feedback dispatched to recipients).
    DISTRIBUTED → ACKNOWLEDGED (all recipients confirmed) or CORRECTED (new evidence).
    CORRECTED → DISTRIBUTED (re-dispatch with updated evaluation).
    ACKNOWLEDGED → RESOLVED (lifecycle complete).
  
  Invalid transitions are logged and rejected.
  
  Output: State transition events recorded in feedback_lifecycle_records.

SERVICE 17: FEEDBACK HISTORY MANAGER
  Purpose: Maintains operational history for auditing, pattern analysis,
  and historical comparison.
  
  Algorithm — Tiered Retention:
  - Hot tier (in-memory LRU cache): Last 200 feedback records. O(1) access.
  - Warm tier (SQLite indexed): All records within retention window (configurable,
    default 90 days). O(log n) access via indexed queries.
  - Cold tier (SQLite archived): Records beyond retention window. Compressed
    summary retained; full detail available via explicit query.
  
  Aggregation support:
  - Performance metrics per engine, per activity type, per time period.
  - Running averages, success rates, failure rates.
  - Trend computation (moving average over configurable windows).
  
  Output: Historical query responses, aggregate statistics, trend data.

1. PERCEPTION ENGINE:
   Ingress: Input interpretation accuracy evidence, perception error reports.

   Contract: `ThoughtOutcomeSignal` — reasoning_quality, error_type, evidence.

4. EMOTION ENGINE:
   Ingress: Emotional regulation outcomes, emotional prediction accuracy.
   Egress: Emotional outcome feedback (how emotion-related decisions worked out).
   Contract: `EmotionalRegulationOutcome` — regulation_strategy, effectiveness.

5. MOTIVATION ENGINE:
   Ingress: Goal completion outcomes, motivation effectiveness signals.
   Egress: Goal-related outcome assessments.

6. LEARNING ENGINE (PRIMARY CONSUMER):
   Egress: `LearningFeedbackPackage` containing standardized `LearningContribution`

   Acknowledgement: Receives ACK from Learning Engine's FeedbackService.

7. PERSONALITY ENGINE:
   Ingress: Behavioral consistency evidence (Diva's behavior matched/deviated

8. SOCIAL COGNITION ENGINE:

   Egress: Social interaction quality assessments.

9. INTERNAL STATE ENGINE:

10. INTERACTION ENGINE:

11. AUTONOMOUS ACTIVITY ENGINE:

12. COGNITIVE INTEGRATION & DECISION ENGINE:

  - Feedback Engine NEVER modifies recipient engine parameters.

  - Dedup: Same (source_engine, source_event_id) processed only once.

PART 5 — MUST-PASS CONDITIONS (44 CHECKPOINTS) & HOW TO PASS EACH
================================================================================

1. FEEDBACK ACQUISITION (5 CHECKPOINTS)
[ ] FA01. Accept feedback from multiple internal and external sources.
  HOW: 6 source-type adapters in Normalizer, one per source category. Integration
  test sends signals from 5 different engines + 1 external user and verifies all
  are processed to FeedbackRecord with correct source_type.

[ ] FA02. Preserve source provenance.
  HOW: Every FeedbackRecord has FeedbackSource with provenance_chain. Unit test
  verifies chain non-empty and traceable to original event.

[ ] FA03. Handle incomplete and delayed feedback.
  HOW: Normalizer fills defaults and sets is_incomplete=True. Lifecycle Manager
  transitions to PENDING_EVIDENCE. Test: submit feedback missing expected_outcome;
  verify PENDING_EVIDENCE state; submit evidence later; verify EVALUATED transition.

[ ] FA04. Detect duplicate feedback.
  HOW: Bloom filter + UNIQUE(source_engine, source_event_id) constraint.
  Test: submit same signal twice; verify second marked is_duplicate=True and
  not re-evaluated.

[ ] FA05. Handle contradictory feedback.
  HOW: When two feedback records for same activity have opposite polarity,
  Lifecycle Manager transitions to CONFLICTED. Confidence Assessment reduces
  consistency_factor. Test: submit positive + negative for same activity_id;
  verify CONFLICTED state and reduced confidence.

2. OUTCOME EVALUATION (6 CHECKPOINTS)
[ ] OE01. Compare expected and actual outcomes.
  HOW: Outcome Evaluator takes (ExpectedOutcome, ActualOutcome) and produces
  OutcomeComparison with per-objective scores. Test: 3-objective scenario with
  2 met, 1 not met; verify PARTIAL_SUCCESS classification.

[ ] OE02. Support partial success.
  HOW: Per-objective ObjectiveResult with FULLY_MET/PARTIALLY_MET/NOT_MET.
  Aggregate formula produces $O_{aggregate} \in (0.50, 0.90)$ for partial.
  Test: verify aggregate correctly weights objectives by importance.

[ ] OE03. Evaluate quality independently of completion.
  HOW: Quality Assessment Module runs independently. A FULLY_MET objective can
  have $Q_{correct} = 0.60$ (poor quality but complete). Test: submit fully
  completed task with low quality indicators; verify SUCCESS classification
  AND low quality score coexist.

[ ] OE04. Evaluate efficiency independently of quality.
  HOW: $Q_{effic}$ computed separately from other quality dimensions. Test:
  high-quality result with 3x expected resource usage; verify high quality
  scores AND low efficiency score.

[ ] OE05. Support qualitative and quantitative evaluation.
  HOW: Numerical objectives use formula; qualitative use LLM similarity scoring.
  Test: mixed objective set with 1 numerical + 1 qualitative; verify both evaluated.

[ ] OE06. Preserve inconclusive outcomes.
  HOW: When evidence is insufficient for determination, OutcomeComparison
  sets overall_classification = INCONCLUSIVE. Lifecycle → PENDING_EVIDENCE.
  Test: submit feedback with no actual_outcome data; verify INCONCLUSIVE.

3. FAILURE ANALYSIS (6 CHECKPOINTS)
[ ] FL01. Distinguish observed failures from suspected causes.
  HOW: FailureRecord stores observation. FailureHypothesis stores suspected
  cause with cause_type and confidence. Test: timeout failure; verify
  FailureRecord (observed timeout) separate from FailureHypothesis (resource
  limitation, $C=0.70$).

[ ] FL02. Support multiple contributing causes.
  HOW: Multiple FailureHypothesis records per FailureRecord. Anti-blame
  safeguard caps single-node $Causal \le 0.80$ unless strong evidence.
  Test: complex failure; verify $\ge 2$ hypotheses generated.

[ ] FL03. Distinguish correlation from causation.
  HOW: CausalRelationship.relationship_type = CORRELATION_ONLY when
  $P_{dependency}=0$ AND $P_{counter}<0.50$. Test: two temporally close events
  with no dependency link; verify CORRELATION_ONLY tag.

[ ] FL04. Preserve uncertainty in causal explanations.
  HOW: FailureHypothesis.confidence reflects uncertainty. Multiple hypotheses
  preserved as ACTIVE when none has $C \ge 0.80$. Test: ambiguous failure;
  verify all hypotheses retained with $C < 0.80$.

[ ] FL05. Identify recurring failure patterns.
  HOW: Pattern Recognition cross-references failure_records. $\ge 3$ similar
  failures → FailurePattern. Test: submit 3 similar failures; verify pattern
  created with EMERGING status.

[ ] FL06. Track unexpected consequences.
  HOW: OutcomeComparison.unexpected_negatives populated when actual contains
  elements not in expected AND those elements have negative impact. Test:
  successful task that caused an unintended side effect; verify tracked.

4. EVIDENCE AND CONFIDENCE (5 CHECKPOINTS)
[ ] EC01. Assess evidence reliability.
  HOW: Confidence Assessment Module with multi-factor formula. Test: compare
  confidence of objective measurement vs. subjective user statement; verify
  objective scores higher on evidence_quality_factor.

[ ] EC02. Distinguish subjective and objective feedback.
  HOW: FeedbackEvidence.evidence_type distinguishes OBJECTIVE_MEASUREMENT
  from SUBJECTIVE_JUDGMENT. FeedbackConfidence separates these in its formula.
  Test: user says "wrong" but system measurement says "correct"; verify both
  preserved as separate evidence items.

[ ] EC03. Support conflicting evidence.
  HOW: CONFLICTED lifecycle state. Both evidence items retained with
  independent confidence. Test: contradictory assessments from two sources;
  verify both persisted, state = CONFLICTED, reduced overall confidence.

[ ] EC04. Preserve positive, negative and neutral feedback.
  HOW: FeedbackRecord.polarity supports all three + MIXED. Test: submit one
  of each; verify all stored with correct polarity tags.

[ ] EC05. Prevent unsupported conclusions from becoming established facts.
  HOW: Feedback with $C_{feedback} < 0.40$ is quarantined in LearningFeedbackPackage
  (is_quarantined=True). Pattern Recognition requires $\ge 3$ supporting
  instances. Test: single low-confidence failure; verify NOT promoted to pattern.

Each walkthrough contains the eight mandatory structural sections.

--------------------------------------------------------------------------------
SCENARIO 1: COMPLETELY SUCCESSFUL ACTIVITY
--------------------------------------------------------------------------------
1. Initial State: Diva completed a research task with 3 objectives. All met.
2. Trigger: Execution infrastructure dispatches ExecutionResult (exit_code=0).
3. Expected Subsystem Interactions:
   - Input Handler validates; Source Validator assigns $Rel_s = 0.90$.
   - Normalizer creates FeedbackRecord. Classifier assigns SUCCESS.
   - Outcome Evaluator: 3/3 objectives FULLY_MET; $O_{aggregate} = 0.95$.
   - Quality Assessment: $Q_{correct}=0.90, Q_{effic}=0.80$.
   - No failure analysis triggered.
   - Pattern Recognition: Increments success counter for research tasks.
   - Feedback Generator: Creates LearningFeedbackPackage with POSITIVE_EVIDENCE.
4. Expected State Transitions: RECEIVED → VALIDATING → PROCESSING → EVALUATED → DISTRIBUTED → ACKNOWLEDGED.
5. Expected Persistence Changes: INSERT into feedback_records, outcome_comparisons, quality_assessments, feedback_contributions, feedback_lifecycle_records.
6. Ownership-Boundary Checks: Feedback evaluates only. No parameter changes. Learning independently decides if the success reinforces any parameter.
7. Expected Result: SUCCESS classification with quality dimensions. Positive evidence dispatched to Learning. Pattern counter updated.
8. Failure Scenario: If Learning Engine ACK times out: Retry 3x. Mark delivery_status = FAILED. Feedback record preserved regardless.

--------------------------------------------------------------------------------
SCENARIO 2: COMPLETELY FAILED ACTIVITY
--------------------------------------------------------------------------------
1. Initial State: Task to generate 3 required features. None completed. Error: timeout.
2. Trigger: ExecutionResult with error_code = TIMEOUT.
3. Subsystem Interactions:
   - Classifier: FAILURE + EXECUTION categories.
   - Outcome Evaluator: 0/3 objectives; $O_{aggregate} = 0.0$; classification = FAILURE.
   - Failure Analysis: FailureRecord (TIMEOUT, severity=HIGH). Generates 2 hypotheses:
     H1: Resource limitation ($C=0.65$). H2: Task complexity exceeded estimate ($C=0.55$).
   - Causal Attribution: Collects preceding events. Identifies high workload during task.
4. State Transitions: → EVALUATED → DISTRIBUTED.
5. Persistence: INSERT failure_records, failure_hypotheses (2 rows), causal_relationships.
6. Ownership: Failure analysis identifies causes but does NOT fix them. Learning receives evidence.
7. Result: FAILURE with 2 failure hypotheses preserved. Neither is confirmed without more evidence.
8. Failure: If LLM hypothesis generation fails: Deterministic-only analysis. Record with fewer hypotheses.

--------------------------------------------------------------------------------
SCENARIO 3: PARTIALLY SUCCESSFUL ACTIVITY
--------------------------------------------------------------------------------
1. Initial State: 3 objectives; 2 fully met, 1 not met. 
2. Trigger: ExecutionResult with partial completion data.
3. Subsystem Interactions:
   - Outcome Evaluator: Obj1=FULLY_MET($w=0.4$), Obj2=FULLY_MET($w=0.3$), Obj3=NOT_MET($w=0.3$).
     $O = (0.4 \cdot 1.0 + 0.3 \cdot 1.0 + 0.3 \cdot 0.0) / 1.0 = 0.70$. PARTIAL_SUCCESS.
   - Quality Assessment: Completed objectives assessed independently for quality.
   - Failure Analysis: Activated for Obj3. Hypothesis: Insufficient information ($C=0.50$).
4. Result: PARTIAL_SUCCESS. Per-objective breakdown preserved. Failure analysis only on Obj3.

--------------------------------------------------------------------------------
SCENARIO 4: SUCCESSFUL BUT INEFFICIENT ACTIVITY
--------------------------------------------------------------------------------
1. Initial State: Task completed successfully. Used 3x expected resources.
2. Trigger: ExecutionResult with high resource_usage.
3. Subsystem Interactions:
   - Classifier: SUCCESS + EFFICIENCY categories.
   - Outcome Evaluator: $O_{aggregate} = 0.95$ (SUCCESS).
   - Quality Assessment: $Q_{effic} = \max(0, 1 - (3.0 - 1.0)/1.0) = 0.0$ (terrible efficiency).
     $Q_{correct} = 0.90$ (good correctness). These coexist.
   - Feedback Generator: Two separate contributions — positive for Learning
     (success evidence) AND efficiency concern for Internal State + Learning.
4. Result: SUCCESS classification but LOW efficiency. Both preserved independently.
   Not collapsed into a single middling score.

--------------------------------------------------------------------------------
SCENARIO 5: CONFLICTING USER AND SYSTEM FEEDBACK
--------------------------------------------------------------------------------

2. Trigger: Two feedback signals — ToolExecution (correct) + ExternalUser (incorrect).
3. Subsystem Interactions:

   - User satisfaction ($Q_{useful} = 0.20$) and factual accuracy ($Q_{correct} = 0.90$)
     preserved as INDEPENDENT dimensions. NOT averaged.
   - Lifecycle Manager: Marks as CONFLICTED until further evidence.
   - Both records dispatched to Learning with CONFLICTED flag.
4. Result: User dissatisfaction and system correctness coexist. Learning receives
   both; may investigate whether the answer was technically correct but poorly explained.

   - Pattern lifecycle: EMERGING (at $n=3$) → ESTABLISHED (now at $n=5, n_{total} \ge 8$ if including successes).
   - Feedback Generator: Creates LearningFeedbackPackage with pattern_evidence

   and may investigate whether a parameter change or capability development is warranted.
