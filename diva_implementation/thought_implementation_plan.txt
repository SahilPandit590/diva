A. CROSS-ENGINE INTERFACES AND OWNERSHIP
--------------------------------------------------------------------------------

A1. MEMORY ENGINE AS A FORMAL CONTEXTUAL PROVIDER (MemoryContextProvider)
Problem Addressed: Previous designs referenced memory in generation pathways without formalizing the boundary, data contracts, or ownership rules.
Architectural Specification:
The Thought Engine interfaces with the Memory Engine exclusively via the asynchronous, read-only `MemoryContextProvider` interface.
Methods Supported:
1. `retrieve_relevant_memories(query_vector, semantic_tags, max_records, min_relevance)`
2. `retrieve_memory_claims(entity_id, claim_predicate, temporal_range)`
3. `retrieve_associated_historical_thoughts(thread_topic, recency_decay, max_nodes)`
4. `retrieve_unresolved_questions(priority_threshold, max_questions)`

Structured Response Data Contract (`MemoryContextResponse`):
- `memory_id`: UUID string (Canonical Memory Engine identifier).
- `content`: Textual and semantic content of the retrieved memory.
- `source_reference`: Identifier and type of original origin (e.g., episode, perception, conversation).
- `confidence`: Float in [0.0, 1.0] (Evidence confidence certified by Memory Engine).
- `relevance_score`: Float in [0.0, 1.0] (Semantic similarity and contextual match score).
- `created_at`: ISO-8601 UTC timestamp of original memory inscription.
- `provenance`: Structured lineage dictionary detailing acquisition channel, verifications, and corroborations.

Strict Ownership Boundaries:
- Memory Engine exclusively decides what is stored, consolidated, indexed, decayed, and retrieved.
- Thought Engine consumes retrieved information solely as premise material or associative inspiration.
- Thought Engine has ZERO authority to modify, overwrite, re-score, or delete memory records.
- Inscriptions into memory follow the formal asynchronous nomination and archival protocol (see Section F).

A2. INPUT AND PERCEPTION AS FORMAL PROVIDERS (PerceptionContextProvider)
Problem Addressed: Perception appeared in thought generation pathways without explicit data contracts, causing ambiguous ingestion boundaries.
Architectural Specification:
The Thought Engine consumes environmental and external sensory inputs through the `PerceptionContextProvider`.
Interface Contract (`PerceptionContextEvent`):
- `event_id`: UUID string (Unique normalized observation event identifier).
- `event_timestamp`: ISO-8601 UTC timestamp of sensory occurrence.
- `modality`: Enum (TEXT, SPEECH, VISUAL_SCENE, ENVIRONMENTAL_STATE, USER_INTERACTION).
- `observation_summary`: High-level normalized semantic interpretation.
- `raw_percept_ref`: Optional reference ID to raw sensory buffer maintained in Perception Engine.
- `entity_references`: Tuple of canonical entity IDs identified in the observation.
- `confidence`: Float in [0.0, 1.0] (Perceptual classification confidence).
- `uncertainty_profile`: Detailed error bounds and ambiguous classification hypotheses.
- `perceptual_urgency`: Float in [0.0, 1.0] (Urgency score computed by Perception Engine).
- `perceptual_salience`: Float in [0.0, 1.0] (Novelty and environmental contrast score).

Strict Ownership Boundaries:
- Perception Engine interprets, filters, grounds, and normalizes sensory input.
- Thought Engine reasons about the resulting structured observations and their cognitive implications.
- Thought Engine cannot manipulate sensory thresholds, sensor buffers, or feature detectors.

A3. FORMAL LEARNING ENGINE INTEGRATION (LearningSignal Contract)
Problem Addressed: Self-reflective thoughts claimed to inform learning without an interface contract, risking self-fulfilling or unverified epistemic contamination.
Architectural Specification:
The Thought Engine outputs reflective and evaluative observations to the Learning Engine using the immutable `LearningSignal` contract.

`LearningSignal` Schema:
- `signal_id`: UUID string (Unique learning signal identifier).
- `source_thought_ids`: Tuple of UUID strings (Thoughts responsible for generating the observation).
- `source_thread_id`: UUID string (Canonical thread where the observation crystallized).
- `signal_type`: Enum with strict values:
  * `REASONING_ERROR`: Detected logical contradiction, flawed deduction, or invalid inference.
  * `SUCCESSFUL_REASONING_PATTERN`: Efficient heuristic, high-utility analogical bridge, or validated deduction.
  * `RECURRING_COGNITIVE_PATTERN`: Persistent bias, recurring query loop, or habitual retrieval sequence.
  * `SELF_REFLECTION`: Meta-cognitive insight into cognitive speed, uncertainty estimation, or knowledge gaps.
  * `CAPABILITY_OBSERVATION`: Discovered reasoning limitation, missing domain skill, or operator latency bottleneck.
  * `PREDICTION_OUTCOME`: Evaluated prediction comparing anticipated consequence against observed reality.
- `observation`: Concrete, structured description of the cognitive event.
- `supporting_evidence`: Tuple of `EvidenceReference` records documenting premises and outcomes.
- `confidence`: Float in [0.0, 1.0] (Confidence of the self-reflective assessment).
- `provenance`: Full derivation chain linking the signal to source premises and operators.
- `created_at`: ISO-8601 UTC timestamp.

Independent Assessment Mandate:
- A Thought Engine signal asserting a mistake does NOT constitute proof of an error.
- The Learning Engine independently evaluates the signal against external outcomes, objective truth records, and historical baselines before admitting it into the epistemic contribution ledger.
- Thought Engine cannot directly mutate parameters, capabilities, or behavioral policies.

A4. SUBSYSTEM TOPOLOGY & EVENT-DRIVEN COOPERATION MODEL
Problem Addressed: The eight subsystems were previously depicted as a rigid linear pipeline, misrepresenting their asynchronous, reactive nature.
Architectural Specification:
The Thought Engine is organized as an event-driven cooperation network. Subsystems interact via internal message dispatch, asynchronous event buses, and shared transactional state:

1. Scheduler & Resource Governance: Central coordinator managing execution cycles, energy throttling, and quotas.
2. Attention & Priority Arbitrator: Reactive evaluation module calculating thread dynamic priority and preemption signals.
3. Thought Generation Subsystem: Event-triggered ingress translating internal/external impulses into candidate thoughts.
4. Thought Development & Reasoning Subsystem: Core reasoning worker executing reasoning operators and DAG expansions.
5. Thought Thread & DAG Manager: Graph authority enforcing acyclicity, edge typing, branching, merging, and thread boundaries.
6. Association & Graph Engine: Background exploration engine identifying cross-thread links, analogies, and semantic clustering.
7. Lifecycle & Checkpoint Manager: Transaction observer recording state transitions, maintaining audit logs, and managing snapshots.
8. Thought Retrieval Interface: Query service supporting continuation, recall, and context re-hydration.

Topology Interaction Matrix:
- Scheduler triggers Thought Generation upon environmental events, timers, or unresolved question thresholds.
- Generation emits candidate thoughts -> Thread & DAG Manager admits nodes to active threads.
- Attention Arbitrator continuously monitors active threads, ranking them into 1 Focal Thread and up to N Background Threads.
- Scheduler dispatches Focal and Background Reasoning Jobs to Thought Development & Reasoning.
- Thought Development expands DAGs, updates premises, checks hypotheses, and emits events to Lifecycle Manager.
- Association & Graph Engine continuously sweeps active DAGs in low-priority background cycles.
- Lifecycle Manager writes append-only event logs to the SQLite persistence store.

A5. MULTI-ORIGIN PROVENANCE FOR THOUGHTS
Problem Addressed: Previous models assumed a single origin reference per thought, preventing the valid representation of blended cognitive triggers.
Architectural Specification:
Every thought instance records a primary origin and a complete tuple of contributing derivations.

`ThoughtDerivation` Schema:
- `derivation_id`: UUID string.
- `source_type`: Enum (MEMORY_ACTIVATION, PERCEPTUAL_INPUT, EMOTIONAL_SPIKE, MOTIVATIONAL_GOAL, COUNTERFACTUAL_PROJECTION, SPONTANEOUS_ASSOCIATION, META_COGNITIVE_RECURSION, HYPOTHESIS_DEDUCTION).
- `source_id`: UUID or URI identifying the specific originating object (memory_id, percept_id, emotion_vector_id, etc.).
- `source_engine`: Enum (MEMORY, PERCEPTION, EMOTION, MOTIVATION, THOUGHT_INTERNAL, COGNITIVE_INTEGRATION).
- `contribution_role`: Enum (PRIMARY_TRIGGER, CONTEXTUAL_CATALYST, PREMISE_FOUNDATION, EMOTIONAL_WEIGHT, INHIBITORY_CONSTRAINT).
- `evidence_reference`: Optional `EvidenceReference` linking to verified underlying data.
- `timestamp`: ISO-8601 UTC timestamp.
- `is_quarantined`: Boolean indicating whether this originating element carries a quarantine flag.

`ThoughtInstance` Provenance Fields:
- `primary_origin_id`: UUID string pointing to the dominant `ThoughtDerivation`.
- `derivation_records`: Immutable Tuple of `ThoughtDerivation` objects capturing all contributory sources.
- Invariant: If ANY derivation record has `is_quarantined == True`, the thought instance automatically inherits `is_quarantined = True`.

B. THREAD, CHAIN, AND THOUGHT LIFECYCLE CORRECTIONS
--------------------------------------------------------------------------------

B1. SEPARATION OF THREAD LIFECYCLE FROM SCHEDULING EXECUTION MODE
Problem Addressed: The `ACTIVE` thread state conflated lifecycle readiness with actual execution allocation, creating contradictions when managing multiple concurrent background threads alongside a single focal thread.
Architectural Specification:
The lifecycle status of a thread is strictly decoupled from its scheduling dispatch mode.

`ThoughtThreadState` (Lifecycle Domain):
- `INITIALIZING`: Thread structure and root thought are being assembled; not ready for execution.
- `ACTIVE`: Thread is epistemically valid, open for expansion, and eligible for scheduler dispatch.
- `SUSPENDED`: Thread is paused (preempted, yielding, or waiting on external information); state preserved in SQLite.
- `SUSPENDED_RUMINATION`: Thread is quarantined due to detected cyclic reasoning or sterile repetition.
- `ABANDONED`: Thread reached a dead-end, exceeded resource bounds, or was discarded; terminal state.
- `CONCLUDED`: Thread successfully resolved its governing query or produced an accepted output; terminal state.

`ThreadExecutionMode` (Scheduling Domain):
- `FOCAL`: Receiving the primary, dedicated processing cycle (Strict Invariant: Exactly 0 or 1 thread across the entire engine).
- `BACKGROUND`: Receiving secondary, asynchronous batch or heuristic processing (Constrained by background job quota, default max 2).
- `NOT_SCHEDULED`: Lifecycle is `ACTIVE` or `SUSPENDED`, but thread is currently idle in the queue.
- `BLOCKED`: Thread is waiting on an outstanding asynchronous provider request (e.g., Memory retrieval).
- `TERMINATED`: Thread lifecycle is `ABANDONED` or `CONCLUDED`; never scheduled again.

Valid State/Mode Alignment Matrix:
* `INITIALIZING` -> only `NOT_SCHEDULED`.
* `ACTIVE` -> `FOCAL`, `BACKGROUND`, `NOT_SCHEDULED`, or `BLOCKED`.
* `SUSPENDED` -> `NOT_SCHEDULED` or `BLOCKED` (Never `FOCAL` or `BACKGROUND`).
* `SUSPENDED_RUMINATION` -> `NOT_SCHEDULED`.
* `ABANDONED` / `CONCLUDED` -> only `TERMINATED`.

B2. DEFINITION & RELATIONSHIP OF THOUGHTS, DAGS, AND CHAINS
Problem Addressed: Inconsistent use of "chain" and "DAG" led to ambiguous ownership and graph structural violations.
Architectural Specification:
The Thought Engine establishes three distinct, strictly typed concepts:

1. Thought (`ThoughtInstance`):
   A discrete cognitive unit containing a proposition, premise references, epistemic status, confidence score, and scratchpad context. A thought belongs to exactly ONE canonical owning thread (`thread_id`).
2. Thought DAG (`ThoughtDAG`):
   The canonical, complete directed acyclic graph of derivation and dependency between thoughts. Managed strictly within a thread. Directed edges point from parent (premise) to child (conclusion). Cycles are mathematically prohibited.
3. Thought Chain (`ThoughtChain`):
   A linear, ordered sequence of thought IDs representing a specific line of reasoning through the DAG. A chain does NOT own nodes exclusively. A single thought may participate in multiple chains (e.g., in a branch-and-merge scenario).

Chain Representation & Non-Owning References:
Chains are stored as distinct entities with an ordered list of thought identifiers:
`chain_memberships: Tuple[ChainMembership, ...]`
Where `ChainMembership` contains:
- `chain_id`: UUID string.
- `sequence_index`: Integer ordinal indicating position within this specific reasoning path.
- `joined_at`: ISO-8601 UTC timestamp.
- `role`: Enum (CHAIN_ROOT, INTERMEDIATE_STEP, HYPOTHESIS_BRANCH, SYNTHESIS_JUNCTION, TERMINAL_CONCLUSION).

B3. COMPLETE LIFECYCLE STATE TRANSITION MATRICES

Thought State Transition Matrix:
The state of an individual `ThoughtInstance` follows a strict state machine:
-------------------------------------------------------------------------------------------------------------
Current State | Event / Trigger                  | Next State  | Invariant / Guard Condition
-------------------------------------------------------------------------------------------------------------
GENERATED     | Context binding initiated        | EVALUATING  | Premises verified; origins attached
GENERATED     | Syntax / validation failure      | DISCARDED   | Malformed proposition or missing origin
EVALUATING    | Epistemic check passed           | ACTIVE      | Confidence calibrated; no fatal contradiction
EVALUATING    | Contradiction / premise invalid  | DISCARDED   | Failed epistemic baseline
ACTIVE        | Bound to logical reasoning chain | CHAINED     | Chain membership record registered
ACTIVE        | Reasoning concludes directly     | COMPLETED   | Terminal node for this derivation step
ACTIVE        | Invalidation during expansion    | DISCARDED   | Premise retracted or quarantined
CHAINED       | Reasoning finalized in chain     | COMPLETED   | Output synthesized or goal satisfied
CHAINED       | Superseded / invalidated         | DISCARDED   | Replaced by stronger alternative
COMPLETED     | (Terminal)                       | None        | Immutable; new developments create new node
DISCARDED     | (Terminal)                       | None        | Immutable; preserved in audit log only
-------------------------------------------------------------------------------------------------------------

Thread State Transition Matrix:
-------------------------------------------------------------------------------------------------------------
Current State        | Event / Trigger               | Next State          | Guard Condition
-------------------------------------------------------------------------------------------------------------
INITIALIZING         | Root thought accepted         | ACTIVE              | Root thought in ACTIVE or CHAINED
INITIALIZING         | Initialization failure        | ABANDONED           | Failed to establish root thought
ACTIVE               | Higher priority thread preempt| SUSPENDED           | Context snapshot committed to SQLite
ACTIVE               | Rumination loop detected      | SUSPENDED_RUMINATION| Cyclic / sterile metric exceeded
ACTIVE               | Goal achieved / output ready  | CONCLUDED           | Terminal thought reached
ACTIVE               | Depth / resource limit reached| ABANDONED           | Quota overflow policy = ABANDON
SUSPENDED            | Scheduler selects from queue  | ACTIVE              | Freshness validated; context restored
SUSPENDED            | Expiration / memory eviction  | ABANDONED           | Max queue dwell time exceeded
SUSPENDED_RUMINATION | Novel external evidence arrived| ACTIVE            | New evidence breaks repetition
SUSPENDED_RUMINATION | Background cleanup timeout    | ABANDONED           | Unresolved rumination expired
CONCLUDED            | (Terminal)                    | None                | Immutable; referenceable read-only
ABANDONED            | (Terminal)                    | None                | Immutable; never resurrected
-------------------------------------------------------------------------------------------------------------

B4. DECOUPLING CHAIN MEMBERSHIP FROM THOUGHT LIFECYCLE
Problem Addressed: The `CHAINED` thought state previously implied a structural location rather than an epistemic stage.
Architectural Specification:
While `CHAINED` is retained for backward compatibility in the transition table, it is semantically defined as an operational state indicating:
1. The thought's premise dependencies are locked and frozen against dynamic mutation.
2. The thought is registered in `chain_memberships` for one or more active reasoning chains.
3. It may serve as a verified premise for downstream deductive or inductive operator jobs.
A thought can advance to `COMPLETED` while retaining its full membership across multiple chains.

B5. THREAD RECONSIDERATION PROTOCOL & HISTORICAL IMMUTABILITY
Problem Addressed: Re-opening abandoned threads risked mutating historical reasoning trails and violating audit invariants.
Architectural Specification:
An `ABANDONED` thread is strictly immutable and can never transition back to `ACTIVE`.
When new evidence, perceptions, or goals warrant re-evaluating an abandoned line of inquiry, the Thought Engine creates a NEW `ThoughtThread` through the Reconsideration Protocol:

`ThoughtReconsiderationRecord`:
- `reconsideration_id`: UUID string.
- `new_thread_id`: UUID string of the newly created thread.
- `reconsidered_from_thread_id`: UUID string of the historical abandoned thread.
- `reconsideration_reason`: Textual justification for reopening the inquiry.
- `triggering_evidence_ids`: Tuple of UUID strings pointing to novel evidence that invalidates previous abandonment.
- `reconsidered_at`: ISO-8601 UTC timestamp.

Operational Rules:
- The historical thread remains intact in `ABANDONED` status with its original execution logs.
- The new thread initializes with a root thought derived from the historical thread's premises plus the triggering evidence.
- The new thread records `reconsidered_from_thread_id` in its header, maintaining transparent cognitive lineage.

C. PERSISTENCE AND CRASH RECOVERY

C1. COMPLETE 15-TABLE SQLITE RELATIONAL SCHEMA
Problem Addressed: The previous specification lacked a comprehensive relational DDL covering all working-state structures.
Architectural Specification:
The working state of the Thought Engine is persisted in an embedded SQLite database operating in WAL (Write-Ahead Logging) mode. All 15 required tables are explicitly defined below:

```sql
-- 1. Thread Metadata & State
CREATE TABLE thought_threads (
    thread_id TEXT PRIMARY KEY,
    topic TEXT NOT NULL,
    state TEXT NOT NULL CHECK (state IN ('INITIALIZING', 'ACTIVE', 'SUSPENDED', 'SUSPENDED_RUMINATION', 'ABANDONED', 'CONCLUDED')),
    execution_mode TEXT NOT NULL CHECK (execution_mode IN ('FOCAL', 'BACKGROUND', 'NOT_SCHEDULED', 'BLOCKED', 'TERMINATED')),
    dynamic_priority REAL NOT NULL,
    current_dag_depth INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    reconsidered_from_thread_id TEXT,
    FOREIGN KEY (reconsidered_from_thread_id) REFERENCES thought_threads(thread_id) ON DELETE RESTRICT
);

-- 2. Individual Thought Nodes
CREATE TABLE thought_instances (
    thought_id TEXT PRIMARY KEY,
    thread_id TEXT NOT NULL,
    content TEXT NOT NULL,
    state TEXT NOT NULL CHECK (state IN ('GENERATED', 'EVALUATING', 'ACTIVE', 'CHAINED', 'COMPLETED', 'DISCARDED')),
    epistemic_status TEXT NOT NULL CHECK (epistemic_status IN ('ESTABLISHED', 'WORKING_HYPOTHESIS', 'SPECULATIVE', 'COUNTERFACTUAL', 'FALSIFIED')),
    confidence REAL NOT NULL CHECK (confidence >= 0.0 AND confidence <= 1.0),
    is_quarantined INTEGER NOT NULL CHECK (is_quarantined IN (0, 1)),
    primary_origin_id TEXT NOT NULL,
    sequence_index INTEGER NOT NULL,
    created_at TEXT NOT NULL,
    completed_at TEXT,
    FOREIGN KEY (thread_id) REFERENCES thought_threads(thread_id) ON DELETE RESTRICT
);

-- 3. Logical Reasoning Chains
CREATE TABLE thought_chains (
    chain_id TEXT PRIMARY KEY,
    thread_id TEXT NOT NULL,
    name TEXT NOT NULL,
    created_at TEXT NOT NULL,
    concluded_at TEXT,
    FOREIGN KEY (thread_id) REFERENCES thought_threads(thread_id) ON DELETE RESTRICT
);

-- 4. Canonical Thought DAG Edges
CREATE TABLE thought_dag_edges (
    edge_id TEXT PRIMARY KEY,
    thread_id TEXT NOT NULL,
    parent_thought_id TEXT NOT NULL,
    child_thought_id TEXT NOT NULL,
    relationship_type TEXT NOT NULL CHECK (relationship_type IN ('DEDUCTIVE_DERIVATION', 'INDUCTIVE_SUPPORT', 'ABDUCTIVE_EXPLANATION', 'CAUSAL_DEPENDENCY', 'ANALOGICAL_INFERENCE', 'COUNTERFACTUAL_BRANCH', 'SYNTHESIS_JUNCTION')),
    created_at TEXT NOT NULL,
    FOREIGN KEY (thread_id) REFERENCES thought_threads(thread_id) ON DELETE RESTRICT,
    FOREIGN KEY (parent_thought_id) REFERENCES thought_instances(thought_id) ON DELETE RESTRICT,
    FOREIGN KEY (child_thought_id) REFERENCES thought_instances(thought_id) ON DELETE RESTRICT,
    UNIQUE(parent_thought_id, child_thought_id)
);

-- 5. Semantic & Associative Graph Edges
CREATE TABLE thought_associations (
    association_id TEXT PRIMARY KEY,
    source_thought_id TEXT NOT NULL,
    target_thought_id TEXT NOT NULL,
    association_type TEXT NOT NULL CHECK (association_type IN ('SEMANTIC_SIMILARITY', 'CONTRAST_OPPOSITION', 'TEMPORAL_CO_OCCURRENCE', 'DOMAIN_ANALOGY')),
    strength REAL NOT NULL CHECK (strength >= 0.0 AND strength <= 1.0),
    created_at TEXT NOT NULL,
    FOREIGN KEY (source_thought_id) REFERENCES thought_instances(thought_id) ON DELETE RESTRICT,
    FOREIGN KEY (target_thought_id) REFERENCES thought_instances(thought_id) ON DELETE RESTRICT
);

-- 6. Thought Origin & Multi-Source Derivations
CREATE TABLE thought_origins (
    derivation_id TEXT PRIMARY KEY,
    thought_id TEXT NOT NULL,
    source_type TEXT NOT NULL,
    source_id TEXT NOT NULL,
    source_engine TEXT NOT NULL,
    contribution_role TEXT NOT NULL,
    is_quarantined INTEGER NOT NULL CHECK (is_quarantined IN (0, 1)),
    created_at TEXT NOT NULL,
    FOREIGN KEY (thought_id) REFERENCES thought_instances(thought_id) ON DELETE RESTRICT
);

-- 7. Working Context & Typed Scratchpad
CREATE TABLE thought_contexts (
    context_id TEXT PRIMARY KEY,
    thread_id TEXT NOT NULL UNIQUE,
    active_premises_json TEXT NOT NULL,
    scratchpad_variables_json TEXT NOT NULL,
    scratchpad_bytes INTEGER NOT NULL CHECK (scratchpad_bytes <= 65536),
    updated_at TEXT NOT NULL,
    FOREIGN KEY (thread_id) REFERENCES thought_threads(thread_id) ON DELETE RESTRICT
);

-- 8. Hypothesis Management & Probabilities
CREATE TABLE thought_hypotheses (
    hypothesis_id TEXT PRIMARY KEY,
    thought_id TEXT NOT NULL UNIQUE,
    thread_id TEXT NOT NULL,
    proposition TEXT NOT NULL,
    prior_probability REAL NOT NULL CHECK (prior_probability >= 0.0 AND prior_probability <= 1.0),
    current_probability REAL NOT NULL CHECK (current_probability >= 0.0 AND current_probability <= 1.0),
    relationship_type TEXT NOT NULL CHECK (relationship_type IN ('MUTUALLY_EXCLUSIVE', 'COMPETING_BUT_NOT_EXHAUSTIVE', 'INDEPENDENT', 'UNKNOWN_RELATIONSHIP')),
    competing_group_id TEXT,
    updated_at TEXT NOT NULL,
    FOREIGN KEY (thought_id) REFERENCES thought_instances(thought_id) ON DELETE RESTRICT,
    FOREIGN KEY (thread_id) REFERENCES thought_threads(thread_id) ON DELETE RESTRICT
);

-- 9. Priority Calculations & Input Snapshots
CREATE TABLE thought_priorities (
    priority_id TEXT PRIMARY KEY,
    thread_id TEXT NOT NULL,
    urgency REAL NOT NULL,
    importance REAL NOT NULL,
    emotional_relevance REAL NOT NULL,
    motivational_alignment REAL NOT NULL,
    unresolved_entropy REAL NOT NULL,
    starvation_boost REAL NOT NULL DEFAULT 0.0,
    final_score REAL NOT NULL CHECK (final_score >= 0.0 AND final_score <= 1.0),
    calculated_at TEXT NOT NULL,
    FOREIGN KEY (thread_id) REFERENCES thought_threads(thread_id) ON DELETE RESTRICT
);

-- 10. Scheduler Pending Queue
CREATE TABLE thought_pending_queue (
    queue_entry_id TEXT PRIMARY KEY,
    thread_id TEXT NOT NULL UNIQUE,
    enqueued_at TEXT NOT NULL,
    scheduling_tier TEXT NOT NULL CHECK (scheduling_tier IN ('FOCAL_CANDIDATE', 'BACKGROUND_ELIGIBLE', 'RUMINATION_HOLD')),
    FOREIGN KEY (thread_id) REFERENCES thought_threads(thread_id) ON DELETE RESTRICT
);

-- 11. Immutable Lifecycle Transition Event Log
CREATE TABLE thought_lifecycle_events (
    event_id TEXT PRIMARY KEY,
    entity_type TEXT NOT NULL CHECK (entity_type IN ('THREAD', 'THOUGHT', 'REASONING_JOB')),
    entity_id TEXT NOT NULL,
    previous_state TEXT,
    new_state TEXT NOT NULL,
    transition_reason TEXT NOT NULL,
    timestamp TEXT NOT NULL
);

-- 12. Local Archival Protocol State
CREATE TABLE thought_archival_records (
    nomination_id TEXT PRIMARY KEY,
    thought_id TEXT NOT NULL,
    status TEXT NOT NULL CHECK (status IN ('PENDING_DISPATCH', 'DISPATCHED', 'ACCEPTED', 'REJECTED_POLICY', 'REJECTED_DUPLICATE', 'REJECTED_INSUFFICIENT_EVIDENCE', 'TEMPORARY_FAILURE')),
    idempotency_key TEXT NOT NULL UNIQUE,
    memory_record_id TEXT,
    retry_count INTEGER NOT NULL DEFAULT 0,
    last_attempt_at TEXT NOT NULL,
    FOREIGN KEY (thought_id) REFERENCES thought_instances(thought_id) ON DELETE RESTRICT
);

-- 13. Asynchronous Reasoning Jobs
CREATE TABLE thought_reasoning_jobs (
    job_id TEXT PRIMARY KEY,
    thread_id TEXT NOT NULL,
    operator_type TEXT NOT NULL,
```

C2. MANDATORY SQLITE FOREIGN-KEY ENFORCEMENT & RETENTION RULES
Architectural Invariant:
SQLite does NOT enforce foreign keys by default. On every database connection initialization, the storage driver MUST execute:
`PRAGMA foreign_keys = ON;`
A connection verification check asserts `PRAGMA foreign_keys;` returns `1`. If foreign keys are disabled, the storage connection raises a fatal initialization exception.

Retention and Referential Integrity Policies:
- ALL relational constraints utilize `ON DELETE RESTRICT`. Under NO circumstances are historical thought instances, lifecycle logs, or derivation edges cascade-deleted.
- Thread conclusion or abandonment simply updates the state column; the entire relational graph remains permanently queryable for audit, reflection, and learning signals.

C3. ATOMIC LOGICAL OPERATIONS & TRANSACTION BOUNDARIES
Problem Addressed: Multi-table updates executed without strict transaction boundaries risk leaving broken DAGs or orphaned records during crashes.
Architectural Specification:
Every high-level cognitive operation is encapsulated in a single, atomic SQLite transaction (`BEGIN IMMEDIATE ... COMMIT`).

Atomic Operation Specifications:
1. `create_thought_transaction(thought, derivations, dag_edges, chain_membership)`:
   Step 1: Insert row into `thought_instances`.
   Step 2: Insert rows into `thought_origins` for each derivation record.
   Step 3: Insert rows into `thought_dag_edges` for premise connections.
   Step 4: Update owning row in `thought_threads` (`updated_at`, `current_dag_depth`).
   Step 5: If chain attached, insert into `thought_chains` / update chain metadata.
   Step 6: Insert row into `thought_lifecycle_events` with transition reason.
   Step 7: COMMIT. (On any exception: full ROLLBACK).

2. `branch_thread_transaction(parent_thread_id, new_thread, root_thought, branching_edges)`:
   Step 1: Insert row into `thought_threads` for `new_thread` (`INITIALIZING`).
   Step 2: Snapshot parent context into `thought_contexts` for `new_thread`.
   Step 3: Execute `create_thought_transaction` for `root_thought`.
   Step 4: Insert cross-thread derivation records in `thought_origins`.
   Step 5: Transition `new_thread` to `ACTIVE`.
   Step 6: Record branch event in `thought_lifecycle_events`.
   Step 7: COMMIT.

C4. 11-STEP DETERMINISTIC CRASH RECOVERY PROTOCOL
Problem Addressed: Previous recovery implementations only flipped active threads to suspended, failing to reconcile pending jobs, queues, or half-finished transitions.
Architectural Specification:
Upon engine startup after an ungraceful shutdown, crash, or power loss, the `ThoughtLifecycleManager` executes the following 11-step idempotent recovery sequence:

Step 1: Acquire exclusive SQLite file lock and recovery coordination mutex.
Step 2: Check WAL integrity and replay any uncommitted write-ahead logs to disk.
Step 3: Generate a unique, idempotent `recovery_session_id` (UUID) and record startup in audit log.
Step 4: Query `thought_reasoning_jobs` for any records in `RUNNING` or `DISPATCHED` state.
Step 5: Mark all such jobs as `INTERRUPTED`; record failure metadata indicating crash abort.
Step 6: Query `thought_instances` for any thoughts stuck in `GENERATED` or `EVALUATING` state. Transition them to `DISCARDED` with reason `"CRASH_DURING_EVALUATION"`.
Step 7: Verify all DAG edge invariants (`PRAGMA integrity_check`, cycle detection, missing foreign keys).
Step 8: Identify any thread in `thought_threads` with `state == 'ACTIVE'`.
        - Set `state = 'SUSPENDED'`.
        - Set `execution_mode = 'NOT_SCHEDULED'`.
        - Insert transition record in `thought_lifecycle_events`.
Step 9: Rebuild `thought_pending_queue`: Inspect all `SUSPENDED` threads, recalculate priorities, and populate the queue.
Step 10: Re-validate `thought_archival_records`: Any record in `DISPATCHED` is reset to `PENDING_DISPATCH` for idempotent retry.
Step 11: Release recovery coordination lock; emit `ENGINE_RECOVERY_COMPLETE` signal to system coordinator.

C5. CRASH RECOVERY CONSISTENCY TEST SUITE (9 SCENARIOS)
The test suite validates recovery invariants against 9 simulated crash injections:
1. Crash Before Transaction Commit: Process terminated mid-execution; verify zero partial rows in `thought_instances` or `thought_dag_edges`.
2. Crash During Transaction Commit: Simulated disk stall during WAL flush; verify SQLite automatic rollback to last consistent state.
3. Crash Immediately After Commit: Process killed before in-memory cache update; verify persistent SQLite state is authoritative upon reload.
4. Crash During Thought Creation: Power failure during step 3 of `create_thought_transaction`; verify complete atomicity (no orphaned origins).
5. Crash During DAG Edge Insertion: Insertion interrupted; verify no dangling parent/child relationships.
6. Crash During Thread Suspension: Process killed during focal preemption; verify thread recovers into `SUSPENDED` without corrupted context.
7. Crash During Archival Acknowledgement: Network drops while Memory Engine processes nomination; verify idempotent retry using stored key.
8. Crash During Model Execution: Sub-process / LLM crashes while reasoning job is active; verify job recovers as `INTERRUPTED` without corrupting thread.
9. Repeated Recovery Attempts: Crash recovery executed 5 consecutive times on identical database; verify identical, idempotent outcome.

D. REASONING AND EPISTEMIC INTEGRITY
--------------------------------------------------------------------------------

D1. SEVEN FORMAL REASONING OPERATORS SPECIFICATION
The Thought Development & Reasoning subsystem executes inferences using seven formal, typed operators. Each operator defines its inputs, responsibilities, outputs, evidence constraints, failure criteria, and validity checks:

1. Deductive Reasoning Operator:
   - Inputs: Set of established premise thoughts ($P_1, P_2, \dots, P_k$), deductive inference rule (Modus Ponens, Modus Tollens, Disjunctive Syllogism).
   - Responsibility: Derives logically necessary consequences from valid premises.
   - Output: New `ThoughtInstance` with logical conclusion, edge type `DEDUCTIVE_DERIVATION`.
   - Evidence Requirements: All premise thoughts must have `epistemic_status == 'ESTABLISHED'` or valid active hypothesis bounds.
   - Failure Conditions: Premise contradiction, invalid rule application, missing premise truth values.
   - Validity Assessment: Pure deductive validity. If premises are true and rule is sound, output confidence = $\min(C(P_1), \dots, C(P_k))$.

2. Inductive Reasoning Operator:
   - Inputs: Tuple of observed instance thoughts ($O_1, O_2, \dots, O_n$), generalization target domain.
   - Responsibility: Formulates generalized principles or regularities from specific recurring observations.
   - Output: New `ThoughtInstance` with generalized proposition, edge type `INDUCTIVE_SUPPORT`.
   - Evidence Requirements: Sample size $n \ge 3$ independent observations from verified perception or memory.
   - Failure Conditions: Counter-examples detected in memory, sample diversity collapse, extreme variance.
   - Validity Assessment: Statistical support metric. Confidence scaled by sample size, regularity, and domain variability; strictly $< 0.85$ unless independently verified.

3. Abductive Reasoning Operator:
   - Inputs: Observed anomalous or salient event thought ($E$), background knowledge base context.
   - Responsibility: Generates best plausible explanatory hypotheses ($H_1, H_2, \dots, H_m$) that would account for $E$.
   - Output: One or more `ThoughtHypothesis` records, edge type `ABDUCTIVE_EXPLANATION`.
   - Evidence Requirements: Explicit observation reference, non-empty candidate explanatory domain.
   - Failure Conditions: Tautological explanation, no plausible causal link, explanation contradicts established ground truth.
   - Validity Assessment: Explanatory parsimony, prior plausibility, explanatory scope.

4. Causal Reasoning Operator:
   - Inputs: Temporal sequence thoughts, observed intervention thoughts, candidate mechanism models.
   - Responsibility: Evaluates cause-and-effect relationships, distinguishing true causality from mere correlation.
   - Output: New `ThoughtInstance` specifying causal link (Cause, Effect, Mechanism, Strength), edge type `CAUSAL_DEPENDENCY`.
   - Evidence Requirements: Temporal precedence ($T_{cause} < T_{effect}$), non-spuriousness check, mechanistic plausibility.
   - Failure Conditions: Reverse temporal order, presence of common confounding factor in memory, zero mechanistic bridge.
   - Validity Assessment: Verification against causal graph invariants; sensitivity analysis under counterfactual interventions.

5. Analogical Reasoning Operator:
   - Inputs: Source domain schema thought ($S$), target domain context thought ($T$).
   - Responsibility: Maps structural relations from known source domain onto novel or unresolved target domain.
   - Output: New `ThoughtInstance` proposing candidate target properties/solutions, edge type `ANALOGICAL_INFERENCE`.
   - Evidence Requirements: Structural mapping score $\ge 0.60$ across relational predicates (not mere surface feature similarity).
   - Failure Conditions: Superficial semantic match with mismatched relational deep structure, breakdown of core invariants.
   - Validity Assessment: Systematicity metric; confidence capped at 0.70 until empirically tested in target domain.

6. Counterfactual Reasoning Operator:
   - Inputs: Historical event thought ($A$), counterfactual premise thought ("If $A'$ had occurred instead of $A$"), causal model.
   - Responsibility: Explores alternative hypothetical trajectories and evaluates causal necessity.
   - Output: New `ThoughtInstance` with `epistemic_status = 'COUNTERFACTUAL'`, edge type `COUNTERFACTUAL_BRANCH`.
   - Evidence Requirements: Valid historical factual anchor, explicit mutable antecedent.
   - Failure Conditions: Antecedent impossible under physical constraints, unconstrained butterfly divergence.
   - Validity Assessment: Closest-possible-world metric. STRICT QUARANTINE MANDATE: All outputs flagged `is_quarantined = 1`.

7. Evaluative / Critical Reasoning Operator:
   - Inputs: Candidate argument DAG, proposition thought, alternative hypotheses, counter-evidence pool.
   - Responsibility: Rigorously critiques reasoning chains, identifies hidden assumptions, evaluates evidence quality, and checks consistency.
   - Output: Evaluative report thought containing detected flaws, contradiction scores, and recalibrated confidences.
   - Evidence Requirements: Full visibility into upstream premise derivations and evidence provenance.
   - Failure Conditions: Self-referential circular evaluation (evaluating an operator with itself without external anchor).
   - Validity Assessment: Objective checklist: fallacy detection, bias detection, contradiction verification.

D2. EVIDENCE PROVENANCE & LINEAGE DEPENDENCY TRACKING
Problem Addressed: Unioning evidence IDs without tracking provenance allowed correlated or duplicate underlying sources to artificially inflate confidence.
Architectural Specification:
The Thought Engine models evidence using the rich `EvidenceReference` contract:

`EvidenceReference` Schema:
- `evidence_id`: UUID string.
- `evidence_type`: Enum (PERCEPTUAL_OBSERVATION, EPISODIC_MEMORY, SEMANTIC_FACT, DEDUCTIVE_DERIVATION, EXTERNAL_TOOL_OUTPUT).
- `source_id`: Canonical ID of the immediate source object.
- `original_source_id`: Root identifier where the information first entered the cognitive architecture.
- `derived_from_ids`: Tuple of ancestor evidence IDs.
- `reliability`: Float in [0.0, 1.0] (Inherent sensor or source reliability score).
- `independence_group_id`: String identifying the underlying causal source (e.g., specific sensor, user utterance, memory cluster).
- `provenance_chain`: Ordered tuple of processing steps applied to the raw evidence.

Branch Merging Deduplication Invariant:
When merging two reasoning branches ($B_1$ and $B_2$), the engine resolves their evidence pools by grouping on `independence_group_id`. If both branches cite evidence stemming from the same `independence_group_id`, the combined evidence pool counts the group as SINGLE independent observation, taking $\max(Reliability)$ rather than summing support. Correlated evidence cannot inflate Bayesian updates or synthesis confidence.

D3. CALIBRATED SYNTHESIS CONFIDENCE ASSESSMENT
Problem Addressed: Previous specifications included an arbitrary "NoveltyBonus" in the confidence formula: $C_{synthesis} \le \min(C(B_1), C(B_2)) + \text{NoveltyBonus}$, which was ungrounded and could exceed 1.0.
Architectural Specification:
The arbitrary formula is completely abolished. Synthesis confidence is determined via a structured, multi-factor assessment process:

Calculation Process:
Let $B_1, B_2$ be the premise branches yielding synthesized thought $S$.
1. Base Premise Alignment:
   $C_{base} = \min(C(B_1), C(B_2))$
2. Corroboration & Independence Multiplier ($\alpha_{indep}$):
   If $B_1$ and $B_2$ have distinct, non-overlapping `independence_group_id` sets:
   $\alpha_{indep} = 1.0 + 0.15 \times \min(Rel(B_1), Rel(B_2))$
   If $B_1$ and $B_2$ share underlying sources:
   $\alpha_{indep} = 1.0$ (no independence boost).
3. Contradiction & Coherence Penalty ($P_{contra}$):
   Let $\delta_{contra} \in [0.0, 1.0]$ be the measured semantic/logical tension between synthesized claims.
   $P_{contra} = 1.0 - 0.50 \times \delta_{contra}$
4. Unsupported Assumption Penalty ($P_{assump}$):
   Let $N_{unsupported}$ be the number of ungrounded bridge assumptions introduced in the synthesis.
   $P_{assump} = \exp(-0.25 \times N_{unsupported})$
5. Synthesis Confidence Formulation:
   $C_{synthesis} = \text{clamp}_{[0.0, 1.0]}\left( C_{base} \times \alpha_{indep} \times P_{contra} \times P_{assump} \right)$

Under NO circumstance does novelty increase epistemic confidence. Novelty increases *motivational or attentional curiosity*, not truth probability.

D4. HYPOTHESIS PROBABILITY ESTIMATION & RELATIONSHIP SEMANTICS
Problem Addressed: $P(H \mid E)$ was previously referenced without specifying update mechanics, relationships, or probability normalization rules.
Architectural Specification:
Hypotheses are managed with explicit relational constraints and Bayesian updating:

Typed Hypothesis Relationships:
1. `MUTUALLY_EXCLUSIVE`: Hypotheses within `competing_group_id` cannot simultaneously be true.
   Constraint: $\sum_{i} P(H_i \mid E) \le 1.0$. If a hypothesis is confirmed ($P \to 1$), all others in the group are falsified ($P \to 0$).
2. `COMPETING_BUT_NOT_EXHAUSTIVE`: Hypotheses compete for likelihood, but all may simultaneously be false (the true cause may be unknown).
   Constraint: Individual $P(H_i \mid E) \in [0.0, 1.0]$; sum is NOT constrained to 1.0.
3. `INDEPENDENT`: Truth of $H_1$ has no mathematical bearing on $H_2$.
4. `UNKNOWN_RELATIONSHIP`: Conservative fallback; no joint normalization applied.

Bayesian Updating Formula:
Given new evidence $E$ with reliability $R \in [0.0, 1.0]$:
$$P(H \mid E) = \frac{P(E \mid H) \times P(H)}{P(E)}$$
Where evidence likelihood is scaled by reliability:
$$P(E \mid H)_{calibrated} = R \times P(E \mid H)_{raw} + (1 - R) \times 0.50$$
If evidence directly contradicts $H$ with high reliability ($R \ge 0.90$), $P(H \mid E)$ is immediately depressed to $< 0.05$ and marked `FALSIFIED`.

D5. STRICT ESTABLISHED ACCEPTANCE POLICY
Problem Addressed: No explicit policy governed when a thought or proposition could be labeled `ESTABLISHED`, allowing ungrounded model outputs to be marked as fact.
Architectural Specification:
A proposition can ONLY transition to `epistemic_status = 'ESTABLISHED'` if it satisfies ALL six mandatory acceptance criteria:
1. Evidence Reliability Threshold: Backed by evidence references with aggregate calibrated reliability $R \ge 0.85$.
2. Source Provenance Verification: Derived from verified Perception observations, authoritative Memory Engine claims, or a sound deductive proof.
3. Zero Unresolved Material Contradictions: Checked against the current working context and active memory claims; zero open high-confidence contradictions.
4. Valid Derivation Lineage: Every ancestor in the derivation DAG must be either `ESTABLISHED` or an empirically corroborated observation.
5. Independent Corroboration: Non-deductive assertions must be corroborated by at least TWO distinct `independence_group_id` sources.
6. Domain Verification: For empirical or physical claims, must be verified against domain constraints.

Crucial Rule: High model confidence or fluent text output from an LLM does NOT qualify a thought as `ESTABLISHED`. Model confidence is treated merely as heuristic prior $P_{prior} \le 0.50$ until grounded.

D6. COMPREHENSIVE DOWNSTREAM QUARANTINE PROPAGATION
Problem Addressed: Quarantine flags were previously checked only on immediate child thoughts, allowing counterfactuals or speculations to leak into proposals or memories.
Architectural Specification:
Quarantine enforcement is total and infectious across all cognitive boundaries:

Propagation Rules:
1. Graph Invariant: If node $T_{parent}$ has `is_quarantined == 1`, any derived child node $T_{child}$ created via ANY operator inherits `is_quarantined = 1`.
2. Cross-Thread Association: Quarantined thoughts referenced across threads taint the receiving thread's context unless explicitly marked as counterfactual premises.
3. Memory Nomination Invariant: The Thought Engine strictly forbids nominating any thought with `is_quarantined == 1` for permanent episodic or semantic memory archival.
4. Cognitive Proposal Invariant: Candidate proposals sent to Cognitive Integration with `is_quarantined == 1` are marked `HYPOTHETICAL_SIMULATION_ONLY`. Under no circumstance can they trigger external action execution.
5. Learning Signal Invariant: Quarantined thoughts cannot generate `REASONING_ERROR` or `CAPABILITY_OBSERVATION` signals against real-world competence.
6. De-Quarantining Prohibition: A quarantined thought can NEVER be "de-quarantined" by completing a chain. To establish a counterfactual insight as real-world knowledge, the system must formulate a completely fresh hypothesis and prove it independently using verified real-world evidence.

E. ATTENTION, SCHEDULING, AND RESOURCE GOVERNANCE

E1. PRECISION PRIORITY INPUTS, SOURCES, AND STARVATION PREVENTION
Problem Addressed: The priority score was previously normalized without operational calibration, clear input ownership, or starvation safeguards.
Architectural Specification:
The Attention & Priority Arbitrator computes dynamic thread priority $P_{thread} \in [0.0, 1.0]$ continuously using five calibrated, strictly owned input components:

Input Component Ownership Matrix:
-------------------------------------------------------------------------------------------------------------
Input Component         | Value Range | Owning Source Engine         | Semantic Meaning
-------------------------------------------------------------------------------------------------------------
Urgency ($U$)           | [0.0, 1.0]  | Perception / Cog Integration | Time-criticality and external deadline pressure
Importance ($I$)        | [0.0, 1.0]  | Cognitive Assessment Module  | Systemic significance and long-term utility of topic
Emotional Relevance ($E$)| [0.0, 1.0]  | Emotion Engine               | Affective salience and emotional resonance
Motivational Alignment ($M$)| [0.0, 1.0]| Motivation Engine            | Congruence with active desires, goals, and needs
Unresolved Entropy ($H$) | [0.0, 1.0]  | Thought Engine (Internal)    | Internal cognitive uncertainty and epistemic open-endedness
-------------------------------------------------------------------------------------------------------------

Crucial Semantic Distinction:
Emotional intensity is explicitly decoupled from urgency. A high-intensity aesthetic emotion or nostalgic feeling has high $E$ but low $U$ ($U \approx 0.0$). Conversely, an immediate collision alert from perception has high $U$ ($U \approx 1.0$) independent of whether Diva has yet formed an emotional reaction.

Calibrated Priority Formulation:
$$P_{raw} = w_U \cdot U(t) + w_I \cdot I + w_E \cdot E + w_M \cdot M + w_H \cdot H$$
Default Base Weights: $w_U = 0.30$, $w_I = 0.25$, $w_M = 0.20$, $w_H = 0.15$, $w_E = 0.10$ (Sum of weights = 1.00).

Urgency Time-Decay Dynamics:
For perceptual impulses without ongoing sensory reinforcement, urgency decays exponentially:
$$U(t) = U_0 \cdot \exp(-\lambda_U \cdot (t - t_0))$$
Where half-life $\tau_{urgency} = \frac{\ln(2)}{\lambda_U} = 5.0\text{ seconds}$.

Starvation Prevention Mechanism:
To guarantee that low-urgency but high-importance background threads are not indefinitely starved by a stream of moderate perceptual events, the Arbitrator maintains a starvation counter $c_{starve} \in \mathbb{N}$ for every active thread waiting in `NOT_SCHEDULED` state:
- For every complete scheduling epoch (500 ms) a thread remains unscheduled, its counter increments: $c_{starve} \leftarrow c_{starve} + 1$.
- Starvation Boost:
  $$B_{starve} = \min\left(0.25, 0.015 \cdot \max(0, c_{starve} - 10)\right)$$
- Final Arbitrated Priority:
  $$P_{final} = \min\left(1.0, P_{raw} + B_{starve}\right)$$
- When a thread is selected for `FOCAL` or `BACKGROUND` execution, its $c_{starve}$ resets to 0.

E2. RIGOROUS PREEMPTION RULES, EMERGENCY OVERRIDES, AND CRITICAL SECTIONS
Problem Addressed: The 0.15 hysteresis rule was treated as an absolute barrier without emergency override, minimum consistency guarantees, or dwell time constraints.
Architectural Specification:
Thread preemption balances attentional responsiveness against cognitive thrashing:

1. Standard Preemption Hysteresis Rule:
   A running `FOCAL` thread ($T_{focal}$) is preempted by a candidate thread ($T_{cand}$) if and only if:
   $$P_{final}(T_{cand}) \ge P_{final}(T_{focal}) + 0.15$$
   And the current dwell time $t_{dwell}(T_{focal}) \ge t_{cooldown} = 500\text{ ms}$.

2. Emergency Preemption Override:
   If an incoming event or urgent perception produces $U(T_{cand}) \ge 0.95$ (e.g., immediate threat, critical system alert, direct user interjection):
   - The 0.15 hysteresis requirement is completely BYPASSED.
   - The 500 ms cooldown is completely BYPASSED.
   - Immediate preemption signal is dispatched to the scheduler.

3. Non-Interruptible Critical Sections:
   Preemption cannot break an atomic transaction in progress. If $T_{focal}$ is inside:
   - Atomic SQLite transaction commit (`create_thought_transaction`, `branch_thread_transaction`).
   - DAG cycle validation check.
   - Quarantine tag recursive tree walk.
   The preemption signal is deferred until the critical section completes (guaranteed latency $< 30\text{ ms}$).

4. Maximum Focal Dwell Time (Anti-Monopoly Rule):
   To prevent complex deductive chains from permanently locking the focal slot, maximum continuous dwell time is capped:
   $$t_{dwell}(T_{focal}) \le t_{max\_focal} = 10.0\text{ seconds}$$
   Upon hitting $t_{max\_focal}$, the scheduler forces a checkpoint yield, transitioning $T_{focal}$ to `SUSPENDED`, allowing equal-priority competitors a turn.

5. Measured Suspension Target:
   Context serialization and SQLite persistence target a suspension latency of 30–50 ms under nominal load, benchmarked on standard local storage.

E3. ASYNCHRONOUS REASONING JOB LIFECYCLE & LATE-RESULT REJECTION
Problem Addressed: Background concurrency was specified without job states, causing ambiguity regarding late model outputs and timeouts.
Architectural Specification:
All computationally intensive reasoning operator executions (e.g., deep inference, abductive generation via LLM, analogical mapping) are executed as tracked asynchronous jobs.

`ReasoningJobState` Machine:
`QUEUED` -> `DISPATCHED` -> `RUNNING` -> (`COMPLETED` | `TIMED_OUT` | `CANCELLED` | `FAILED` | `INTERRUPTED`)

Concurrency Boundaries:
- Maximum Concurrent Background Jobs: Exactly 2.
- Focal Processing: 1 synchronous or high-priority dedicated asynchronous pipeline. Background job concurrency is independent of focal scheduling.

Late-Result Rejection Protocol:
When a background job exceeds its deadline ($t > t_{timeout}$, default 4000 ms), the scheduler immediately:
1. Transitions job state in `thought_reasoning_jobs` to `TIMED_OUT`.
2. Emits cancellation token to worker process.
3. If the worker sub-process subsequently finishes and delivers a late result:
   - The Thought Engine checks job state in SQLite.
   - Because state is `TIMED_OUT` or `CANCELLED`, the incoming payload is STRICTLY REJECTED and discarded.
   - Under no circumstances can a late result modify the target thread's DAG, context, or state.
   - Audit event logged: `LATE_JOB_RESULT_DISCARDED`.

E4. QUOTA OVERFLOW POLICIES & ENERGY REDUCTION HANDLING
Problem Addressed: System limits existed without explicit enforcement behaviors, risking silent drops or unmanaged runaway memory growth.
Architectural Specification:
The Thought Engine enforces strict policies when hard cognitive boundaries are encountered:

Quota Boundary Enforcement Table:
-------------------------------------------------------------------------------------------------------------
Resource Limit               | Bound Value | Action on Overflow
-------------------------------------------------------------------------------------------------------------
Active Threads Total         | Max 5       | SUSPEND lowest priority active thread to disk; if all equal, DEFER new
Concurrent Background Jobs   | Max 2       | QUEUE request in pending job buffer; if buffer full, REJECT generation
Thread DAG Depth             | Max 15      | Trigger mandatory Evaluative Synthesis; if unable, CONCLUDE or ABANDON
Thread Node Count            | Max 50 nodes| Execute Graph Summarization; freeze historical nodes into sub-graph ref
Working Context Scratchpad   | Max 64 KB   | Reject additional variables; evict least-recently-accessed scratchpad key
Unresolved Questions Pool    | Max 20 open | Suppress low-entropy questions; overwrite lowest-entropy question
-------------------------------------------------------------------------------------------------------------

Dynamic Energy Reduction Throttling:
When the Energy Regulation Engine reports dropping cognitive energy ($E_{cog} < 0.30$ on a [0.0, 1.0] scale):
- Active Thread Quota drops dynamically: $\text{Quota}_{threads} = \max(1, \lfloor 5 \times E_{cog} \rfloor)$.
- Background Concurrency drops: If $E_{cog} < 0.20$, background jobs = 0 (focal processing only).
- Overflow Handling: Excess active threads are NOT discarded. They are gracefully serialized, transitioned to `SUSPENDED`, and kept intact in SQLite until cognitive energy recovers.

F. MEMORY RETRIEVAL AND ARCHIVAL PROTOCOL

F1. STRUCTURED ASYNCHRONOUS RETRIEVAL & UPDATE CONTRACTS
Problem Addressed: Boolean retrieval/update signatures failed to convey error nuances, stale records, or version mismatches.
Architectural Specification:
All interactions between the Thought Engine and Memory Engine return comprehensive, structured response payloads.

`MemoryOperationResponse` Contract:
- `status`: Enum (`SUCCESS`, `DUPLICATE_IGNORED`, `STALE_VERSION_REJECTED`, `REJECTED_POLICY`, `REJECTED_INSUFFICIENT_EVIDENCE`, `TEMPORARILY_UNAVAILABLE`, `FAILED_UNKNOWN`).

- `error_code`: Optional string code (e.g., `"ERR_MEM_CONSTRAINTS_VIOLATED"`, `"ERR_MEM_UNREACHABLE"`).

F2. HISTORICAL DEVELOPMENT VERSIONING VIA IMMUTABLE SNAPSHOTS
Problem Addressed: Thoughts evolving over time risked mutating original premise records, breaking historical auditability.
Architectural Specification:
Every thought instance, once created and committed to SQLite, is completely IMMUTABLE.
When an existing thought proposition is refined, deepened, or updated with new evidence:
1. Original Record Preserved: The original row in `thought_instances` remains unmodified with its original timestamps.
2. New Instance Created: A new `ThoughtInstance` is created with a unique `thought_id`.
3. Derivation Linked: A `ThoughtDerivation` is added pointing to the original thought ID with `contribution_role = 'PREMISE_FOUNDATION'`.
4. Directed Edge Inserted: A row is inserted in `thought_dag_edges` with `relationship_type = 'SYNTHESIS_JUNCTION'` or relevant operator.
5. Thread Pointer Updated: The thread's active premise list updates to reference the new thought ID, preserving complete historical development.

F3. CATEGORIZED ARCHIVAL REJECTIONS & IDEMPOTENT RETRY RULES
Problem Addressed: Conflating rejection reasons into a single transient error resulted in improper infinite retries of policy rejections.
Architectural Specification:
When a thought is nominated for permanent episodic/semantic storage, Memory Engine evaluation outcomes fall into five distinct categories:

1. `ACCEPTED`:
   - Memory Engine inscriber accepts and consolidates the record.
   - Action: `thought_archival_records.status` set to `ACCEPTED`; `memory_record_id` recorded. No further retries.

2. `REJECTED_POLICY`:
   - Memory Engine rejects nomination because content violates epistemic policy (e.g., unsubstantiated belief, prohibited topic, ungrounded speculation).
   - Action: `status` set to `REJECTED_POLICY`. Retries STRICTLY FORBIDDEN.

3. `REJECTED_DUPLICATE`:
   - Memory Engine already possesses an identical semantic claim with equal or higher confidence.
   - Action: `status` set to `REJECTED_DUPLICATE`. Retries STRICTLY FORBIDDEN. Local thought links to existing memory ID.

4. `REJECTED_INSUFFICIENT_EVIDENCE`:
   - Memory Engine deems supporting evidence reliability too weak ($R < 0.85$) for permanent storage.
   - Action: `status` set to `REJECTED_INSUFFICIENT_EVIDENCE`. Automatic retry FORBIDDEN. Re-nomination permitted ONLY if a new thought provides additional independent corroboration.

5. `TEMPORARY_FAILURE`:
   - Database lock, I/O timeout, or temporary subsystem unavailability.
   - Action: `status` set to `TEMPORARY_FAILURE`; `retry_count` incremented.
   - Retry Policy: Exponential backoff with jitter ($1\text{s}, 2\text{s}, 4\text{s}, \dots$), capped at 3 retries. If `retry_count > 3`, status set to `FAILED_ABANDONED`.
