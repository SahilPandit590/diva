EXECUTIVE ARCHITECTURAL SUMMARY & REVISED V2.0 FOUNDATIONS
================================================================================

The Cognitive Integration & Decision Engine is the central executive coordinator of
Diva's cognitive architecture. In this revised Version 2.0 specification, the previous
flaw of treating Cognitive Integration as a monolithic decision-and-execution controller
is permanently eliminated.

Cognitive Integration is structured into exactly THREE distinct, cooperating subparts:
1. MAIN DECISION ENGINE: Owns the deliberation, conflict resolution, prospective evaluation,
   and executive authorization process.
2. ATTENTION ENGINE: Owns cognitive attention priority, active working context, and the
   leasing of processing permissions for deliberate thoughts and cognitive tasks.
3. COGNITIVE ACTIVITY CONTROLLER: Owns the lifecycle, dependency resolution, progress
   monitoring, and coordination of deliberate cognitive activities selected by Decision.

--------------------------------------------------------------------------------
THE SUPREME INVARIANT: COGNITIVE VS. AUTONOMOUS DOMAIN SEPARATION
--------------------------------------------------------------------------------
Diva possesses two parallel operational domains:
- THE COGNITIVE DOMAIN: Deliberate, conscious, high-level reasoning, formal decision-making,
  and intentional task execution. Governed by Cognitive Integration (Decision, Attention, Activity Controller).
- THE AUTONOMOUS DOMAIN: Spontaneous, curiosity-driven, background ideation, self-directed
  initiatives, and continuous internal life. Governed by the Autonomous Activity & Initiative Engine.

CRITICAL ARCHITECTURAL RULES:
1. Attention controls cognitive processing ONLY. Autonomous processing possesses its own
   independent control mechanism and is NEVER directly governed by the Attention Engine.
2. Autonomous internal states are strictly isolated from the cognitive active attention context.
3. Cognitive Integration authorizes cognitive operations; the autonomous domain authorizes
   its own internal operations.
4. Both domains access common physical resources (CPU, GPU, energy, memory) via the
   Shared Resource Manager, which resolves contention without merging domain internal states.
5. Both domains execute external operations via the Shared Execution Infrastructure, which
   tags all execution requests and returned results with their originating domain UUID.

--------------------------------------------------------------------------------
SHARED INFRASTRUCTURE TRIAD
--------------------------------------------------------------------------------
- SHARED LLM INFRASTRUCTURE: Architecture-wide model routing, context window management,
  schema validation, and fallback handling. Used by all engines; owned by none.
- SHARED EXECUTION INFRASTRUCTURE: Centralized, sandboxed execution of external tools,
  scripts, filesystem operations, and network APIs. Validates cryptographic authorization tokens.
- SHARED RESOURCE MANAGER: Cross-engine arbitrator of physical compute, memory bandwidth,
  and cognitive energy budgets supplied by the Internal State Engine.

PART 1 — SUBSYSTEM 1: MAIN DECISION ENGINE
================================================================================

1.1 MULTI-SOURCE INPUT SYNTHESIS & DECISION CONTEXT ASSEMBLY
   The Main Decision Engine receives continuous signal streams from across the architecture.
   When an actionable situation arises (goal conflict, incoming communication, resource
   threshold, autonomous proposal, or cognitive impasse), it synthesizes a deeply frozen
   `DecisionContext` record:
   - Ingests active drives and candidate goals from Motivation Engine.
   - Ingests current emotional valence, arousal, and mood vector from Emotion Engine.
   - Ingests social rapport, norms, and partner expectations from Social Cognition.
   - Ingests available energy $E_{\text{cog}}$ and workload $W_{\text{cog}}$ from Internal State.
   - Ingests proposed activity candidates from Autonomous Activity Engine.
   - Ingests active reasoning deductions and hypotheses from Thought Engine.
   - Ingests communication requirements from Interaction Engine.

1.2 DELIBERATION ENGINE: MAUT, CONSTRAINT SATISFACTION & PROSPECTIVE SIMULATION
   The decision algorithm executes in three sequential phases:

   PHASE 1: HARD CONSTRAINT FILTERING (Constraint Satisfaction Problem):
   - Safety, ethical boundaries, constitutional persona locks, and strict budget ceilings
     are applied as non-negotiable boolean filters: $C_{\text{hard}}(A) \in \{0, 1\}$.
   - Any alternative violating a hard constraint is immediately rejected with reason code
     `REJECTED_SAFETY_VIOLATION` or `REJECTED_RESOURCE_EXCEEDED`.

   PHASE 2: PROSPECTIVE OUTCOME SIMULATION:
   - For surviving alternatives, the engine forecasts anticipated consequences across
     three time horizons: immediate ($t+0$), short-term ($t+1\text{h}$), and long-term ($t+24\text{h}$).
   - Uses deterministic rules for standard tasks; routes to Shared LLM Infrastructure for
     complex qualitative social/strategic consequence forecasting.

   PHASE 3: MULTI-ATTRIBUTE UTILITY THEORY (MAUT) EVALUATION:
   $$U(A) = \sum_{k} w_k \cdot u_k(A)$$
   Where:
   - $u_{\text{goal}}(A)$: Contribution to active high-priority goals.
   - $u_{\text{drive}}(A)$: Satisfaction of chronic motivational drives.
   - $u_{\text{social}}(A)$: Alignment with social rapport and relationship commitments.
   - $u_{\text{cost}}(A)$: Negative utility of cognitive energy and execution risk.
   - $u_{\text{novelty}}(A)$: Epistemic exploration bonus derived from curiosity drive.
   Weights $w_k$ are dynamically calibrated by Personality baselines and emotional state.

1.3 INTENTION LIFECYCLE, COMMITMENT FORMATION & RECONSIDERATION LOGIC
   - Winning alternative transitions to an active `ExecutiveIntention`.
   - Intention FSM: `FORMULATED` -> `AWAITING_RESOURCES` -> `COMMITTED` -> `EXECUTING` ->
     (`COMPLETED` | `SUSPENDED` | `ABANDONED` | `RECONSIDERED`).
   - Dynamic Reconsideration Triggers:
     1. Invalidation of primary epistemic assumption in Memory.
     2. Acute arrival of higher-urgency external event (Urgency $U > 0.90$).
     3. Drastic drop in available energy ($E_{\text{cog}} < 0.20$).
     4. Critical execution failure reported by Cognitive Activity Controller.
   - Anti-Thrashing Guard: An intention cannot be reconsidered within $T_{\text{cooldown}} = 2.0\text{s}$
     unless an emergency safety trigger occurs.

1.4 ACTION ALTERNATIVE GENERATION & OUTCOME FORECASTING
   - When external circumstances present an ambiguous choice, Decision Engine requests
     alternative generation:
     - Route 1: Thought Engine expands abductive branches.
     - Route 2: Autonomous Activity retrieves cached alternative strategies.
     - Route 3: Shared LLM synthesizes novel compromise options.
   - Decisions can result in 6 explicit outcomes: `ACT_IMMEDIATELY`, `WAIT_AND_OBSERVE`,
     `DEFER_TO_SCHEDULE`, `REQUEST_CLARIFICATION`, `REJECT_PROPOSAL`, `DO_NOTHING`.

1.5 EXECUTIVE GATEKEEPING: AUTHORIZATION GRANTS & SECURITY TOKENS
   - Zero operations leave Diva or alter system files without an `AuthorizationRecord`.
   - The Main Decision Engine is the SOLE authority permitted to sign authorization tokens.
   - Authorization payload:
     `{authorization_id: UUID, domain: COGNITIVE, target_module: Enum, permitted_scope: String, valid_until: Timestamp, signature: HMAC}`.

PART 2 — SUBSYSTEM 2: ATTENTION ENGINE (COGNITIVE FOCUS & LEASING)
================================================================================

2.1 STRICT SCOPE: COGNITIVE ATTENTION VS. AUTONOMOUS PROCESSING
   - Architectural Boundary: The Attention Engine manages COGNITIVE processing focus.
     It has zero jurisdiction over background autonomous processing loops.
   - Autonomous background ideation runs on dedicated, non-leased worker cycles governed
     by Autonomous Activity. Attention Engine neither schedules nor pauses autonomous tasks.
   - The Attention Engine governs: (1) Active thought thread leasing in Thought Engine,
     (2) Context window occupancy in deliberate reasoning, (3) Focus slots for active cognitive activities.

2.2 ACTIVE CONTEXT WINDOW & WORKING MEMORY ALLOCATION
   - Cognitive working memory is strictly bounded ($K=7 \pm 2$ operational slots).
   - Attention Engine maintains the active cognitive context package:
     `ActiveCognitiveContext`: `{focal_thought_id, primary_activity_id, active_participants, active_goal_refs, working_memory_items}`.
   - Context Switching: Swapping working memory items incurs a switching cost delay (50–150 ms)
     to prevent thrashing and simulate cognitive friction.

2.3 ATTENTION PRIORITY FORMULATION & ANTI-STARVATION AGING
   The Attention Engine continuously scores cognitive focus candidates:
   $$P_{\text{attn}} = w_D \cdot P_{\text{decision}} + w_U \cdot U_{\text{perceptual}} + w_E \cdot E_{\text{salience}} + B_{\text{starve}}$$
   Where:
   - $P_{\text{decision}}$: Priority assigned by Main Decision Engine ($w_D = 0.45$).
   - $U_{\text{perceptual}}$: Perceptual urgency from external events ($w_U = 0.30$).
   - $E_{\text{salience}}$: Affective salience from Emotion Engine ($w_E = 0.15$).
   - $B_{\text{starve}} = \min(0.25, 0.02 \cdot \text{wait\_epochs})$: Anti-starvation aging boost ($w = 0.10$).

2.4 PROCESSING PERMISSION LEASES (COGNITIVE FOCUS GRANTS)
   - To consume cognitive reasoning tokens or invoke shared LLM reasoning, a cognitive
     thread must hold an active `AttentionLease`.
   - Lease properties: `lease_id: UUID`, `holder_activity_id: UUID`, `granted_capacity_pct: Float`,
     `lease_duration_ms: Integer`, `expires_at: Timestamp`.
   - When an activity completes its step, it yields the lease. If it exceeds `lease_duration_ms`,
     the Attention Engine forcefully preempts it.

2.5 PREEMPTION, HYSTERESIS (0.15 DELTA), DWELL CAPS & INTERRUPTION HANDLING
   - Standard Preemption Hysteresis Rule: Candidate task $T_{\text{cand}}$ preempts running
     focal task $T_{\text{focal}}$ IF AND ONLY IF:
     $$P_{\text{attn}}(T_{\text{cand}}) \ge P_{\text{attn}}(T_{\text{focal}}) + 0.15$$
     AND current dwell time $t_{\text{dwell}}(T_{\text{focal}}) \ge 500\text{ ms}$.
   - Emergency Preemption Override: If $U_{\text{perceptual}} \ge 0.95$ (immediate threat / critical
     user interjection), hysteresis and dwell cooldown are instantly bypassed.
   - Maximum Focal Dwell Cap: Continuous focal execution is capped at $t_{\text{max\_dwell}} = 10.0\text{s}$,
     forcing a checkpoint yield to prevent thread starvation.

PART 3 — SUBSYSTEM 3: COGNITIVE ACTIVITY CONTROLLER
================================================================================

3.1 DELIBERATE COGNITIVE ACTIVITY LIFECYCLE (11-STATE FSM)
   Deliberate cognitive activities (e.g., executing a verified calculation, conducting a
   focused research step, formulating a specific reply, verifying a logical proof) are
   governed by a strict finite state machine:
   `CREATED` -> `VALIDATING` -> `READY` -> `SCHEDULED` -> `ACTIVE` ->
   (`PAUSED` | `INTERRUPTED` | `BLOCKED`) -> `AWAITING_VERIFICATION` ->
   (`COMPLETED` | `FAILED` | `CANCELLED`).

3.2 VALIDATION & INSTANTIATION OF DECISION ENGINE DIRECTIVES
   - Ingests `CognitiveActivityDirective` from Main Decision Engine.
   - Verifies required capabilities, preconditions, and valid authorization token.
   - Instantiates formal `CognitiveActivityRecord` and inserts into execution registry.
   - Declares prerequisite dependencies and registers completion criteria.

3.3 ATTENTION ALLOCATION COORDINATION & PROGRESS TRACKING
   - When an activity reaches `READY`, it requests a processing slot from the Attention Engine.
   - Upon receiving an `AttentionLease`, Activity Controller transitions activity to `ACTIVE`
     and initiates execution via Shared Execution Infrastructure.
   - Monitors execution progress and tracks subtask completion counters.

3.4 SUBTASK DEPENDENCY RESOLUTION & BARRIER SYNCHRONIZATION
   - Multi-step cognitive tasks form DAGs.
   - Activity Controller evaluates prerequisite satisfaction using topological sorting.
   - Unblocks downstream subtasks when prerequisite outputs are verified.

3.5 SUSPENSION, RESUMPTION, FAILURE & CANCELLATION PROTOCOLS
   - On Attention preemption: Serializes working state, snapshots context, marks `PAUSED`.
   - On Resumption: Restores context snapshot, requests renewed attention lease, resumes `ACTIVE`.
   - On Tool Execution Error: Categorizes error (transient vs. fatal). Retries transient errors up
     to 2 times; transitions to `FAILED` if unrecoverable and alerts Main Decision Engine.
   - On Executive Cancellation: Instantly aborts active tool runs and updates status to `CANCELLED`.

PART 4 — COGNITIVE / AUTONOMOUS SEPARATION & SHARED INFRASTRUCTURE
================================================================================

4.1 STRICT DOMAIN INVARIANTS: STATE, IDENTITY & CONTROL SEPARATION
   The architecture enforces a hard, physical boundary between domains:
   - DOMAIN TAGGING: Every packet, candidate, activity, request, and receipt is stamped with
     `originating_domain: Enum('COGNITIVE', 'AUTONOMOUS')`.
   - IDENTITY PRESERVATION: Autonomous activities retain their UUIDs and autonomous ownership
     even when reviewed by Cognitive Integration. Cognitive Integration approves or denies;
     it NEVER absorbs or overwrites autonomous task identity.
   - CONTROL ISOLATION: The Attention Engine is structurally incapable of dispatching preemption
     or lease events to autonomous worker loops. Autonomous processing state is invisible to
     the cognitive attention priority heap.

4.2 SHARED LLM INFRASTRUCTURE
   - Centralized gateway module providing language model inference across all 15 engines.
   - Capabilities:
     1. Provider Routing: Routes requests to local models (e.g., small quantized models for fast classification)
        or remote frontier models (for deep reasoning, coding, or synthesis) based on declared brief complexity.
     2. Context Packaging & Truncation: Enforces hard token limits per engine brief, pruning history safely.
     3. Structured Output Enforcement: Validates model responses against engine JSON schemas using Pydantic;
        retries with corrective prompts on format violations; falls back to deterministic handlers on repeated failure.
     4. Fault Isolation: An LLM provider outage or rate limit triggers circuit breakers. Non-LLM
        deterministic engine logic (FSMs, database updates, rule filters) continues operating with zero impairment.
     5. Complete Provenance: Records prompt tokens, completion tokens, latency, provider name, and calling engine UUID.

4.3 SHARED EXECUTION INFRASTRUCTURE
   - Centralized, hardened execution harness running external operations: tool invocations, shell scripts,
     file modifications, and API calls.
   - Security Invariants:
     1. Dual Authorization Check: Validates that Cognitive requests have valid Cognitive Integration signatures,
        and Autonomous requests have valid Autonomous Activity signatures.
     2. Process Isolation: Every script/tool executes in an isolated sandbox with restricted filesystem access.
     3. Timeout Enforcement: Hard execution kill timers (default 30s) prevent zombie subprocesses.
     4. Domain Egress Tagging: Execution results are returned strictly to the queue of the domain that originated them.

4.4 SHARED RESOURCE MANAGER
   - Arbitrates global compute resources between Cognitive and Autonomous domains:
     - Resource Envelope: Total CPU threads, GPU VRAM, RAM, and Cognitive Energy $E_{\text{cog}}$.
     - Allocation Policy:
       * When $E_{\text{cog}} \ge 0.60$: Cognitive domain guaranteed 60% capacity; Autonomous domain allocated 40%.
       * When $0.30 \le E_{\text{cog}} < 0.60$: Cognitive domain guaranteed 80% capacity; Autonomous domain throttled to 20%.
       * When $E_{\text{cog}} < 0.30$: Emergency conservation. Autonomous domain allocated 0% (suspended);
         Cognitive domain limited strictly to critical user interactions.
     - Anti-Contention Arbitration: If both domains request exclusive GPU/tool access simultaneously,
       Shared Resource Manager grants access based on systemic urgency $U$, ensuring cognitive user
       responsiveness while preventing autonomous starvation through bounded wait queues.

PART 5 — TRI-SUBSYSTEM INTERNAL COMMUNICATION PROTOCOLS
================================================================================

The three subparts communicate across a high-speed in-memory async message bus using
frozen, validated contract payloads:

1. `DecisionToActivityDirective`:
   - Egress: Main Decision Engine -> Cognitive Activity Controller.
   - Payload: `{directive_id: UUID, intention_id: UUID, activity_title: String, operational_type: Enum,
     parameters: Dict, priority: Float, authorization_id: UUID, created_at: Timestamp}`.

2. `ActivityAttentionRequest`:
   - Egress: Cognitive Activity Controller -> Attention Engine.
   - Payload: `{request_id: UUID, activity_id: UUID, base_priority: Float, required_capacity_pct: Float,
     max_dwell_ms: Integer, requested_at: Timestamp}`.

3. `AttentionGrantResponse`:
   - Egress: Attention Engine -> Cognitive Activity Controller.
   - Payload: `{grant_id: UUID, request_id: UUID, lease_id: UUID, status: Enum('GRANTED','QUEUED','DENIED','PREEMPTED'),
     allocated_capacity_pct: Float, valid_until: Timestamp}`.

4. `ActivityProgressReport`:
   - Egress: Cognitive Activity Controller -> Main Decision Engine.
   - Payload: `{report_id: UUID, activity_id: UUID, status: Enum, percent_complete: Float,
     intermediate_results: Dict, blocker_info: Optional[Dict], reported_at: Timestamp}`.

5. `DecisionPreemptionCommand`:
   - Egress: Main Decision Engine -> Attention Engine & Activity Controller.
   - Payload: `{command_id: UUID, target_activity_id: UUID, action: Enum('SUSPEND','ABORT','REPRIORITIZE'),
     new_priority: Optional[Float], reason: String, issued_at: Timestamp}`.

6. `AttentionRevocationNotice`:
   - Egress: Attention Engine -> Cognitive Activity Controller.
   - Payload: `{revocation_id: UUID, lease_id: UUID, activity_id: UUID, reason: Enum('DWELL_TIMEOUT','HIGHER_PRIORITY_PREEMPTION','RESOURCE_CRUNCH'),
     grace_period_ms: Integer, revoked_at: Timestamp}`.
