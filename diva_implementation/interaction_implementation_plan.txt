EXECUTIVE ARCHITECTURAL SUMMARY & GOVERNING PRINCIPLES
================================================================================

The Interaction Engine manages how Diva communicates and maintains ongoing
interactions with users, applications, external AI agents, and third-party systems.
Its mandate is NOT simply to generate text or emit messages. It governs the complete
lifecycle of communication: receiving raw events across heterogeneous channels,
normalizing them into standard message envelopes, tracking conversational turns,
maintaining operational session continuity, coordinating outbound delivery under
strict cognitive authorization, handling real-time interruptions, and enforcing
privacy, consent, and channel boundaries.

--------------------------------------------------------------------------------
THE EIGHT NON-NEGOTIABLE AXIOMS
--------------------------------------------------------------------------------
1. INTERACTION IS NOT COGNITION
   The Interaction Engine manages the communication process, not Diva's independent
   decisions, beliefs, desires, or thoughts. It never decides whether Diva should
   forgive, assist, challenge, ignore, or contact someone. Cognitive Integration
   makes decisions; Interaction coordinates delivery mechanics.

2. A CONVERSATION IS NOT A MEMORY
   Operational session state (active turn, channel routing, pending response buffer)
   is distinct from permanent autobiographical memory. When an operational session
   closes or expires, Memory Engine preserves durable historical experiences.
   Interaction Engine never mutates or claims ownership over Memory tables.

3. A THOUGHT IS NOT PERMISSION
   No autonomous or proactive communication may ever be dispatched solely because an
   internal thought occurred, an emotion spiked, or a motivation escalated. Proactive
   communication strictly requires explicit, cryptographically verifiable
   authorization from Cognitive Integration.

4. GENERATING A MESSAGE IS NOT DELIVERING A MESSAGE
   Drafting or rendering content via shared LLM infrastructure is an isolated,
   reversible stage. A generated message must pass authorization, recipient
   validation, format constraints, and channel capability checks before entering
   the Delivery Manager. Generation failure must never yield unvalidated fallback text.

5. A TIMEOUT IS NOT PROOF OF NON-DELIVERY
   Network disconnections and adapter timeouts represent ambiguous delivery states.
   The engine preserves delivery uncertainty (`DELIVERY_UNCERTAIN`) rather than
   naively assuming failure and blasting duplicates onto external channels.

6. EVERY CONVERSATION IS STRICTLY ISOLATED
   Every conversation maintains its own UUID, participant set, turn state, and
   context window. Context, private messages, and operational state must never leak
   across conversations, even when two concurrent sessions share the same user.

7. CHANNELS ARE PLUGGABLE AND REPLACEABLE
   Core conversational logic has zero coupling to specific transport protocols
   (Discord, Telegram, WebSockets, REST, CLI). Channel adapters expose standard
   capability manifests; core engine treats all channels through identical abstractions.

8. LLMS DO NOT CONTROL DELIVERY OR AUTHORIZATION
   Language models produce text representations from approved intent. They do not
   evaluate permissions, determine turn transitions, authorize proactive pings,
   or bypass privacy gates. All authorization, turn state machines, and rate limits
   are strictly deterministic.

--------------------------------------------------------------------------------

PART 1 — HOW THE ENGINE RUNS: OVERALL EXECUTION MODEL & CONCURRENCY
================================================================================

1.1 MULTI-TIER ASYNCHRONOUS PIPELINE TOPOLOGY
   The Interaction Engine runs on Python 3.12+ `asyncio` utilizing an event-driven,
   bounded queue architecture structured into three operational tiers:

   TIER 1 — INGRESS / EGRESS DISPATCH (Synchronous & Fast-Path Async, <15 ms):
   - Channel adapters listen to external network sockets / webhooks.
   - Incoming events are immediately enveloped, stamped with monotonically increasing
     arrival sequence numbers, checked against an in-memory Bloom filter for duplicate
     suppression, and queued into the bounded Inbound Priority Queue.
   - Outbound packets cleared for delivery are handed to channel adapter drivers.

   TIER 2 — TURN & CONTEXT ORCHESTRATION (Async Core, <100 ms):
   - Inbound Message Handler dequeues envelopes, resolves conversation IDs via
     Conversation Manager, links participant identities via Participant Manager,
     and updates Conversation Turn FSM.
   - Interaction Router dispatches normalized envelopes to Perception Engine.
   - Context Manager dynamically constructs bounded `InteractionContextPackage`
     snapshots when Cognitive Integration requests context to formulate replies.

   TIER 3 — CONTENT COORDINATION & RECOVERY (Background Async, Non-Blocking):
   - Content Coordination Module interfaces with Shared LLM Infrastructure to render
     approved communication intents into channel-compliant text.
   - Delivery Manager tracks ACKs, updates Delivery Receipt FSM, invokes Retry and
     Recovery Manager on failures.
   - Session Lifecycle Manager evaluates inactivity timers and archives stale sessions.

1.2 CONCURRENCY & PER-CONVERSATION ISOLATION MODEL
   - Every active conversation maintains a dedicated asyncio `ConversationActor`
     queue. Messages arriving for conversation $C_A$ are processed sequentially in
     $C_A$'s actor loop, guaranteeing strict causal ordering of turns within that
     conversation without distributed locking.
   - Distinct conversations $C_A$ and $C_B$ execute in parallel on disjoint actor loops.
     A network timeout or blocking retry on $C_A$ has zero latency impact on $C_B$.
   - Thread-safe, atomic SQLite WAL persistence is handled by a single background
     persistence worker draining an asynchronous persistence queue, ensuring atomic
     transaction boundaries without database lock contention.

1.3 RESOURCE THROTTLING & BACKPRESSURE MECHANICS
   - Internal State Engine feeds cognitive energy $E_{\text{cog}}$ and workload $W_{\text{cog}}$.
   - Normal Load ($E_{\text{cog}} \ge 0.40, W_{\text{cog}} \le 0.75$): All inbound and
     outbound queues operate at full capacity.
   - Throttled Load ($0.20 \le E_{\text{cog}} < 0.40$ or $W_{\text{cog}} > 0.75$):
     Proactive communication is suspended; low-priority background conversations
     experience delayed response scheduling; rate limits tighten by 50%.
   - Emergency Backpressure ($E_{\text{cog}} < 0.20$ or Queue Fill $> 85\%$):
     Non-interactive notifications rejected; incoming bursts queued with HTTP 429 /
     adapter-level backpressure signals; active turns limited to critical channels.

1.4 CRASH RECOVERY & STARTUP RECONCILIATION PROTOCOL
   When Diva boots or restarts following an ungraceful shutdown:
   Step 1: Execute `PRAGMA integrity_check` on SQLite database file.
   Step 2: Load all `interaction_sessions` where `status IN ('ACTIVE', 'PROCESSING', 'RESPONDING')`.
   Step 3: Reconcile in-progress turns:
           - Turns in `GENERATING` or `RESPONSE_REQUESTED`: Set to `INTERRUPTED`.
             Dispatch state notification to Cognitive Integration.
           - Turns in `DELIVERING`: Set to `DELIVERY_UNCERTAIN`. Inspect channel adapter
             outbox if adapter supports remote message query by client-generated nonce.
   Step 4: Expire dangling authorizations: Any `AuthorizationRecord` whose `valid_until`
           is in the past or whose session was ungracefully interrupted is marked `REVOKED`.
   Step 5: Rebuild in-memory duplicate detection Bloom filter from the last 10,000
           persisted message deduplication hashes.
   Step 6: Mark engine lifecycle state `ACTIVE` and open inbound channel adapters.

PART 2 — INTERNAL ARCHITECTURE & THE TWENTY-ONE LOGICAL MODULES
================================================================================

--------------------------------------------------------------------------------
1. CHANNEL ADAPTER MANAGER
--------------------------------------------------------------------------------
- Purpose: Registers, configures, monitors, and abstracts external transport interfaces.
- Inputs: Adapter registrations, configuration manifests, health heartbeats.
- Outputs: Certified `ChannelRecord` instances, channel status telemetry.
- Internal State: In-memory registry `Dict[channel_id, ChannelAdapterInstance]`,
  cached `ChannelCapabilityRecord` per channel.
- Algorithms: Capability negotiation; adapter heartbeat monitor (interval: 5s);
  dynamic adapter load/unload without engine restart.
- Decision Rules: Reject message dispatch if adapter status is `DISCONNECTED` or
  requested MIME type not in `supported_content_types`.

--------------------------------------------------------------------------------
2. INBOUND MESSAGE HANDLER
--------------------------------------------------------------------------------
- Purpose: Primary ingress gate for incoming communication packets.
- Inputs: Raw channel events from Channel Adapters.
- Outputs: Validated, deduplicated internal `MessageEnvelope` records.
- Internal State: Fast-lookup Bloom filter for message IDs; arrival rate meter.
- Algorithms: Monotonic arrival timestamping ($T_{\text{recv}}$); SHA-256 content
  hash calculation for idempotency; rate-limiting sliding window (token bucket).
- Error Handling: Duplicates drop into `IdempotencyRecord` with `duplicate_detected=True`;
  floods trigger adapter backpressure.

--------------------------------------------------------------------------------
3. MESSAGE NORMALIZER
--------------------------------------------------------------------------------
- Purpose: Converts heterogeneous channel payloads into canonical `MessageEnvelope`.
- Inputs: Raw adapter payload, channel metadata.
- Outputs: Normalized `MessageEnvelope` conforming to strict internal schema.
- Internal State: Channel-specific schema mapping tables.
- Algorithms: Structural field mapping; attachment reference resolution; UTF-8
  sanitization; timezone normalization to ISO-8601 UTC.
- Invariants: Original raw payload is stored as serialized JSON in persistence for
  audit trails, but internal engines only receive normalized envelopes.

--------------------------------------------------------------------------------
4. PARTICIPANT MANAGER
--------------------------------------------------------------------------------
- Purpose: Tracks human, agent, and system identities within conversations.
- Inputs: Sender IDs, platform handles, Social Cognition identity resolution links.
- Outputs: Validated `ParticipantRecord` associations.
- Internal State: In-memory mapping `Dict[(conversation_id, channel_participant_id), participant_id]`.
- Algorithms: Multi-participant membership validation; join/leave event tracking;
  distinguishes sender, direct recipient, and CC'd observers in group interactions.

--------------------------------------------------------------------------------
5. CONVERSATION MANAGER
--------------------------------------------------------------------------------
- Purpose: Coordinates creation, lookup, routing, and isolation of conversation threads.
- Inputs: Normalized envelopes, session creation directives.
- Outputs: Canonical `conversation_id`, conversation lookup results.
- Internal State: Active conversation cache `Dict[conversation_id, ConversationRecord]`.
- Algorithms: Session resolution heuristic (Match external thread ID -> match
  active user session on channel -> spawn new conversation if inactivity > threshold);
  strict isolation firewall preventing cross-thread data contamination.

--------------------------------------------------------------------------------
6. SESSION LIFECYCLE MANAGER
--------------------------------------------------------------------------------
- Purpose: Manages conversation session states and automated expiration policies.
- Inputs: Turn activity timestamps, explicit close signals, timeout sweeps.
- Outputs: State transition events (`SESSION_SUSPENDED`, `SESSION_CLOSED`, `SESSION_ARCHIVED`).
- Internal State: Min-heap priority queue of conversation expiration deadlines.
- Algorithms: Inactivity timeout sweep (runs every 60s); graceful state transitions:
  `ACTIVE` -> `SUSPENDED` (after $T_{\text{inactivity}} = 15\text{m}$) -> `ARCHIVED` (after 7 days).

--------------------------------------------------------------------------------
7. TURN MANAGER
--------------------------------------------------------------------------------
- Purpose: Governs conversational floor control, turn ownership, and turn states.
- Inputs: Inbound messages, Cognitive Integration turn directives, interruption alerts.
- Outputs: `ConversationTurn` instances, turn transition events.
- Internal State: Active turn map `Dict[conversation_id, ConversationTurn]`.
- Algorithms: Turn state machine enforcement (14 distinct states); multi-message
  turn buffering (groups rapid consecutive messages from same speaker into single turn);
  turn pacing delays.

--------------------------------------------------------------------------------
8. CONTEXT MANAGER
--------------------------------------------------------------------------------
- Purpose: Assembles bounded operational conversation context packages for cognitive reasoning.
- Inputs: Context queries from Cognitive Integration / Thought Engine.
- Outputs: Frozen `InteractionContextPackage` data models.
- Internal State: Sliding window cache of last $N=30$ turns per active conversation.
- Algorithms: Token-bounded context window construction; recency weighting;
  injects active topic, unanswered questions, pending tasks, and applicable preferences;
  does NOT inject unlimited history (delegates historical recall to Memory Engine).

--------------------------------------------------------------------------------
9. INTERACTION ROUTER
--------------------------------------------------------------------------------
- Purpose: Dispatches normalized interaction events to downstream cognitive engines.
- Inputs: Normalized `MessageEnvelope`, turn events.
- Outputs: Typed asynchronous events to Perception, Memory, Social Cognition, Feedback.
- Internal State: Engine routing subscription table.
- Algorithms: Non-blocking parallel fan-out; backpressure monitoring on inter-engine queues.

--------------------------------------------------------------------------------
10. OUTBOUND MESSAGE MANAGER
--------------------------------------------------------------------------------
- Purpose: Receives, validates, and stages outbound communication directives.
- Inputs: `DeliveryRequest` from Cognitive Integration.
- Outputs: Staged outbound tasks ready for content coordination and delivery.
- Internal State: Priority-ranked outbound staging buffer.
- Algorithms: Request validation against schema and channel capability; deduplication
  check via request idempotency key; priority queue insertion.

--------------------------------------------------------------------------------
11. CONTENT COORDINATION MODULE
--------------------------------------------------------------------------------
- Purpose: Interfaces with Shared LLM Infrastructure to produce natural language outputs.
- Inputs: Approved communication intent, style tokens, interaction context.
- Outputs: Rendered message content conforming to channel length and format limits.
- Internal State: Pending generation request tracking table.
- Algorithms: Style parameter injection; length truncation / chunking heuristics;
  deterministic post-generation validation (ensures LLM did not hallucinate unauthorized
  system prompts or leak private tags).

--------------------------------------------------------------------------------
12. DELIVERY MANAGER
--------------------------------------------------------------------------------
- Purpose: Dispatches finalized messages to Channel Adapters and monitors receipts.
- Inputs: Formatted outbound payloads from Content Coordination.
- Outputs: Raw channel transmissions, `DeliveryReceipt` generation.
- Internal State: In-flight transmission ledger `Dict[request_id, DeliveryAttemptState]`.
- Algorithms: Channel dispatch; synchronous/asynchronous ACK capture; latency tracking.

--------------------------------------------------------------------------------
13. RETRY AND RECOVERY MANAGER
--------------------------------------------------------------------------------
- Purpose: Governs retransmission policies for transient channel failures.
- Inputs: Channel delivery errors, timeout events.
- Outputs: Retry dispatch schedules, terminal failure escalations.
- Internal State: Exponential backoff state table `Dict[request_id, RetryRecord]`.
- Algorithms: Truncated exponential backoff with full jitter:
  $T_{\text{retry}} = \min(M_{\text{max}}, B \cdot 2^{\text{attempt}}) \pm \text{random\_jitter}$;
  hard cap at 3 attempts; permanent failure categorization (e.g., HTTP 400 vs 503).

--------------------------------------------------------------------------------
14. INTERRUPTION MANAGER
--------------------------------------------------------------------------------
- Purpose: Handles race conditions, user cancellations, and interjections mid-turn.
- Inputs: New inbound message during `GENERATING`/`DELIVERING`, explicit cancel signals.
- Outputs: Turn preemption orders, pipeline abortion signals.
- Internal State: Active cancellation token registry `Dict[turn_id, asyncio.Event]`.
- Algorithms: Fast-path cancellation flag check; immediate teardown of active LLM streaming;
  evaluation of whether pending draft should be discarded, amended, or superseded.

--------------------------------------------------------------------------------
15. PREFERENCE MANAGER
--------------------------------------------------------------------------------
- Purpose: Manages channel- and user-specific communication style preferences.
- Inputs: Preference declarations from Social Cognition / direct user settings.
- Outputs: `CommunicationPreference` bundles attached to Context Packages.
- Internal State: Cached preference table indexed by `(participant_id, channel_id)`.
- Algorithms: Preference precedence resolver (Explicit user preference > Channel
  standard > Inferred social tendency); source attribution tracking (`EXPLICIT` vs `INFERRED`).

--------------------------------------------------------------------------------
16. AUTHORIZATION VALIDATOR
--------------------------------------------------------------------------------
- Purpose: Hard security gate verifying permissions before ANY external communication.
- Inputs: Outbound delivery requests, initiation requests.
- Outputs: Cryptographic validation verdict (`APPROVED` / `REJECTED_UNAUTHORIZED`).
- Internal State: Active authorization grant ledger.
- Algorithms: Nonce verification; checks grant issuer is Cognitive Integration;
  validates `valid_until` timestamp; confirms target recipient and channel match grant scope.
- Invariant: Zero exceptions. No message leaves Diva without passing this gate.

--------------------------------------------------------------------------------
17. PROACTIVE COMMUNICATION HANDLER
--------------------------------------------------------------------------------
- Purpose: Manages self-initiated outreach originating from internal autonomous drives.
- Inputs: `InitiationRequest` from Autonomous Activity / Cognitive Integration.
- Outputs: Authorized proactive `DeliveryRequest` payloads.
- Internal State: Proactive frequency budget counters (sliding window).
- Algorithms: Strict notification rate-limiting (e.g., max 1 unprompted message per 4 hours
  unless flagged `URGENT_SAFETY`); quiet hours suppression; recipient opt-in validation.

--------------------------------------------------------------------------------
18. QUEUE AND PRIORITY MANAGER
--------------------------------------------------------------------------------
- Purpose: Arbitrates scheduling order across simultaneous conversations and tasks.
- Inputs: Inbound and outbound envelopes tagged with priority weights.
- Outputs: Scheduled task dispatch order.
- Internal State: Multi-level priority queues (CRITICAL, HIGH, NORMAL, BACKGROUND).
- Algorithms: Strict priority scheduling with aging (starvation prevention formula:
  effective priority increases by +0.05 every 500ms spent in queue).

--------------------------------------------------------------------------------
19. INTERACTION HISTORY MANAGER
--------------------------------------------------------------------------------
- Purpose: Persists and indexes operational interaction history in SQLite.
- Inputs: Completed turns, message envelopes, delivery receipts, interruption logs.
- Outputs: Audit records, historical session lookups for resumed conversations.
- Internal State: Thread-safe SQLite connection pool (WAL mode).
- Algorithms: Asynchronous batch committing; retention window enforcement (purges raw
  payloads of closed sessions older than 30 days while preserving metadata and turns).

--------------------------------------------------------------------------------
20. LIFECYCLE AND STATE VALIDATOR
--------------------------------------------------------------------------------
- Purpose: Enforces formal state transition invariants across Sessions and Turns.
- Inputs: Proposed state transition requests.
- Outputs: Approved transition or `InvalidStateTransitionError`.
- Internal State: Static FSM transition matrices for `SessionState` and `TurnState`.
- Algorithms: Table-driven state verification; atomic state swap; logs illegal
  transition attempts for security audit.

--------------------------------------------------------------------------------
21. EVENT AND FEEDBACK PUBLISHER
--------------------------------------------------------------------------------
- Purpose: Publishes completed interaction metrics to Feedback and Memory Engines.
- Inputs: Turn completions, delivery receipts, user response latencies.
- Outputs: `InteractionOutcomeSignal` to Feedback Engine; `InteractionMemoryNomination`
  to Memory Engine.
- Internal State: Unacknowledged outcome queue.
- Algorithms: Asynchronous event publishing; delivery outcome classification
  (DELIVERY_SUCCESS, DELIVERY_TIMEOUT, USER_INTERRUPTED, USER_DISENGAGED).

PART 3 — COMPREHENSIVE DATA DICTIONARY (20 FROZEN DATA STRUCTURES)
================================================================================

All models are deeply frozen Pydantic models (`frozen=True`, `extra='forbid'`,
nested collections as immutable tuples).

1. `InteractionSession`:
   - `session_id`: UUID (Primary Key).
   - `conversation_id`: UUID.
   - `channel_id`: String (e.g., 'discord_main', 'web_chat_01').
   - `status`: Enum (`CREATED`, `ACTIVE`, `WAITING_FOR_INPUT`, `PROCESSING`,
     `RESPONDING`, `INTERRUPTED`, `SUSPENDED`, `RESUMING`, `CLOSED`, `ARCHIVED`).
   - `created_at`: ISO-8601 UTC.
   - `last_activity_at`: ISO-8601 UTC.
   - `expires_at`: ISO-8601 UTC.
   - `session_version`: Integer.

2. `ConversationRecord`:
   - `conversation_id`: UUID (Primary Key).
   - `title`: Optional String.
   - `primary_channel_id`: String.
   - `status`: Enum (`ACTIVE`, `SUSPENDED`, `CLOSED`, `ARCHIVED`).
   - `participant_ids`: Tuple[UUID, ...].
   - `created_at`: ISO-8601 UTC.
   - `updated_at`: ISO-8601 UTC.
   - `conversation_version`: Integer.

3. `ParticipantRecord`:
   - `participant_id`: UUID (Primary Key).
   - `conversation_id`: UUID.
   - `social_entity_id`: Optional UUID (links to Social Cognition `individual_id`).
   - `channel_identity`: String (e.g., 'discord:849204810294').
   - `display_name`: String.
   - `role`: Enum (`PRIMARY_USER`, `EXTERNAL_USER`, `OBSERVER`, `SYSTEM_AGENT`, `DIVA`).
   - `membership_status`: Enum (`ACTIVE`, `LEFT`, `MUTED`, `BANNED`).
   - `joined_at`: ISO-8601 UTC.

4. `MessageEnvelope`:
   - `message_id`: UUID (Primary Key).
   - `conversation_id`: UUID.
   - `turn_id`: Optional UUID.
   - `sender_id`: UUID (Participant ID).
   - `recipient_ids`: Tuple[UUID, ...].
   - `channel_id`: String.
   - `direction`: Enum (`INBOUND`, `OUTBOUND`).
   - `content_type`: Enum (`TEXT_PLAIN`, `MARKDOWN`, `AUDIO_STREAM`, `IMAGE_REF`, `STRUCTURED_JSON`).
   - `raw_content`: String.
   - `attachment_refs`: Tuple[String, ...].
   - `reply_to_message_id`: Optional UUID.
   - `source_timestamp`: ISO-8601 UTC (timestamp assigned by external channel).
   - `received_timestamp`: ISO-8601 UTC (arrival time in Diva).
   - `sequence_number`: Integer.
   - `idempotency_hash`: String (SHA-256).
   - `privacy_classification`: Enum (`INTERNAL_ONLY`, `APPROVED_FOR_RECIPIENT`, `PUBLIC`).

5. `ConversationTurn`:
   - `turn_id`: UUID (Primary Key).
   - `conversation_id`: UUID.
   - `turn_number`: Integer.
   - `initiator_participant_id`: UUID.
   - `status`: Enum (`CREATED`, `RECEIVED`, `PROCESSING`, `AWAITING_DECISION`,
     `RESPONSE_REQUESTED`, `GENERATING`, `READY_TO_DELIVER`, `DELIVERING`,
     `DELIVERED`, `WAITING_FOR_REPLY`, `INTERRUPTED`, `CANCELLED`, `FAILED`, `COMPLETED`).
   - `inbound_message_ids`: Tuple[UUID, ...].
   - `outbound_message_ids`: Tuple[UUID, ...].
   - `started_at`: ISO-8601 UTC.
   - `completed_at`: Optional ISO-8601 UTC.

6. `InteractionEvent`:
   - `event_id`: UUID (Primary Key).
   - `event_type`: Enum (`MESSAGE_RECEIVED`, `TURN_STARTED`, `TURN_COMPLETED`,
     `RESPONSE_GENERATED`, `MESSAGE_DELIVERED`, `INTERRUPTION_TRIGGERED`,
     `SESSION_STATE_CHANGED`, `DELIVERY_FAILED`, `PREFERENCE_UPDATED`).
   - `conversation_id`: UUID.
   - `session_id`: UUID.
   - `turn_id`: Optional UUID.
   - `source_module`: String.
   - `payload_json`: String.
   - `occurred_at`: ISO-8601 UTC.

7. `ChannelRecord`:
   - `channel_id`: String (Primary Key).
   - `adapter_type`: String (e.g., 'discord_adapter', 'websocket_ui', 'rest_api').
   - `connection_status`: Enum (`CONNECTED`, `CONNECTING`, `DISCONNECTED`, `DEGRADED`, `SUSPENDED`).
   - `is_interactive`: Boolean.
   - `rate_limit_rpm`: Integer.
   - `last_heartbeat_at`: ISO-8601 UTC.

8. `ChannelCapabilityRecord`:
   - `capability_id`: UUID (Primary Key).
   - `channel_id`: String.
   - `supports_text`: Boolean.
   - `supports_markdown`: Boolean.
   - `supports_attachments`: Boolean.
   - `supports_reactions`: Boolean.
   - `supports_replies`: Boolean.
   - `supports_message_edit`: Boolean.
   - `supports_message_delete`: Boolean.
   - `supports_delivery_receipts`: Boolean.
   - `supports_cancellation`: Boolean.
   - `max_payload_length_bytes`: Integer.

9. `DeliveryRequest`:
   - `request_id`: UUID (Primary Key).
   - `conversation_id`: UUID.
   - `turn_id`: UUID.
   - `recipient_ids`: Tuple[UUID, ...].
   - `channel_id`: String.
   - `approved_content`: String.
   - `content_type`: Enum (`TEXT_PLAIN`, `MARKDOWN`, `AUDIO_STREAM`, `STRUCTURED_JSON`).
   - `authorization_id`: UUID.
   - `priority`: Enum (`CRITICAL`, `HIGH`, `NORMAL`, `BACKGROUND`).
   - `timing_constraints`: String (e.g., 'send_immediately', 'delay_until:ISO').
   - `created_at`: ISO-8601 UTC.
   - `expires_at`: ISO-8601 UTC.

10. `DeliveryReceipt`:
    - `receipt_id`: UUID (Primary Key).
    - `request_id`: UUID.
    - `message_id`: UUID.
    - `channel_id`: String.
    - `state`: Enum (`DELIVERED`, `PENDING_CONFIRMATION`, `TIMEOUT_UNCERTAIN`, `FAILED`, `CANCELLED`).
    - `attempt_count`: Integer.
    - `external_receipt_id`: Optional String.
    - `dispatched_at`: ISO-8601 UTC.
    - `acknowledged_at`: Optional ISO-8601 UTC.
    - `latency_ms`: Optional Integer.

11. `InteractionContextPackage`:
    - `package_id`: UUID (Primary Key).
    - `conversation_id`: UUID.
    - `session_id`: UUID.
    - `turn_id`: UUID.
    - `active_topic`: Optional String.
    - `unresolved_questions`: Tuple[String, ...].
    - `recent_messages`: Tuple[MessageEnvelope, ...].
    - `participant_profiles`: Tuple[ParticipantRecord, ...].
    - `applicable_preferences`: Tuple[CommunicationPreference, ...].

PART 5 — INTER-ENGINE COMMUNICATION CONTRACTS (12 CONNECTED SYSTEMS)
================================================================================

1. PERCEPTION ENGINE (`PerceptionContextProvider`):
   - Egress (Interaction -> Perception): Dispatches normalized `MessageEnvelope`
     with raw text, attachments, and channel metadata.
   - Ingress (Perception -> Interaction): Receives comprehension tokens, semantic
     intents, and parsed user goals.
   - Boundary: Interaction normalizes envelopes; Perception extracts meaning.

2. MEMORY ENGINE (`MemoryContextProvider` + `MemoryNominationContract`):
   - Egress (Interaction -> Memory): Dispatches `InteractionMemoryNomination` for
     completed turns deemed socially or factually significant.
   - Ingress (Memory -> Interaction): Receives retrieved historical conversational
     references when assembling deep context.
   - Boundary: Memory owns persistent biographical history; Interaction owns operational turns.

3. SOCIAL COGNITION ENGINE (`SocialCognitionProvider`):
   - Egress (Interaction -> Social): Dispatches participant identifiers, turn events,
     and raw conversational interaction data for Theory of Mind & relationship modeling.
   - Ingress (Social -> Interaction): Receives participant identity resolution,
     rapport scores, and social boundary warnings.
   - Boundary: Social Cognition models relationships; Interaction routes messages.

4. PERSONALITY ENGINE (`PersonalityContextProvider`):
   - Ingress (Personality -> Interaction): Ingests stable communication traits,
     verbosity biases, and warmth baselines.
   - Boundary: Read-only context for style formatting. Interaction never mutates personality.

5. EMOTION ENGINE (`EmotionalContextProvider`):
   - Egress (Interaction -> Emotion): Emits interaction trigger alerts (e.g., received
     praise, hostile remarks, communication interruptions).
   - Ingress (Emotion -> Interaction): Ingests current emotional state snapshot
     to modulate expressive tone in Content Coordination.
   - Boundary: Emotion owns Diva's feelings; Interaction applies tone constraints.

6. MOTIVATION ENGINE (`MotivationContextProvider`):
   - Egress (Interaction -> Motivation): Provides communication outcome receipts
     (e.g., social desire fulfilled, collaboration goal progressed).
   - Ingress (Motivation -> Interaction): Ingests communication drive signals via
     Cognitive Integration.
   - Boundary: Motivation drives desire to speak; cannot authorize dispatch directly.

7. THOUGHT ENGINE (`ThoughtContextProvider`):
   - Egress (Interaction -> Thought): Dispatches external turn events to seed
     internal thought threads.
   - Ingress (Thought -> Interaction): Receives proposed reasoning outputs via
     Cognitive Integration.
   - Boundary: Thought develops ideas; cannot directly broadcast onto channels.

8. LEARNING ENGINE (`LearningSignalContract`):
   - Egress (Interaction -> Learning): Dispatches `CommunicationPerformanceSignal`
     detailing turn dropouts, misunderstandings, and adapter latency metrics.
   - Ingress (Learning -> Interaction): Applies `ParameterChangeRequest` to
     `interaction.*` parameters (e.g., retry backoff factors, pacing delays) using v2.5.0 protocol.

9. FEEDBACK ENGINE (`FeedbackEngineContract`):
   - Egress (Interaction -> Feedback): Dispatches structured `InteractionOutcomeSignal`
     detailing delivery success, failure, timeout uncertainty, or user interruption.
   - Ingress (Feedback -> Interaction): Receives retrospective interaction evaluations.

10. AUTONOMOUS ACTIVITY & INITIATIVE ENGINE (`InitiationContract`):
    - Ingress (Autonomous -> Interaction): Receives `InitiationRequest` for self-directed outreach.
    - Egress (Interaction -> Autonomous): Returns initiation lifecycle receipts.
    - Boundary: Autonomous Activity proposes outreach; Interaction validates authorization.

11. COGNITIVE INTEGRATION & DECISION ENGINE (`CognitiveIntegrationContract`):
    - Ingress (Cognitive Integration -> Interaction): Executive directives, response
      authorizations (`AuthorizationRecord`), cancellation commands, and priorities.
    - Egress (Interaction -> Cognitive Integration): Operational context packages,
      turn states, interruption notices, and delivery outcomes.
    - Boundary: Cognitive Integration authorizes what to say; Interaction manages how it is sent.

12. SHARED LLM INFRASTRUCTURE (`SharedLLMContract`):
    - Egress (Interaction -> LLM): Formats structured generation briefs with approved
      intent, context package, and channel format limits.
    - Ingress (LLM -> Interaction): Streams rendered natural language text chunks.
    - Boundary: Interaction deterministically validates all LLM output before delivery.
