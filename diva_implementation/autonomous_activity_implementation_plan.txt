EXECUTIVE ARCHITECTURAL SUMMARY & GOVERNING PRINCIPLES
================================================================================

The Autonomous Activity & Initiative Engine is the engine that endows Diva with an
authentic, ongoing internal life, enabling her to exist as an agentic entity rather
than a passive reactive system awaiting external prompts. Its central responsibility
is to identify, formulate, organize, prioritize, schedule, monitor, and adapt activities
that Diva independently initiates—whether to pursue curious inquiries, advance
long-term goals, revisit unresolved questions, practice capabilities, maintain
commitments, or reflect on past experiences.

Crucially, the engine does NOT decide what Diva will execute, nor does it run tools:
The Autonomous Activity Engine PROPOSES and MANAGES activities; Cognitive Integration
& Decision AUTHORIZES them; and Shared Execution Infrastructure PERFORMS them.

--------------------------------------------------------------------------------
THE THREE PROTECTED ARCHITECTURAL RULES
--------------------------------------------------------------------------------
1. AN ACTIVITY IS NOT A MOTIVATION
   Motivation explains WHY Diva wants something (drives, desires, curiosity intensity).
   An activity describes WHAT she proposes to pursue and HOW it is structured
   (subtasks, dependencies, resources, completion criteria). The Motivation Engine
   does not track operational task steps; Autonomous Activity does not create basic drives.

2. AN INITIATIVE IS NOT A COMMITMENT
   Diva generates candidate initiatives freely across multiple internal and external
   triggers. Generating an idea does NOT obligate her to pursue it. A candidate only
   becomes a committed pursuit after validation, prioritization, and explicit authorization
   by Cognitive Integration.

3. AUTONOMY IS NOT UNRESTRICTED EXECUTION
   Diva operates under controlled autonomy. The engine maintains a rich portfolio of
   initiatives, but no external tool execution, file modification, or outbound
   communication may occur without formal authorization from Cognitive Integration.

--------------------------------------------------------------------------------
STRICT ARCHITECTURAL OWNERSHIP & BOUNDARY MATRIX
--------------------------------------------------------------------------------
Engine / Subsystem           | Owns                                           | Does NOT Own
-----------------------------|------------------------------------------------|-------------------------------------------
Motivation Engine            | Drives, desires, interests, goal priorities    | Activity task lifecycle, execution plans
Thought Engine               | Dynamic reasoning threads, hypotheses, DAGs    | Activity scheduling, portfolio management
Emotion Engine               | Affective states, mood dynamics, regulation    | Deciding activities based solely on mood
Memory Engine                | Persistent episodic and semantic retention     | Active operational portfolio state
Learning Engine              | Coordinating competence and parameter evolution| Scheduling every practice activity
Internal State Engine        | Energy, fatigue, cognitive workload, capacity  | Deciding which activity to run
Social Cognition Engine      | Person models, relationships, Theory of Mind   | Initiating social communication
Feedback Engine              | Retrospective outcome evaluation & attribution | Ongoing activity monitoring & adaptation
Interaction Engine           | Conversational turns, sessions, channel drivers| Deciding whether communication happens
Cognitive Integration        | Executive decisions, approvals, authorizations | Initiative generation and decomposition
Shared Execution Infra       | Sandboxed tool and script execution            | Generating motives or initiatives

PART 1 — HOW THE ENGINE RUNS: OVERALL EXECUTION MODEL & CONCURRENCY
================================================================================

1.1 MULTI-TIER ASYNCHRONOUS PIPELINE TOPOLOGY
   The Autonomous Activity Engine runs on Python 3.12+ `asyncio` utilizing an event-driven,
   prioritized queue architecture organized into three tiers:

   TIER 1 — INGRESS & SIGNAL HARVESTING (Fast-path Async, <20 ms):
   - Ingests incoming initiative signals from 10 connected engines via the `InitiativeSignalCollector`.
   - Filters noise, computes idempotency hashes, and drops duplicates via Bloom filters.
   - Places validated signals into the Ingress Signal Priority Queue.

   TIER 2 — CANDIDATE FORMATION & PORTFOLIO ARBITRATION (Core Async, <150 ms):
   - `InitiativeGenerator` transforms signals into `InitiativeCandidate` objects.
   - `CandidateValidator` checks feasibility, constraints, and dependencies.
   - `DuplicateDetectionManager` consolidates identical or semantically overlapping items.
   - `ActivityFormationManager` instantiates structured `ActivityRecord` hierarchies.
   - `ActivityPortfolioManager` updates the portfolio ledger and maintains limits.

   TIER 3 — MONITORING, SCHEDULING & ADAPTATION (Background Periodic Async):
   - `ActivityPriorityAssessor` computes multi-factor priority scores.
   - `SchedulingProposalManager` packages candidate schedules for Cognitive Integration.
   - `ProgressMonitor` listens to execution events from Shared Execution Infrastructure.
   - `ActivityAdaptationManager` detects blockers, stalls, or obsolete assumptions.
   - `UnfinishedActivityManager` reviews suspended tasks for potential resumption.

1.2 CONCURRENCY & PER-ACTIVITY ISOLATION MODEL
   - Every active activity tree (parent activity + subtasks) executes within an isolated
     `ActivityActor` coroutine loop.
   - Cross-activity dependencies are managed via asynchronous event barriers (`asyncio.Event`),
     ensuring that child task completions unlock downstream dependencies without race conditions.
   - Single-writer thread for SQLite persistence ensures atomic commits of portfolio state
     changes without database table lock contention.

1.3 RESOURCE-AWARE THROTTLING & SPONTANEOUS INITIATIVE CYCLES
   - Internal State Engine feeds $E_{\text{cog}}$ (cognitive energy) and $W_{\text{cog}}$ (workload).
   - High Resources ($E_{\text{cog}} \ge 0.60, W_{\text{cog}} \le 0.50$): Engine triggers periodic
     spontaneous initiative cycles (every 5 minutes during idle cognitive periods) to propose
     curiosity-driven exploration or maintenance reviews.
   - Moderate Resources ($0.30 \le E_{\text{cog}} < 0.60$): Spontaneous cycles throttled to once
     per 30 minutes; only goal-directed and essential maintenance candidates are formed.
   - Depleted Resources ($E_{\text{cog}} < 0.30$ or $W_{\text{cog}} > 0.85$): All initiative generation
     halted. Engine generates a `Recovery` activity proposal advising cognitive rest.

1.4 CRASH RECOVERY & STARTUP RECONCILIATION PROTOCOL
   Upon Diva system reboot:
   Step 1: Verify SQLite WAL database integrity (`PRAGMA integrity_check`).
   Step 2: Load all activities in non-terminal states (`IN_PROGRESS`, `AWAITING_DECISION`, `COMMITTED`).
   Step 3: Reconcile executing tasks: Any task recorded as `IN_PROGRESS` during crash is transitioned
           to `UNVERIFIED` state, querying Shared Execution Infrastructure for partial outputs.
   Step 4: Re-evaluate dependency DAGs: Unblock tasks whose prerequisites were committed before crash.
   Step 5: Expire stale proposals: Any proposal in `AWAITING_DECISION` older than 24 hours is moved
           to `DEFERRED` for portfolio review.
   Step 6: Mark engine lifecycle state `ACTIVE` and resume monitoring coroutines.

PART 2 — AUTONOMOUS ACTIVITY CATEGORIES & HIERARCHICAL TAXONOMY
================================================================================

2.1 NINE CORE ACTIVITY CATEGORIES
   Every candidate and activity belongs to one of nine distinct functional categories:
   1. `GOAL_DIRECTED`: Directly advances an established, active goal from the Motivation Engine.
   2. `CURIOSITY_DRIVEN`: Investigates unexplained or fascinating phenomena without requiring a goal.
   3. `EXPLORATION`: Open-ended discovery in new domains, permitting high outcome uncertainty.
   4. `LEARNING_PRACTICE`: Acquires new skills, tests capabilities, or addresses gaps noted by Learning.
   5. `CREATIVE`: Generates designs, concepts, prototypes, or novel problem formulations.
   6. `MAINTENANCE`: Checks project health, reviews known concepts, and prevents skill degradation.
   7. `REFLECTIVE`: Re-evaluates past mistakes, contradiction in beliefs, or reasoning failures.
   8. `SOCIAL`: Prepares for interactions, collaboration, or follows up on interpersonal ties.
   9. `RECOVERY`: Recommends cognitive rest, workload reduction, or lower-demand activities.

2.2 TEN OPERATIONAL ACTIVITY TYPES
   At the execution boundary, activities map to specific operational modalities:
   - `INVESTIGATION`: Internal or external question resolution.
   - `LEARNING`: Knowledge absorption and structured study.
   - `PRACTICE`: Capability exercise and performance evaluation.
   - `CREATION`: Production of code, artifacts, or written analysis.
   - `MAINTENANCE`: Routine health check or state validation.
   - `REFLECTION`: Epistemic re-evaluation of historical beliefs.
   - `EXPLORATION`: Broad scanning of conceptual territory.
   - `SOCIAL`: Interaction coordination via Interaction Engine.
   - `RECOVERY`: Idle, low-compute state for energy replenishment.
   - `PROJECT`: Coordinated parent container governing multiple sub-activities.

2.3 HIERARCHICAL GRAPH STRUCTURES & TASK DECOMPOSITION
   Activities form Directed Acyclic Graphs (DAGs) representing complex undertakings:
   - `Parent Activity`: High-level objective (e.g., "Build Vision Classifier").
   - `Child Subtasks`: Sequential or parallel executable units (e.g., "Fetch Dataset", "Train Model").
   - `Dependency Edges`: Explicit prerequisites (`FINISH_TO_START`, `START_TO_START`).
   - `Incomplete Plan Support`: Activities can be approved with partial decomposition; subtasks
     can be dynamically generated as earlier milestones complete.
   - `Anti-Premature Completion`: A parent activity CANNOT transition to `COMPLETED` while any
     mandatory child subtask remains incomplete.

PART 3 — INTERNAL ARCHITECTURE: THE TWENTY-TWO LOGICAL MODULES
================================================================================

--------------------------------------------------------------------------------
1. INITIATIVE SIGNAL COLLECTOR
--------------------------------------------------------------------------------
- Purpose: Ingestion point for raw signals from Thought, Motivation, Emotion, Memory,
  Perception, Learning, Feedback, and Internal State engines.
- Inputs: Heterogeneous inter-engine signal envelopes.
- Outputs: Standardized `InitiativeSignal` records queued for generator.
- Algorithms: Signal source authentication; payload validation; duplicate signal hash suppression.

--------------------------------------------------------------------------------
2. INITIATIVE GENERATOR
--------------------------------------------------------------------------------
- Purpose: Synthesizes signals into concrete `InitiativeCandidate` records.
- Inputs: Ingested `InitiativeSignal` instances; periodic spontaneous cycle ticks.
- Outputs: Candidate proposals with rationale, expected outcome, and category.
- Algorithms: Rule-based mapping for goal/maintenance triggers; Shared LLM synthesis for
  complex curiosity and reflective impulses; spontaneous candidate generator.

--------------------------------------------------------------------------------
3. CANDIDATE VALIDATOR
--------------------------------------------------------------------------------
- Purpose: Enforces quality, feasibility, and constraint gates on candidates.
- Inputs: Raw `InitiativeCandidate` records.
- Outputs: Validated candidate verdict (`ACCEPTED`, `REJECTED`, `DEFERRED`).
- Algorithms: Schema check; constraint verification against known systemic limits;
  dependency existence validation; reject logging with explicit reason codes.

--------------------------------------------------------------------------------
4. DUPLICATE DETECTION MANAGER
--------------------------------------------------------------------------------
- Purpose: Prevents identical or redundant activity proposals from entering the portfolio.
- Inputs: Validated candidates.
- Outputs: Dedup verdict (`UNIQUE`, `EXACT_DUPLICATE_DROP`, `SEMANTIC_MERGE`).
- Algorithms: Exact hash matching on (category, target_domain, objective_key);
  cosine similarity on vector embeddings of candidate descriptions (threshold $\ge 0.88$
  triggers semantic merge check); preserves all originating motivation references on merge.

--------------------------------------------------------------------------------
5. ACTIVITY FORMATION MANAGER
--------------------------------------------------------------------------------
- Purpose: Transforms accepted candidates into structured `ActivityRecord` hierarchies.
- Inputs: Accepted, deduplicated candidates.
- Outputs: Formal `ActivityRecord` instances with unique UUIDs and initial version 1.
- Algorithms: Schema instantiation; default resource budget allocation; baseline
  completion criteria derivation.

--------------------------------------------------------------------------------
6. ACTIVITY CLASSIFICATION MANAGER
--------------------------------------------------------------------------------
- Purpose: Categorizes activities into the 9 categories and 10 operational types.
- Inputs: Formed activities.
- Outputs: Tagged `ActivityRecord` with validated category and operational modality.
- Algorithms: Multi-label classification rules; category compatibility validation.

--------------------------------------------------------------------------------
7. ACTIVITY DECOMPOSITION MANAGER
--------------------------------------------------------------------------------
- Purpose: Breaks complex activities into ordered, manageable subtask trees.
- Inputs: Complex `ActivityRecord` requiring decomposition.
- Outputs: `ActivityHierarchy`, `ActivityPlan`, and `ActivitySubtask` records.
- Algorithms: Top-down hierarchical task decomposition (deterministic templates for routine
  tasks; Shared LLM synthesis for open-ended creative/investigative tasks); cycle detection
  on dependency graphs (Tarjan's strongly connected components algorithm).

--------------------------------------------------------------------------------
8. ACTIVITY PORTFOLIO MANAGER
--------------------------------------------------------------------------------
- Purpose: Maintains the complete ledger of all activities across all lifecycle states.
- Inputs: Formed, updated, or adapted activities.
- Outputs: Portfolio state queries, `PortfolioSnapshot` telemetry.
- Algorithms: Portfolio capacity enforcement; maintains counters for active, proposed,
  and suspended activities; blocks new proposals when portfolio limit ($N=200$) is reached.

--------------------------------------------------------------------------------
9. ACTIVITY PRIORITY ASSESSOR
--------------------------------------------------------------------------------
- Purpose: Computes objective, multi-factor priority scores for all candidate proposals.
- Inputs: Active activity records, current internal state, motivation drive intensities.
- Outputs: `ActivityPriorityAssessment` records with individual factor breakdown.
- Algorithms: Multi-Factor Priority Formulation (Section 9 of user request):
  $P_{\text{total}} = w_M \cdot M + w_G \cdot G + w_C \cdot C + w_V \cdot V + w_U \cdot U + w_F \cdot F + w_D \cdot D - w_R \cdot R$
  Where $M$=Motivation, $G$=Goal relevance, $C$=Curiosity, $V$=Expected Value, $U$=Urgency,
  $F$=Feasibility, $D$=Dependency importance, $R$=Resource cost.
  Preserves separate sub-scores; prevents exploration suppression by applying category floor boosts.

--------------------------------------------------------------------------------
10. SCHEDULING PROPOSAL MANAGER
--------------------------------------------------------------------------------
- Purpose: Prepares actionable scheduling recommendations for Cognitive Integration.
- Inputs: Priority assessments, dependency states, resource availability.
- Outputs: `ActivityScheduleProposal` records (`START_NOW`, `START_AFTER`, `RESUME_LATER`, `DEFER`).
- Algorithms: Topological sort on dependency DAGs; constraint satisfaction scheduling
  respecting energy limits and external time windows; adaptive schedule re-planning.

--------------------------------------------------------------------------------
11. ACTIVITY DEPENDENCY MANAGER
--------------------------------------------------------------------------------
- Purpose: Tracks and resolves prerequisite relationships between tasks.
- Inputs: Dependency declarations from Decomposition Manager.
- Outputs: Dependency status updates (`SATISFIED`, `BLOCKED`, `CIRCULAR_ERROR`).
- Algorithms: Directed graph traversal; prerequisite completion checks; cascading unblock events.

--------------------------------------------------------------------------------
12. EXECUTION COORDINATION INTERFACE
--------------------------------------------------------------------------------
- Purpose: Prepares execution briefs and coordinates approved tasks with Cognitive Integration.
- Inputs: Approved activities from Cognitive Integration.
- Outputs: `ActivityExecutionRequest` packages routed to Shared Execution Infrastructure.
- Algorithms: Parameter binding; input asset validation; cancellation condition attachment;
  enforces mandatory requirement: Zero execution without valid `AuthorizationRecord`.

--------------------------------------------------------------------------------
13. PROGRESS MONITOR
--------------------------------------------------------------------------------
- Purpose: Monitors real-time task progress, milestone achievements, and runtime telemetry.
- Inputs: Execution status events from Shared Execution Infrastructure.
- Outputs: `ActivityProgressRecord`, progress percentage updates.
- Algorithms: Progress delta tracking; heartbeat timeout detection (flags stalled tasks
  if zero progress recorded for $> 10$ minutes).

--------------------------------------------------------------------------------
14. ACTIVITY ADAPTATION MANAGER
--------------------------------------------------------------------------------
- Purpose: Proposes dynamic modifications when activities encounter blockers, invalid assumptions, or changing goals.
- Inputs: Blocker alerts, motivation change notifications, recurring execution errors.
- Outputs: `ActivityAdaptationProposal` (`MODIFY`, `RE_DECOMPOSE`, `SUSPEND`, `ABANDON`, `SUPERSEDE`).
- Algorithms: Assumption invalidation check; failure threshold evaluation; version incrementation on adaptation.

--------------------------------------------------------------------------------
15. UNFINISHED ACTIVITY MANAGER
--------------------------------------------------------------------------------
- Purpose: Prevents suspended or partially completed activities from being silently forgotten.
- Inputs: Suspended activity ledger, periodic portfolio review ticks.
- Outputs: Resumption candidate proposals, portfolio consolidation recommendations.
- Algorithms: Resumption Assessment Heuristic (checks goal relevance, resource availability,
  and validity of remaining subtasks); anti-accumulation pruning (archives stale tasks > 30 days).

--------------------------------------------------------------------------------
16. EXPLORATION MANAGER
--------------------------------------------------------------------------------
- Purpose: Specifically governs open-ended curiosity-driven exploration and branch limits.
- Inputs: Curiosity signals from Motivation / Thought engines.
- Outputs: `ExplorationRecord` instances, exploration branch proposals.
- Algorithms: Exploration tree tracking; Branching Cap Enforcer: Restricts active exploration
  branches to max 3 levels deep and max 5 concurrent branches to prevent cognitive divergence.

--------------------------------------------------------------------------------
17. RECURRENCE MANAGER
--------------------------------------------------------------------------------
- Purpose: Governs recurring maintenance activities, skill practice, and health reviews.
- Inputs: `ActivityRecurrenceRule` declarations.
- Outputs: Triggered maintenance proposals based on elapsed time or usage count.
- Algorithms: Cron-like / interval-based recurrence scheduling; checks completion status
  of previous cycle before spawning next instance.

--------------------------------------------------------------------------------
18. COMPLETION VALIDATOR
--------------------------------------------------------------------------------
- Purpose: Verifies whether an activity has truly achieved its defined success criteria.
- Inputs: Raw execution results, artifact references, test output data.
- Outputs: `ActivityCompletionRecord` (`COMPLETED`, `PARTIALLY_COMPLETED`, `UNVERIFIED`, `FAILED`).
- Algorithms: Deterministic assertion checking against `completion_criteria`; marks task
  `UNVERIFIED` if execution halted without positive verification proof; rejects false completion claims.

--------------------------------------------------------------------------------
19. ACTIVITY HISTORY MANAGER
--------------------------------------------------------------------------------
- Purpose: Persists immutable version history and lifecycle audit trails in SQLite.
- Inputs: State transitions, adaptation proposals, completion records.
- Outputs: `ActivityHistory` audit logs, historical session reconstruction data.
- Algorithms: Append-only ledger updates; JSON state snapshot serialization; version tracking.

--------------------------------------------------------------------------------
20. LIFECYCLE MANAGER
--------------------------------------------------------------------------------
- Purpose: Enforces valid state machine transitions for Candidates and Activities.
- Inputs: Proposed transition requests from modules.
- Outputs: Approved state transition or `InvalidActivityTransitionError`.
- Algorithms: Table-driven FSM verification; atomic status swap; guarantees transition legality.

--------------------------------------------------------------------------------
21. RESOURCE ASSESSMENT INTERFACE
--------------------------------------------------------------------------------
- Purpose: Translates Internal State Engine telemetry into activity feasibility constraints.
- Inputs: Cognitive energy $E_{\text{cog}}$, fatigue level, cognitive workload $W_{\text{cog}}$.
- Outputs: Resource feasibility coefficients attached to priority assessments.
- Algorithms: Workload estimation vs. available budget; rest proposal generation when $E_{\text{cog}} < 0.25$.

--------------------------------------------------------------------------------
22. EVENT PUBLISHER
--------------------------------------------------------------------------------
- Purpose: Dispatches outward activity status updates to external cognitive engines.
- Inputs: Lifecycle events, completion records, outcome evidence.
- Outputs: Typed asynchronous events to Feedback, Learning, Memory, Motivation, and Cognitive Integration.
- Algorithms: Asynchronous event queue distribution; guarantees delivery of outcome evidence.

PART 6 — INTER-ENGINE COMMUNICATION CONTRACTS (13 CONNECTED SYSTEMS)
================================================================================

1. MOTIVATION ENGINE (`MotivationContract`):
   - Ingress: Ingests drive intensities ($D_{\text{curio}}, D_{\text{social}}$, etc.), active candidate goals,
     and chronic need deficits.
   - Egress: Emits activity progress updates that satisfy or advance specific drives/goals.
   - Boundary Rule: Motivation owns desires; Autonomous Activity structures the work.

2. THOUGHT ENGINE (`ThoughtContract`):
   - Ingress: Ingests unresolved questions, abductive hypotheses, and reflective insights.
   - Egress: Dispatches activity contexts to seed background reasoning threads.
   - Boundary Rule: Thought generates ideas; Autonomous Activity manages task portfolios.

3. EMOTION ENGINE (`EmotionContract`):
   - Ingress: Ingests current mood valence/arousal snapshot and emotional alerts.
   - Egress: Emits activity milestone events (e.g., successful accomplishment or frustration) to stimulate emotional appraisals.
   - Boundary Rule: Emotions bias activity valuation; cannot force activity execution without validation.

4. MEMORY ENGINE (`MemoryContract`):
   - Ingress: Queries historical experiences and retrieves unresolved historical activities.
   - Egress: Dispatches `MemoryNomination` for completed autonomous activities deemed significant.
   - Boundary Rule: Memory stores durable biographical knowledge; Autonomous Activity owns working tasks.

5. PERCEPTION ENGINE (`PerceptionContract`):
   - Ingress: Ingests environmental affordances, sensory observations, and external opportunities.
   - Egress: Requests specific targeted sensory focus when required for an investigation.
   - Boundary Rule: Perception observes; Autonomous Activity identifies actionable initiatives.

6. LEARNING ENGINE (`LearningContract`):
   - Ingress: Ingests capability gaps, skill development recommendations, and practice goals.
   - Egress: Emits practice task completions and empirical trial results as `LearningSignal`.
   - Boundary Rule: Learning coordinates development; Autonomous Activity schedules concrete practice sessions.

7. FEEDBACK ENGINE (`FeedbackContract`):
   - Egress: Dispatches structured outcome records (`ActivityCompletionRecord`) for retrospective evaluation.
   - Ingress: Receives causal attribution feedback and recurring failure pattern warnings.
   - Boundary Rule: Feedback evaluates outcome quality; Autonomous Activity adapts future task proposals.

8. INTERNAL STATE ENGINE (`InternalStateContract`):
   - Ingress: Ingests cognitive energy ($E_{\text{cog}}$), workload ($W_{\text{cog}}$), and fatigue metrics.
   - Egress: Provides projected resource consumption profiles for scheduled candidate activities.
   - Boundary Rule: Internal State tracks fatigue; Autonomous Activity proposes rest activities when exhausted.

9. SOCIAL COGNITION ENGINE (`SocialCognitionContract`):
   - Ingress: Ingests relational rapport scores, interpersonal obligations, and partner availability.
   - Egress: Proposes collaborative or social outreach initiatives with target participant IDs.
   - Boundary Rule: Social Cognition models people; Autonomous Activity organizes interpersonal initiatives.

10. PERSONALITY ENGINE (`PersonalityContract`):
    - Ingress: Ingests constitutional baseline preferences, curiosity weights, and risk tolerance.
    - Boundary Rule: Personality parameters weight priority assessments; engine never mutates personality.

11. INTERACTION ENGINE (`InteractionContract`):
    - Egress: Transmits authorized outbound communication requests to external participants via Cognitive Integration.
    - Ingress: Receives message delivery receipts and external conversational completion signals.
    - Boundary Rule: Interaction delivers messages; Autonomous Activity originates the outreach initiative.

12. COGNITIVE INTEGRATION & DECISION ENGINE (`CognitiveIntegrationContract`):
    - Egress: Dispatches prioritized activity proposals, scheduling recommendations, and cancellation requests.
    - Ingress: Receives executive authorizations (`ActivityCommitment`), rejections, preemption overrides, and priorities.
    - Boundary Rule: Supreme executive gate. Zero activity moves to `IN_PROGRESS` without Cognitive Integration grant.

13. SHARED EXECUTION INFRASTRUCTURE (`ExecutionInfrastructureContract`):
    - Egress: Routes signed `ActivityExecutionRequest` packages for sandboxed tool/code execution.
    - Ingress: Receives streaming execution logs, error codes, and produced artifacts.
    - Boundary Rule: Autonomous Activity describes task requirements; Execution Infrastructure runs the code.
